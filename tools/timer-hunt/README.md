# 找闪电模式倒计时（实验脚本，非 bot 的一部分）

这里放的是「定位闪电模式那个 60 秒倒计时存在哪」用的探测脚本。
**不是 bot 运行所需的东西**，是排查过程留下的工具。

## 为什么这些脚本长这样

闪电模式一局只有 60 秒，而全进程扫描一度要 **145 秒**
（Python 逐 4 字节过滤 1007MB = 2.6 亿次迭代）——
「扫一遍、等几秒、再扫一遍」永远跨局，局末数值冻结，必然对不上。

改用 numpy 向量化后 **1.0 秒**扫完一遍，一局之内能扫几十遍，这才做得下去。

## 脚本

| 文件 | 用途 |
|---|---|
| `np_diff.py` | 两次全进程扫描逐位比对，找「N 秒内恰好降 N」的位置 |
| `final_scan.py` | 存图 + 扫所有 `== 0..61` 的地址，多轮取交集，用屏幕秒数精确匹配 |
| `watch_cands.py` | 盯住若干候选，每秒记录值 + 存倒计时截图，用于人工甄别 |
| `lock_time.py` | 把倒计时按住不动，方便从容观察时间宝石机制。**测试用，别长期开着** |

## 已确认的坐标

倒计时框在原图 **`x=500..620, y=20..80`**。
（我一度裁 `x=1000..1120`，拍出来全是空的，白费了好几轮。）

## 已经排除的方向

- `gApp+0x680` / `+0x4D0` / `+0x6E4` / `+0x6F8` —— 都不是本局倒计时
- `Board+0x30E4` —— 跳到 20 后不动
- `0xF98DBF0`（double，58.3→56.2）—— 看着极像，实为堆里被复用的位置
- `np_diff.py` 找出的 159 个「6 秒降 6」候选 —— 没一个逐秒 -1，都是动画计时器

## 一个记下来的坑

**别把扫描结果塞进 Python dict。** 我一次收了 105 万个键，
每遍扫描从 1 秒涨到 3.3 秒，10 遍跨过局末，拿到的全是冻结后的阶梯值。
现在全部用 numpy 原地比对，不建容器。

## lock_time.py 的注意点

它要写游戏内存（把倒计时按住）。`reader_mem.py` 本身是**只读**的，
写入逻辑只在这个脚本里，两者分开。

写入用 `process_vm_writev`，**iovec 必须用 `_IOV` 对象 + `ctypes.byref` 传参**。
第一版我写成 `(_IOV*1)(...)` 数组形式，返回 0 且 errno 也是 0，完全查不出原因。
