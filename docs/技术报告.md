# Bejeweled 3 Deck Bot —— 技术报告

> **项目**：Steam Deck 上 Bejeweled 3 的自动游玩机器人 + 游戏模式控制插件
> **开发方式**：**100% 由 AI 开发**（模型 `deepseek-v4.1-flash`）
> **报告日期**：2026-09-24
> **所有结论均基于真机实测；推断项与错误判断均已标注**

---

## 0. 一句话摘要

**用外置视觉（截屏识别 + 模拟鼠标）实现 Bejeweled 3 自动游玩，
单步耗时从 3940 ms 优化到 1155 ms，并做成 Steam Deck 游戏模式可一键开关的 Decky 插件。**

## 1. 项目定位与技术路线

### 1.1 为什么选"外置视觉"而不是"内存修改"

| 路线 | 可行性 | 取舍 |
|---|---|---|
| **内存读写/注入** | 技术可行（实测 `process_vm_readv` 达 1463 MB/s） | ❌ 需注入、风险高、易被视为作弊 |
| **外置视觉（采用）** | ✅ 实测可行 | 不碰游戏、不改文件、不改内存 |

**最终方案**：截屏 → 识别棋盘 → 求解 → 模拟鼠标点击。**纯外部行为，等同于一个人在看屏幕玩。**

## 3. 核心实现

### 3.1 抓帧：为什么必须用 PipeWire

| 方式 | 帧率 | 说明 |
|---|---|---|
| `gamescopectl screenshot` | **2.2 fps** | 只支持 PNG，瓶颈在编码（0.45 s/帧） |
| **PipeWire `pipewiresrc`** | **~90 fps** | 11 ms/帧，RGB 直出 |

```bash
gst-launch-1.0 -q pipewiresrc path=93 ! videoconvert \
  ! video/x-raw,format=RGB ! fdsink fd=1
```

**关键点**：
- `path=93` 是本机 PipeWire 节点号，**换机器必须改**（用 `pw-cli ls Node` 找）
- `fdsink` 会**短读**，必须累积到完整帧再解码（否则得到半截图）
- ⚠️ **不要用 `sudo`** —— 会清掉 `XDG_RUNTIME_DIR` 导致 PipeWire 连接失败

### 3.2 识别：静止判定与识别必须解耦 ★核心优化

**错误做法（最初版本）**：
```python
while not still:
    frame = grab()
    grid = read_grid_np(frame)     # ← 每帧都识别！50 ms/次
    if is_still(frame): break
```
一次等待要处理 40+ 帧 ⇒ **视觉开销累计 2147 ms/步**。

**正确做法**：
```python
while not still:
    d = frame_diff_downsampled()   # ← 只要 1 ms，不调识别
    if d < thr: still_frames += 1
grid = read_grid_np(frame)         # ← 确认静止后只识别一次
```

**效果**：视觉开销 **2147 ms/步 → 62 ms/步**。

### 3.3 静止判定：必须"先见运动、再见静止"

解耦后静止判定只要 40 ms，**远短于动画启动延迟** ⇒ bot 抢在动画开始前出手
⇒ 交换被游戏吃掉 ⇒ 连锁反应（反复无效交换、盲点击落到菜单）。

**规则**：
1. 先检测到运动（`d >= thr`）
2. 再检测到静止，且**静止须持续 ≥250 ms**
3. 才认定动画演完

### 3.4 pending 复用 ★第二大优化

**问题**：每步都重新"等交换前静止"，但**上一步结束时已确认过静止** —— 纯重复劳动。

**实现**：如果是有效交换，把本次的静止识别结果存为 `pending`，下一步直接复用。

| 配置 | 步/秒 | 每步 | 等待 | 识别 |
|---|---|---|---|---|
| 无 pending | 0.48 | 2080 ms | **1523 ms** | 154 ms |
| **有 pending** | **1.11** | 900 ms | **642 ms** | 62 ms |

### 3.5 求解器

**计分表（真实游戏规则）**：3 连=50 / 4 连=100 / 5 连=200 / 6 连=300 / 7 连=400 / 8+连=500，
含连消倍数、底部优先、特殊宝石权重、终局潜力评估。

**超立方体规则**：`S ↔ X` ⇒ 清空所有 X 并消耗 S。

**实测效果**：`solver_pro` 优于 `solver_fast` **2.17 倍**（695 vs 320 均分/步）。

**⚠️ 重要发现：得分本质随机，无法预测**
- 预测/实际相关性仅 **0.083**
- 292 个真实候选中，90% 只消 3 格、80% 只连消 1 层
- 期望分区间 50–342（中位 67），但实际出现 500 / 880 / 3450

### 3.6 执行：必须用相对移动 ★重要否证

| 方式 | 结果 |
|---|---|
| **`EV_REL` 相对 + 撞角归零**（`vmouse2.py`） | ✅ **30/30 成功** |
| `EV_ABS` 绝对定位（试验） | ❌ **游戏收到点击并高亮，但交换不被接受** |

**结论：本 gamescope 环境必须用相对移动，不要用绝对定位。**

**交互方式对照**：

| 方式 | 成功率 |
|---|---|
| `drag`（相对，3 步） | ✅ 30/30 |
| click-click（绝对） | 部分 |
| drag-1step（绝对） | ❌ |
| micro-drag（绝对） | ❌ |

## 4. 性能

### 4.1 优化链条（5 环）

| # | 问题 | 修复 | 效果 |
|---|---|---|---|
| 1 | **每帧都跑识别（50 ms/次）** | 解耦：静止判定只用 1 ms 像素差 | 视觉 2147 → 62 ms/步 |
| 2 | 静止判定 40 ms < 动画 535 ms | `min_still_ms=250` + 运动感知 | 有效 98% |
| 3 | 漏"拉黑" ⇒ 无效交换无限重试 | 恢复拉黑（同格 3 次无效标 `?`） | 不再死循环 |
| 4 | 每次新建鼠标（+0.4 s） | 设备常驻 | −400 ms/次 |
| 5 | **每步重复"等交换前静止"** | **pending 复用** | 等待 1523 → 458 ms |

### 4.2 实测结果（100 步长跑）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| **单步耗时** | 3940 ms | **1155 ms** |
| **步/秒** | 0.25 | **0.87** |
| **分/秒** | 26.2 | **168.3** |
| 有效率 | — | **98/100** |
| 净得分 | — | **+14,900** |

### 4.3 ★ 物理下限与"假速度"陷阱

**干净测量**（`tools/measure_anim2.py`，设备常驻 + 纯像素差轮询）：

| 组成 | 耗时 | 说明 |
|---|---|---|
| 拖动 | 182 ms | 游戏需要收到按下-移动-抬起 |
| **消除动画** | **535 ms** | 游戏自己的动画，改不了 |
| **合计下限** | **717 ms** | ⇒ 上限 **1.39 步/秒** |

**⚠️ 假速度陷阱**：曾跑到 **1.39 步/秒**（720 ms/步）看着最漂亮，
但它的 **分/秒只有 69.4，低于基线** —— 因为等待压得太短，**部分步抢在动画结算前出手**，
交换被吃掉 ⇒ 步数虚高、得分虚低。

> **裁定任何速度优化必须用「分/秒」（净得分/秒），不能只看步/秒。**

### 4.4 静止窗裁定

| 组 | 步/秒 | 等待 | 有效 | **分/秒** |
|---|---|---|---|---|
| 无 pending | 0.25 | 2583 ms | 98% | 26.2 |
| **s250 ★最优** | **0.86** | 888 ms | **98%** | **168.3** |
| s350 | 0.79 | 989 ms | 95% | 124.4 |
| s450 | 0.80 | 969 ms | 92% | 58.6 |

**`--still-ms 250` 最优** —— 等待窗加大反而劣化（多等没换来更高命中率，只降步速）。

## 5. 被证伪的路线（诚实记录）

### 5.1 SpeedHack 时间加速 —— 已证伪

**思路**：hook 游戏的时间函数（`timeGetTime` / `Sleep` 等）加速动画。

**完整实现的 IAT hook 基础设施**：
- `/proc/pid/mem` 可写只读页（`process_vm_writev` 不行）
- 代码洞 `0x008bd000-0x008d6000`
- 定位全部 8 个时间函数 IAT

**结果**：**两次把游戏搞崩**，最终结论 **时间 API 加速不可行**。
- 第一次：只 hook `Sleep` 降 8 倍 ⇒ 画面冻结
- 第二次：**BASE 用错**（用了 Linux `time.time()` 而非游戏自身 tick）⇒ `real-BASE` 回绕 257 次 ⇒ 状态机崩溃
- 修正 BASE 后游戏能进棋盘，但 **SpeedHack 零效果**（A/B 均为 9.877 s）

**同时也证伪了目标前提**：见下节。

### 5.2 "动画占 96.7%" —— 测量假象

**原假设**：单步 1975 ms 中 1900 ms（96.7%）是游戏动画。

**实测推翻**（逐阶段剖析）：

| 阶段 | 平均耗时 | 占比 |
|---|---|---|
| **vision（识别）** | **2146.9 ms** | **32.8%** |
| quiet_wait（等静止） | 2353.3 ms | 35.9% |
| post_wait | 1718.3 ms | 26.2% |
| grab / drag / solve | 335.1 ms | 5.1% |
| **合计** | **6553.6 ms** | 100% |

**关键**：`quiet_wait`(2353 ms) 里 **vision 占 2147 ms（91%）**
—— 因为原代码**每帧都识别**。

> **那 2.1 秒与游戏动画毫无关系，纯粹是自己的代码开销。**

**游戏动画真实只有 535 ms。**

### 5.3 内存定位动画变量 —— 未证伪但未成功

**Phase 1~3（全部只读，零事故）**：
- 两阶段快照（全量 A 1.032 s → 增量 diff 1.541 s）
- 热页 1206 → 394 span / **4.71 MB** → 采样 **13.76 ms/轮，146 轮**
- 完整候选集 **70,568** 个地址

**关键发现**：
- **背景动画陷阱**：`0x0f9b6570` 动画期变 266 次，但**静止时也变 47 次**
  ⇒ 必须加"静止时不变"的反向条件，得到 **50,567 个"仅动画"地址**
- **Phase 3 交叉引用：22,301 个候选中只有 16 个（0.07%）被绝对寻址引用**
  ⇒ 游戏变量通过 **基址寄存器 + 偏移**访问（`mov eax,[ebx+0x2c]`）
  ⇒ **佐证了独立的"棋盘是指针/对象图"结论**
- 计数器波形搜索命中 6 个候选，**全部被 3 次交换重现性排除**（是单调累加器，不是周期进度）

**结论**：动画控制变量逆向**尚未被证伪**，但**也不需要** —— 因为瓶颈根本不是游戏动画。

### 5.4 棋盘内存搜索 —— 死路

5 种方法、零命中。结合 Phase 3 的指针图结论，**不再重复尝试**。

## 6. Decky 插件（游戏模式开关）

### 6.1 为什么需要

**Steam Deck 游戏模式没有终端** —— `./run2.sh on` 只能在桌面模式或 SSH 用。
所以做成 Decky 插件，在侧边栏（QAM）一键开关。

### 6.2 架构

```
QAM 面板（React + TS）
    ↓ @decky/api callable (RPC)
main.py（status / start / stop / logs）
    ↓ subprocess
/home/deck/run2.sh   ← 复用已实测可用的控制台，不在插件里重造
```

### 6.3 ★ 开发中踩的四个坑（全部实测）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| **1** | **手写 bundle 猜 `window.DFL`** | **整个 QAM 白屏、插件商城打不开** | 必须用 `@decky/rollup` 正规构建 |
| **2** | 本容器 arm64，装 x64 rollup | `EBADPLATFORM` | 换 `@rollup/rollup-linux-arm64-gnu` |
| **3** | `tsconfig` 的 `jsx: "react-jsx"` | 产物引入 `SP_JSX`（Decky 不注入） | 必须设 `"react"`（classic） |
| **4** | **`LD_LIBRARY_PATH` 污染** | 子进程调 `/bin/bash` 崩 `rl_trim_arg_from_keyseq` | `_env()` 里清空 `LD_LIBRARY_PATH` |

**坑 1 的细节**（最严重）：
`DFL` **不是全局变量**，而是 rollup 打包 `@decky/ui` 后的**局部绑定名**。
手写 bundle 时 `window.DFL` 是 `undefined` ⇒ `DFL.definePlugin()` 抛异常
⇒ **Decky 整个前端崩溃**。

**坑 4 的细节**：
Decky 用 PyInstaller 打包，把解包目录注入 `LD_LIBRARY_PATH`：
```
实测: LD_LIBRARY_PATH=/tmp/_MEIPmBEEx
$ LD_LIBRARY_PATH=/tmp/_MEIPmBEEx /bin/bash -c "echo ok"
  symbol lookup error: undefined symbol: rl_trim_arg_from_keyseq
$ LD_LIBRARY_PATH="" /bin/bash -c "echo ok"
  ok
```
修法：`env["LD_LIBRARY_PATH"] = ""`

### 6.4 ★ 隔离验证（装前必跑）

`verify.mjs` 在 node 里模拟 Decky 环境，**6 项检查**：

```
① 全局变量检查   只用 SP_REACT，无未经检验的全局
② DFL 绑定检查   不引用 window.DFL
③ bundle 执行    无异常
④ definePlugin   返回 title/content/icon/onDismount
⑤ 组件渲染       模拟 React 调用 Content 组件，无异常
⑥ RPC 契约       status/start/stop/logs 与后端一致
```

**⑤ 是重点** —— 坑 1 是**渲染期**才炸的，光看加载日志发现不了
（`Loaded BJBot` 只证明后端起来了）。

## 8. 方法论沉淀

1. **"每帧都识别"是最容易犯的性能错误** —— 静止判定该用便宜特征（像素差）
2. **裁定速度优化必须用"有效吞吐"（分/秒），不能只看步数/秒** —— 否则会优化出"假速度"
3. **物理下限要单独测** —— 不测就不知道"还差多少"，也不知道"再快就是丢步"
4. **目标的前提也要验证** —— 本项目最大的发现是"动画 96.7%"这个前提本身就是错的
5. **否定性结论同样有价值** —— SpeedHack 证伪、绝对定位证伪，都节省了后续时间
6. **改动系统级组件前先隔离验证** —— 本项目曾把 Decky 前端搞崩
7. **日志"成功"不等于功能可用** —— `Loaded` 只说明后端起来了
