# 技术报告

Steam Deck 上自动玩 Bejeweled 3 的完整方案。2026-09-24。

文中所有数字都是真机测出来的。推断的地方会说明是推断，判断错的地方也会写明。

## 为什么是外置视觉

一开始想过读游戏内存。技术上完全可行，`process_vm_readv` 实测能到 1463 MB/s，
同一个 uid 不需要 root。但那样得注入，风险高，而且说白了是在作弊。

最后选了外置视觉：截屏、认棋盘、算一步、动鼠标。整个过程游戏感知到的东西
和一个真人玩没什么区别。

运行环境是 Steam Deck，SteamOS，Bejeweled 3（AppID 78000），
GE-Proton10-32，1280x800，装了汉化高清补丁。

## 整体流程

```
截屏        PipeWire 直取，90 帧每秒，一帧 11 毫秒
  ↓
静止判定    降采样后做像素差，一毫秒一帧，不调用识别
  ↓
识别        64 格宝石颜色，按高饱和像素投票
  ↓
求解        模拟连消 + 真实计分表 + 终局潜力
  ↓
执行        uinput 虚拟鼠标，相对移动
```

代码分层：

| 层 | 文件 | 干什么 |
|---|---|---|
| 抓帧 | `capture_pw.py` `cap2.py` | PipeWire 取帧，处理短读 |
| 识别 | `vision_np.py` `reader_fast.py` | 认颜色，以及静止判定 |
| 求解 | `solver_pro.py` `solver_fast.py` | 算消哪一步分高 |
| 执行 | `vmouse2.py` | 虚拟鼠标 |
| 主控 | `bot_v6.py` | 主循环、拉黑、pending、抗遮挡 |
| 守护 | `watch2.py` | 游戏一起就跟着跑 |
| 控制台 | `run2.sh` | 开关和日常操作 |
| 标定 | `calib.py` | 棋盘标定 |
| 游戏模式 | `decky-plugin/BJBot/` | 侧边栏开关 |

## 抓屏为什么非得用 PipeWire

| 方式 | 帧率 | 说明 |
|---|---|---|
| `gamescopectl screenshot` | 2.2 fps | 只出 PNG，编码就花了 0.45 秒 |
| PipeWire `pipewiresrc` | 90 fps | 一帧 11 毫秒，直接出 RGB |

```
gst-launch-1.0 -q pipewiresrc path=93 ! videoconvert \
  ! video/x-raw,format=RGB ! fdsink fd=1
```

三个注意的地方。`path=93` 是这台机器的 PipeWire 节点号，换机器一般要改，
用 `pw-cli ls Node` 找。`fdsink` 会短读，必须攒够一整帧再解码，不然拿到半张图。
还有别用 sudo，会把 `XDG_RUNTIME_DIR` 清掉，PipeWire 就连不上了。

## 性能这件事

### 原本的假设是错的

一开始我以为单步 1975 毫秒里有 1900 毫秒是游戏的消除动画，占了 96.7%。
照着这个思路优化了半天，后来逐阶段计时才发现根本不是：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 识别 | 2146.9 ms | 32.8% |
| 等静止 | 2353.3 ms | 35.9% |
| 交换后等待 | 1718.3 ms | 26.2% |
| 抓帧 / 拖动 / 求解 | 335.1 ms | 5.1% |
| 合计 | 6553.6 ms | 100% |

看第二行，"等静止"这 2353 毫秒里有 2147 毫秒是识别。因为原来的代码在每一帧
都调用识别，一次等待要处理四十多帧。

也就是说，那两秒多跟游戏动画一点关系都没有，全是我自己代码的开销。

### 动画到底多长

把识别从等待循环里摘掉之后，用纯像素差重新测，测了六次：

| 交换 | 拖动 | 首次运动 | 末次运动 |
|---|---|---|---|
| (4,2)↔(4,3) | 182 ms | 472 ms | 472 ms |
| (4,0)↔(4,1) | 183 ms | 478 ms | 589 ms |
| (4,2)↔(4,3) | 181 ms | 182 ms | 195 ms |
| (4,2)↔(4,3) | 183 ms | 491 ms | 535 ms |
| (4,2)↔(4,3) | 181 ms | 无运动 | 无运动 |
| (4,2)↔(4,3) | 182 ms | 150 ms | 622 ms |

中位数：拖动 182 毫秒，动画 535 毫秒。

所以单步的下限是 182 + 535 = 717 毫秒，换算成速度是每秒 1.39 步。
原来定的"降到 500 毫秒级"其实物理上做不到，除非不等动画演完，但那样会丢步。

### 五步优化

第一步也是收益最大的一步，把静止判定和识别拆开。等待的时候每帧只做像素差
（一毫秒），确认静止了才认一次棋盘。识别开销从每步 2147 毫秒降到 62 毫秒。

第二步，判断静止之前先得看见画面在动。拆开之后静止判定 40 毫秒就成立了，
比动画启动还快，bot 抢在动画前面出手，交换全被吃掉。

第三步，恢复拉黑机制。我在重写的时候漏掉了这个，结果无效交换被无限重试，
实测同一招重复了三十多次。

第四步，虚拟鼠标改成常驻。构造的时候有 0.4 秒的 sleep，每步都新建就等于
每步白花 400 毫秒。

第五步，pending 复用。上一步结束的时候已经确认过静止了，这一步不用再等一遍。

| 配置 | 步/秒 | 每步 | 等待 | 识别 |
|---|---|---|---|---|
| 没有 pending | 0.48 | 2080 ms | 1523 ms | 154 ms |
| 有 pending | 1.11 | 900 ms | 642 ms | 62 ms |

### 假速度的坑

中间有一版跑到 1.39 步每秒，每步 720 毫秒，看着是所有版本里最漂亮的。
但它的分/秒只有 69.4，比基线还低。

原因是等待压到 458 毫秒，动画还没结算完就出手了，交换被游戏吃掉。步数是上去了，
得分反而少了。

后来就改成看分/秒，不看步/秒。

### 静止窗取多少

四十步一组，看分/秒：

| 静止窗 | 步/秒 | 等待 | 有效 | 分/秒 |
|---|---|---|---|---|
| 无 pending | 0.25 | 2583 ms | 98% | 26.2 |
| 250 ms | 0.86 | 888 ms | 98% | 168.3 |
| 350 ms | 0.79 | 989 ms | 95% | 124.4 |
| 450 ms | 0.80 | 969 ms | 92% | 58.6 |

250 毫秒最好。再往上加反而更差，多等的时间并没有换来更高的命中率，
只是把步速拖下来了。

### 最后的结果

跑了 100 步，两轮：

| 轮次 | 步/秒 | 每步 | 有效 | 净得分 | 分/秒 |
|---|---|---|---|---|---|
| 第一轮 | 1.10 | 910 ms | 97/100 | +11560 | 119.9 |
| 第二轮 | 0.87 | 1155 ms | 98/100 | +14900 | 124.7 |

单步从 3940 毫秒降到 1155 毫秒，分/秒从 26.2 涨到 168.3。

## 求解器

计分表是按游戏实际规则来的：三连 50 分，四连 100，五连 200，六连 300，
七连 400，八连以上 500。再加上连消倍数、底部优先、特殊宝石权重和终局潜力。

超立方体的规则单独处理：S 和 X 交换，消掉所有 X。

`solver_pro` 比 `solver_fast` 强一倍多（均分 695 对 320）。

有个发现值得记一下：得分基本是随机的，预测不了。预测和实际的相关性只有
0.083。292 个真实候选里，90% 只消三格，80% 只连消一层。期望分区间是 50 到
342，中位数 67，但实际跑出过 500、880、3450 这种分。

调参也试过，六组权重各跑两轮，同一组在两次之间能差十倍，权重完全被噪声淹没。

## 输入这件事

必须用相对移动。

| 方式 | 结果 |
|---|---|
| EV_REL 相对 + 撞角归零 | 30/30 成功 |
| EV_ABS 绝对定位 | 游戏收到点击也高亮了，但交换不接受 |

绝对定位那版我一开始以为是它绕过了鼠标加速所以更好，实际上它在 gamescope
下面根本不生效。排查了好久才发现"落点漂移"的真凶是这个。

拖动方式也试了几种：相对移动分三步拖是 30/30；绝对定位下的点击-点击只有
部分成功；一步到位和微拖都是全败。

## 被否掉的几条路

### SpeedHack 时间加速

思路是 hook 游戏的时间函数来加快动画。IAT hook 的基础设施全做好了：
`/proc/pid/mem` 能写只读页，代码洞在 `0x008bd000-0x008d6000`，
八个时间函数的 IAT 都定位到了。

结果是把游戏搞崩了两次。第一次只 hook Sleep 降八倍，画面直接冻住。第二次
BASE 用错了，拿 Linux 的 `time.time()` 当游戏 tick，导致 `real-BASE` 回绕了
257 次，状态机崩了。改成游戏自己的 tick 之后游戏能进棋盘，但加速效果是零，
A/B 对比都是 9.877 秒。

结论：时间 API 加速这条路走不通。

### 动画变量逆向

Phase 1 到 3 全是只读的，没出事故。两阶段快照拿到热页 1206 个，压缩到 394 个
span 共 4.71 MB，采样 13.76 毫秒一轮。完整候选集 70568 个地址。

中间发现一个背景动画的陷阱：`0x0f9b6570` 在动画期间变 266 次，但静止的时候
也变了 47 次。加上"静止时不变"的条件之后，剩 50567 个真正的动画相关地址。

Phase 3 交叉引用：22301 个候选里只有 16 个（0.07%）被绝对寻址引用。说明游戏
变量是通过基址寄存器加偏移访问的，`mov eax,[ebx+0x2c]` 这种。这跟另一个独立
结论对上了——棋盘是个指针/对象图。

计数器波形搜索命中六个候选，全部被三次交换的重现性排除了，它们都是单调累加器，
不是周期进度。

结论：动画控制变量的逆向没有被证伪，但也不需要做了，因为瓶颈压根不是动画。

### 棋盘内存搜索

五种方法零命中。结合上面的指针图结论，就不再折腾了。

### 自动标定

做过，不靠谱。覆盖率这个指标会随关卡背景变：同一套正确参数，白天丛林是 0.912，
夜间森林只有 0.568。自动搜索在夜间会漂到错的位置，而且因为分数看起来更高，
它还以为自己找对了。

所以 `calib.py` 最后做成了可视化的：画网格、打印识别结果、存张图让人眼确认。

## Decky 插件

游戏模式没有终端，`./run2.sh on` 在那边用不了。所以做了个 Decky 插件，
把开关放进侧边栏。

结构是插件面板调 `main.py` 的四个方法（status、start、stop、logs），
`main.py` 再去调已经验证过的 `run2.sh`，不在插件里重造一遍。

### 四个坑

第一个最惨。我手写前端 bundle 没编译，猜了个全局变量 `window.DFL`。实际上
`DFL` 不是全局变量，是 rollup 打包 `@decky/ui` 之后的局部绑定名，只在那个
bundle 内部存在。所以它是 undefined，`DFL.definePlugin()` 抛异常，整个 QAM
面板白屏，连插件商城都打不开。

麻烦的是加载日志显示的是成功的——`found plugin`、`Loaded` 都正常。那只说明
后端起来了，前端的错要到 Steam UI 真正渲染面板的时候才暴露。

第二个，本机构建环境是 arm64，`@rollup/rollup-linux-x64-gnu` 装不上，报
EBADPLATFORM，得换成 arm64 版的。

第三个，`tsconfig.json` 里 `jsx` 设成 `react-jsx` 的话，产物会引用 `SP_JSX`
这个全局。对比参考插件的产物只有 `SP_REACT`，说明 `SP_JSX` 是 Decky 不注入的。
必须设成 classic 的 `react`。

第四个，Decky 用 PyInstaller 打包，运行时会把解包目录塞进 `LD_LIBRARY_PATH`。
实测是 `/tmp/_MEIPmBEEx`，里面有它自带的 libreadline。子进程调 `/bin/bash`
的时候加载到错误版本，直接崩：

```
$ LD_LIBRARY_PATH=/tmp/_MEIPmBEEx /bin/bash -c "echo ok"
/bin/bash: symbol lookup error: undefined symbol: rl_trim_arg_from_keyseq
$ LD_LIBRARY_PATH="" /bin/bash -c "echo ok"
ok
```

修法就是在 `_env()` 里清空 `LD_LIBRARY_PATH`。这个处理方式是从参考项目
`decky-wmsxwd` 的源码里学来的，它当年踩过同一个坑。

### 装之前先验证

`verify.mjs` 在 node 里模拟 Decky 环境做六项检查。重点是第五项，真的调用一次
组件函数，抓渲染期的异常。第一个坑就是渲染期才炸的，光看加载日志发现不了。

## 一些经验

每帧都识别是很容易犯的性能错误，静止判定该用便宜的特征。

优化速度要看有效吞吐，光看步数会优化出假速度。

物理下限要单独测，不然不知道还差多少，也不知道再往上就是丢步。

目标的前提也得验证。这个项目最大的发现就是"动画占 96.7%"这个前提本身错了。

否定的结论也有价值。SpeedHack 和绝对定位都证伪了，后面就不用再花时间。

改系统级的东西之前先在隔离环境跑一遍，不然容易把用户环境搞崩。

日志显示成功不等于功能可用。

不要拿着异常日志就倒推是自己的代码有问题，先问清楚用户干了什么。

## 已知的限制

标定跟分辨率和画质绑死了，换一样就得重做。

抓屏依赖 PipeWire，没有的话得改实现，我没试过。

`path=93` 是机器相关的。

标定没法全自动，覆盖率随背景变，必须人眼看。

得分预测不了，相关性只有 0.083。
