## 二、关键技术突破（按价值排序）

### ★★★ 2.1 PipeWire 抓帧：11 ms/帧，零注入

**问题**：`gamescopectl screenshot` 只有 **2.2 fps**（0.45 s/帧），瓶颈在 PNG 编码。

**突破**：gamescope 暴露一个 `Video/Source` 节点（`node.name=gamescope`，`path=93`）：

```bash
gst-launch-1.0 -q pipewiresrc path=93 ! videoconvert \
  ! video/x-raw,format=RGB ! fdsink fd=1
```

→ 原始 RGB 3072000 字节/帧，**90.7 fps（11.07 ms/帧）**。

**意义**：原以为要写 D3D9 注入 DLL 才能拿到的速度，用现成 PipeWire 就够了——**零注入、零风险**。

### ★★★ 2.2 内存直读：0.0067 ms，免 root

**实测性能**：

| 操作 | 耗时 |
|---|---|
| 读一个 int32 | **0.0067 ms** |
| 读 64 KB | **0.021 ms** |
| 全量快照（1.1 GB） | **0.76 s**（1463 MB/s） |

**免 root**：同 uid 直接 `process_vm_readv` 即可（483 个可写区，写入权限已验证）。

⚠️ **禁忌**：**不要用 `sudo`** —— sudo 会清空 `XDG_RUNTIME_DIR`，导致 PipeWire 抓帧失败（表现为"读不到棋盘"）。

### ★★★ 2.3 用户提出的定位方法（本次最高价值）

> **"多走几步让分数变大再搜，内存地址不就更少了吗"**

**实测验证，完全正确**：

| 搜索值 | 候选数 |
|---|---|
| `400` | **1603 个** |
| `10940` | **14 个** |
| `12110` | **4 个** |

⇒ 分数越大候选越少，**一步就能定死**。这是整个修改器工作的突破口。

### ★★ 2.4 分数在内存里的结构与位置规律

```
0x0f405ee4  ← 权威源（写它才生效）
0x0f405f24  ← 同步副本（相距 0x40；写它会被游戏立刻覆盖回权威值）
```

**位置规律**：分数**总是**落在 **`0x0f400000` 起的 64 KB 窗口**内：

| 会话 | 分数地址 |
|---|---|
| 第 1 次 | `0x0f403bf0` |
| 第 2 次 | `0x0f405aec` |
| 第 3 次 | `0x0f405ee4` |
| 第 4 次（游戏重启后） | `0x0f405ee4`（**位置不变**） |

⇒ 这是 Wine 的**确定性映射区**。定位从"扫 1.1 GB"缩到 **"扫 64 KB"**（快 17000 倍）。

## 四、未成功的方向（诚实记录）

### 4.1 内存读棋盘：5 种方法全部零命中

| 方法 | 参数范围 | 结果 |
|---|---|---|
| 紧凑数组匹配 | u8/i16/i32 × 行列主序 × 容错 | ❌ 最佳 40/64 |
| 步长扫描（结构体数组） | 15 种 struct_size × 全偏移 | ❌ 最高 36/64 |
| 64 指针数组（`Gem* board[8][8]`） | 6 个区域，判定指针有效性 | ❌ 无 |
| 32 位带状态位掩码 | low3/low4/low5/low8/exact | ❌ 无 |
| 多重集特征（不要求顺序） | 全内存 | ❌ 无 |

**一致性实验的发现**（连走 3 步找"每次都变"的地址）：

- 每次都变化的地址 **103,706 个**
- 其中值恰好在 1..7 的只有 3 个，集中在 `0x01098xxx`
- 但该区域**地址间隔 4/8/16/44/116 混杂，值里全是堆指针**（`0x01099xxx`、`0x2248xxx`）

**结论**：棋盘是**通过指针树索引的对象集合**（对象图），不是任何形式的数组。要定位它需要**指针链分析**（跟根指针 → 容器 → 棋盘），属**数小时级深度逆向**，且不保证成功。

### 4.2 原版 KelSat 修改器：无法修复

**根因：代际不兼容**

| 事实 | 内容 |
|---|---|
| 修改器针对 | **`popcapgame1.exe`**（2010-12-11，v1.0.8.6128） |
| 游戏实际运行 | **`Bejeweled3.exe`**（Steam 版，2019-07-14） |
| 后果 | 修改器**按进程名找不到游戏** → "没有检测到程序" → 完全无反应 |
| 实测替代方案 | 用 `popcapgame1.exe` 启动游戏 → Steam 加载界面出现 → **随即退出**，此路不通 |
| 自身问题 | **ASPack 壳**（字符串/地址全加密）、快捷键 **NUMPAD0~9**（Deck 无小键盘）、GUI 托盘程序 |

**它的 9 项功能清单**（GBK 解码原文，后续扩展参照）：
```
NUMPAD0 一百万分数   NUMPAD5 无限移动数
NUMPAD1 一百万金矿   NUMPAD6 无限炸弹时间
NUMPAD2 当前等级完成 NUMPAD7 红蓝点数总是平衡
NUMPAD3 当前任务完成 NUMPAD8 扑克总是同花
NUMPAD4 无限时间     NUMPAD9 冰块用不上升
```
✅ 已完成 2/9（分数、立即过关）。

### 4.3 无限时间（闪电模式）：受挫

| 困难 | 说明 |
|---|---|
| 每局仅 1 分钟 | 定位需反复采样验证，一局做不完 |
| 计时器有多个副本 | 11 个"写后保持"的候选，写 600 秒**画面差异全为 0** |
| 画面永远在动 | 瀑布+宝石动画，致差异判据大量误报 |

**已排除**：不在 `0x0f400000` 窗口内；`0x0011xxxx` 是字体字形缓存。

**建议的替代路线**：闪电模式时间靠左面板 `+0:00` 的**时间奖励池**续命 ⇒ 改池子为大值即等效无限时间。池子**不随时间流逝、只在消除时变化**，比计时器好找。

## 五、性能剖析（抉择的核心依据）

### 5.1 单步耗时分解

| 环节 | 耗时 | 占比 |
|---|---|---|
| 抓帧（PipeWire） | 11.07 ms | 0.6% |
| 视觉识别棋盘 | 50.85 ms | 2.6% |
| 求解 | 2 ms | 0.1% |
| 输入（uinput 拖动） | 11 ms | 0.6% |
| **游戏消除动画 + 结算等待** | **~1900 ms** | **96.7%** |
| **合计** | **~1975 ms** | 100% |

### 5.2 关键结论

> **视觉识别只占 2.6%。即使把识别优化到 0 ms，单步也只从 1975 ms 降到 1924 ms（快 2.6%）——用户感知不到。**

**真瓶颈是游戏自身的消除动画**，且这是**不可压缩**的：

| 实验 | 结果 |
|---|---|
| A 不干预 | ≈1.25 s |
| B 点击棋盘 | ≈1.25 s |
| C 点击空白 | ≈1.25 s |

⇒ **点击无法加速结算**。`compat.cfg` 中也没有动画/速度相关选项。

### 5.3 已被证伪的加速思路

| 思路 | 为什么无效 |
|---|---|
| 写 D3D9 注入 DLL | 抓帧/输入已经不是瓶颈（PipeWire 已够快） |
| 提高抓帧帧率 | 90.7 fps 已远超需要 |
| 优化视觉识别 | 只占 2.6% |
| 排队连发（不等结算） | 实测 `--gap 0.22` 的 1.77 步/秒是**假速度**：动作在两交换间交替，约一半被丢弃 |
| 点击加速动画 | 三种干预方式实测全部无效 |
| **时间 API 加速（SpeedHack）** | ❌ 已证伪：A/B 零差异（9.877s vs 9.877s）+ 两次卡死 |
| **hook `Sleep` 缩短等待** | ❌ 已证伪：直接卡死 |

⚠️ **边界说明**：上表证伪的是**时间 API 加速路径**；
**"游戏内部存在可修改的动画变量/状态机"这一路径尚未被证伪**（本轮未触及）。

## 六、踩坑与教训（可复用于其他 Steam Deck 逆向项目）

### ★★★ 6.1 四条通用方法论

1. **进程名对不上 = 修改器/注入器失效的常见根因**。先比对"目标进程名 vs 实际运行进程名"，别急着逆向。
2. **Cheat Engine 两步法的铁律**：过滤必须筛"**精确等于新读数**"，不能筛"值变了且为正"——我犯过这个错，把独立计数器误判为分数。
3. **写入验证必须看画面**。只看内存会**假阳性** —— 写入未被使用的地址也会"保持不变"（11 个计时器候选全栽在这）。
4. **分类判据 > 差异判据**。差异判据（画面变没变）会被动画污染；**分类判据**（写 0 vs 写大值，UI 是否相应变化）无法伪造 —— "立即完成等级"就是这么确认的。

### 6.2 具体技术坑

| # | 坑 | 解法 |
|---|---|---|
| 1 | `gamescopectl` 写 `/tmp` 静默失败（exit 0 无文件） | gamescope 有独立 mount namespace，**写到 `/home/deck/`** |
| 2 | 抓帧得到半截 PNG | `Image.open().verify()` + 重试 |
| 3 | `fdsink` 短读 → reshape 报错 | **累积满帧再 reshape** |
| 4 | `sudo` 后读不到棋盘 | **不要 sudo**（会清空 `XDG_RUNTIME_DIR`） |
| 5 | `pkill -f "gst-launch..."` 在 SSH 里**自杀** | 用脚本文件，或 `gst-launc[h]` 规避 |
| 6 | "两帧识别相同" ≠ 棋盘静止 | 连消+道具自播动画造成假静止 → 改**像素级帧间差 <2.0 连续 4 帧**（实测静止 p90=0.44 vs 动画 p90=10.73） |
| 7 | 火焰宝石的火焰在**外圈** | 边缘环/整格投票都读成白 → 改**高饱和像素投票**（P=0.80） |
| 8 | 无效交换会被游戏弹回 | 只用**求解器算出的有效交换**验证输入 |
| 9 | `is_board_like` 会把结算页误判成棋盘 | 加**颜色多样性**判据（≥4 种色相） |
| 10 | gamescope 下 `xdotool getmouselocation` 不可靠 | 用**游戏内实际反应**验证输入，别信指针位置 |

### 6.3 ⚠️ 一次假警报的教训

我一度根据"`xdotool getmouselocation` 指针不动"判定 **uinput 已失效**，并据此得出"找不到输入通路"的结论。

**实际是错的**：用"游戏内棋盘是否变化"重新验证 → **uinput 完全可用**。

⇒ **教训**：在 gamescope/Wayland 环境下，**X11 的指针位置查询不可信**；判定输入是否生效，必须用**应用层的实际反应**。

## 七、抉择：三条路线的成本收益

### 路线 A：接受现状，优化别处
**做什么**：保持视觉读棋盘，把 bot 的分数监控改成内存直读（省 50 ms/次）。
**预期收益**：单步 1975 ms → 1924 ms（**快 2.6%，感知不到**）。
**成本**：1~2 小时。
**评价**：❌ 收益太小。

### 路线 B：深挖指针链，实现内存读棋盘
**做什么**：跟根指针 → 容器 → 棋盘对象图，定位 64 个宝石格的地址。
**预期收益**：
- 读棋盘 **0.007 ms**（比视觉快 7000 倍）
- 附加价值：能读宝石**动画状态**、可做**落子预测**（视觉做不到）
**成本**：**数小时级**，且**不保证成功**（对象图可能有多层间接、可能有动态重分配）。
**对速度的影响**：**几乎为零**（识别只占 2.6%）。
**评价**：⚠️ 只有当你需要"读动画状态/落子预测"时才值得。

### 路线 C：攻真正的瓶颈（游戏消除动画 1900 ms）

> ⚠️ **本路线已于 2026-09-24 实测，结论边界如下：**
> **基于时间 API 的动画加速不可行；动画变量/状态机逆向尚未被证伪。**
> 已证伪的是 `timeGetTime` / `Sleep` 等**时间 API 加速路径**，而**不是动画控制变量本身**。

**C-1 时间 API 加速（SpeedHack）** —— ❌ **已证伪**
A/B 实测：无加速 **9.877s** vs 2 倍加速 **9.877s**，**零差异**；且两次卡死。
根因：`timeGetTime` 实测 **1131 次/秒**（主循环轮询），而动画时长固定 —— 动画进度**不由实时 tick 驱动**。

**C-2 点击干预** —— ❌ 已证伪（3 种方式全部无效）；`compat.cfg` 无相关选项。

**C-3 动画变量 / 状态机逆向** —— 🟡 **尚未证伪，待验证（当前最有希望的路径）**
**做什么**：不先找时间、不先找棋盘，直接扫描"**只在动画期间变化**"的变量，
再反汇编 `.text` 找"**变量与常量比较 → 分支到 READY**"的模式定位完成条件。
**成本**：Phase 1~3 全程只读（零风险）；Phase 4 扰动验证需重启预案。
**预期收益**：若成功，单步可能从 1975 ms 降到 500 ms 级（**3~4 倍提速**）。
**评价**：✅ **收益最大且风险可控**（前三阶段零写操作）。
详见 `动画变量逆向可行性分析-20260924.md`。

### 路线 D：补完修改器剩余 7 项功能
**做什么**：金矿、扑克同花、红蓝平衡、冰块、无限时间/移动/炸弹。
**成本**：每项 0.5~2 小时（无限时间最难，闪电每局仅 1 分钟）。
**评价**：✅ 收益明确（功能可见），但**与 bot 速度无关**，属独立需求。

## 八、我的建议

**如果目标是"让 bot 更快"** → 选 **C**（攻动画瓶颈），但要接受高难度与注入风险；**A、B 都已用数据证明收益可忽略**。

**如果目标是"修改器功能更全"** → 选 **D**，从**金矿**开始（它和分数同属"累积数值"，我已掌握成熟方法）。

**如果目标是"降低技术风险、稳定可用"** → 维持现状（bot + 2 项修改功能都已实测可用）。
