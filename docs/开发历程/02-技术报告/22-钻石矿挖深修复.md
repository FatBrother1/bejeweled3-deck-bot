日期：2026-09-26 01:10
设备：Steam Deck，Bejeweled 3，钻石矿模式

## 一、现场（00:56 抓的图）

- 金币 **$327,000**、本局剩余 **0:42**
- bot 日志：`00:54:44 死局现场 ...` → `00:55:20 死局(30)等洗牌/新局...` → `00:55:59 死局(60)...`

## 二、根因：拉黑掩码把真棋盘掩成了「假死局」

`bot_v6.py` 里有一条老机制：**同一格连续被拒 3 次，就把这格改写成 `'?'`**（拉黑）。
而 `'?'` 不只是"这格不能碰"——求解器里它**既不能参与连线，还会切断别人的连线**。

实测对照（同一时刻、同一盘面）：

| 给求解器的棋盘 | 候选数 | 结果 |
|---|---|---|
| bot 实际用的（含 4 个 `?` 掩码） | **0** | 判定"死局" → 就地待命，看着像"不工作了" |
| 真实棋盘（无掩码） | **2** | `(2,3)<->(3,3)`、`(3,3)<->(4,3)` |

被掩掉的 `(3,3)<->(4,3)` 本来靠第 2 列 `R,R,R` 成三连，正是被 `(2,3)=?` 切断的。

**为什么是"挖到一定深度"才犯**：钻石矿往下挖，泥土从底部往上占，可用的宝石区越来越小，
有效走法本来就少；这时只要有几格被拉黑，就足以把整盘掩成 0 候选。
越深越容易踩，浅的时候走法多、掩几个无所谓。

## 三、修复

`bot/bot_v6.py`：**0 候选且确实存在掩码时，用真实棋盘再算一次；算得出候选就说明是掩码造成的，
清空拉黑、按真实棋盘继续走**。pro（`solver_pro`）与 fast（`solver_fast`）两条求解路径都加了。

```
★ 拉黑掩码掩出了假死局 → 清空拉黑，按真实棋盘走（候选 N，掩码格 M）
```

## 四、验证：强制复现（端到端）

真实场景下阈值=3、掩码出现得慢，所以造了一份**测试副本**（把拉黑阈值从 3 降到 1，让掩码快速出现），
停掉守护后单独跑 70 秒：

| 指标 | 结果 |
|---|---|
| 假死局解禁触发 | **2 次**（01:04:13 候选 16 / 掩码 18 格；01:04:31 候选 2 / 掩码 10 格） |
| 死局现场（真死局） | **0 次** |
| 步数 | 49 步（33 ✓ / 16 ✗）正常出招 |

⇒ 走的就是这次改的代码路径，命中即解禁、再没出现"死局趴窝"。

之后恢复正式版（阈值 3）在跑：67 步 = 48 ✓ / 19 ✗、**死局现场 0**、最长连续同一招 2 次。
