## 二、⚠️ 对原方案的修正：全量快照采样率不成立

### 2.1 问题

原方案要求：

> 执行一次有效交换 → **每 10~20 ms 抓一次内存快照** → 比较

**实测数据不支持**：

| 项 | 实测值 |
|---|---|
| 全量快照（1.1 GB / 29 万页） | **0.76 秒** |
| 原方案要求 | 0.01~0.02 秒 |
| **差距** | **38~76 倍** |

**后果**：一次交换动画仅约 1.25 秒，按 0.76s/次只能抓到 **1~2 帧** —— 根本看不到 `0→1→2→3→4→0` 的过程。

**最危险之处**：失败会表现为"**找不到动画变量**"，而真实原因是"**采样率不足**"。
⇒ **必须把这两种失败区分开**，否则会得出错误结论。

### 2.2 修正方案：两阶段（全量建热点 → 热点增量轮询）

```
① 静止时全量快照 A                          0.76 s（只需一次）
② 自动执行一次有效交换
③ 动画结束后全量快照 B                      0.76 s（只需一次）
④ 差分 A/B → 得到变化页集合（实测 787~1059 页 ≈ 4 MB）
⑤ 之后【只轮询这约 4 MB 热点区】            ≈ 3 ms/次  ✅
   → 1.25 秒动画可抓到约 400 帧，足够看到完整变化序列
```

**依据**：走一步引起的内存变化实测为 **787~1059 页（约 4 MB）** —— 这是已验证的数据。

**关键收益**：把"不可行的 0.76s/次"变成"**可行的 3ms/次**"。

### 2.3 采样率自检（防止误判）

必须实现一条**自检逻辑**：

> 若某轮动画采样**帧数 < 20**，则判定为"**采样率不足**"，**不得得出"无动画变量"的结论**。
> 应降低热点区范围（更严格过滤）或降低采样深度后重试。

## 三、Phase 1：动画期间内存变化地图（纯只读）

### 3.1 流程

```
1. 启动游戏，进入棋盘
2. 等静止（像素级帧间差 < 2.0 连续 4 帧）★ 用已验证的硬标准
3. 全量快照 A（记录时间戳）
4. 自动执行一次有效交换（求解器给出的合法交换）
5. 以 ≈3ms 周期轮询热点区，每轮记录 (时间戳, 值)
6. 判定动画结束（同一硬标准）
7. 差分计算每个地址的统计特征
```

### 3.2 ⭐ 每个地址要计算的统计量

| 统计量 | 用途 |
|---|---|
| 首次变化时间 | 判断"何时参与" |
| 最后变化时间 | 判断"何时结束" |
| **变化次数** | 高频 vs 阶段切换 |
| 最大/最小值 | 值域 |
| **是否单调** | 计数器特征 |
| **是否周期** | 循环特征 |
| **离散值个数** | **状态枚举识别（关键）** |
| 变化发生在哪些动画阶段 | 阶段关联 |

### 3.3 ⭐⭐ 输出要求（按用户指示修正）

> **不只输出 Top 100 —— 必须保存完整候选集，同时另出 Top 100 报告。**

**理由**（用户提出，完全正确）：

```
完整差分结果
    ↓ 过滤明显噪声
    ↓ 分类
    ├── 高频变化
    ├── 单调变化
    ├── 阶段切换   ★
    └── 其他
    ↓
Top 100 只是展示结果
```

若 Phase 2 发现某个**被 Top 100 排掉的"低频状态枚举"**其实非常像状态机，
就**不必重跑昂贵的全量实验** —— 完整候选集已落盘。

**落盘格式建议**：
- `anim_full.jsonl` —— 完整候选集（每行一个地址的全部统计量）
- `anim_top100.md` —— 人类可读报告
- `anim_hotpages.bin` —— 热点页集合（供复现）

## 四、Phase 2：候选分类（纯只读）

| 类别 | 判据 | 优先级 |
|---|---|---|
| **阶段切换型** | 静止不变；动画期少量离散值跳变（如 0→1→2→3）；结束回 0/停 | ⭐⭐⭐ **最高** |
| **单调型** | 单调递增/递减，步长小 | ⭐⭐⭐ |
| **高频周期型** | 变化频繁且有周期性 | 🟡 中（可能是渲染噪声） |
| **噪声/缓存** | 高频无规律、值域乱 | 排除 |

### ⚠️ 两个必须注意的陷阱（已有实测教训）

**陷阱 1：渲染/字体缓存会被误判**
> 实测 `0x01098xxx` 那片是**字体字形缓存**，随动画高频变化但**不是游戏逻辑**。
> 必须加过滤：排除已知的渲染缓冲区与字形缓存区。

**陷阱 2：状态枚举型容易被"变化次数"判据漏掉**
> 若变量是**状态枚举**（0/1/2/3），它**每个阶段只变一次**，变化次数很低，
> 会被"只留高频"的过滤条件**直接排掉**。
> ⇒ **必须保留"少量离散值 + 低变化次数"这一类**（这正是用户强调的"阶段切换型"）。

## 五、Phase 3：反汇编反推"动画完成条件"（纯只读，**最高价值**）

### 5.1 为什么这条最值得做

> 不需要先找到棋盘对象，直接定位"**比较指令 + 常量**"，命中率远高于盲扫数据区。

### 5.2 技术基础（已具备，Route C 已验证）

| 能力 | 状态 |
|---|---|
| PE 结构解析（节表/导入表/IAT） | ✅ 已实现（`iat.py`） |
| 读代码段 | ✅ `process_vm_readv` |

### 5.3 具体做法

```
① 反汇编 .text 段
② 搜索"读变量 → 与常量比较 → 分支"的模式：
     mov  eax, [addr]
     cmp  eax, IMM
     jle / jge / jne ...
③ 候选常量：动画帧数（30/40/60）、毫秒数（1250）、或其他阈值
④ 提取 [addr] → 得到"动画控制变量"的地址
⑤ 交叉引用：在数据段找该地址的其他引用
⑥ 与 Phase 1 候选集【交叉验证】
```

### 5.4 与 Phase 1 的协同

> **Phase 3 给出"理论候选"，Phase 1 给出"实测候选"，
> 两者**交集**的置信度远高于任何单一路径。**

## 六、Phase 4：扰动验证（**唯一会写内存的阶段**）

### 6.1 严格的前置条件

> **仅对高置信候选执行**（Phase 1 与 Phase 3 交叉验证过的）。

### 6.2 扰动协议（按用户要求）

```
原值 → 记录并落盘
   ↓
+1（最小扰动）
   ↓
观察动画时长变化 + 验证进程存活
   ↓
+10% / -10%
   ↓
观察动画
   ↓
成功且安全，才考虑扩大幅度
```

### 6.3 ⚠️ 安全要求（Route C 的血的教训）

| 要求 | 理由 |
|---|---|
| **必须先保存原值** | 回滚依据 |
| **自动回滚 + 重启检查** | Route C 证明"内存恢复 ≠ 运行状态恢复" |
| **每次扰动后验证进程存活** | 及早发现异常 |
| **准备重启预案** | 卡死时只能靠重启恢复 |
| **禁止直接写 999999** | 会破坏状态机 |
