## 一、结论：方案 A 成立，但要换掉抓帧通路

设计文档里的方案 A（外置视觉闭环）方向是对的，**但它的关键实测数据有一条是错的**，本次重测纠正：

| 能力 | 设计文档写的 | 本次实测 | 说明 |
|---|---|---|---|
| `gamescopectl screenshot` | 0.35 s/帧 | **0.45 s/帧（2.2 fps）** | 这是 PNG **编码**瓶颈，不是抓帧瓶颈 |
| ⭐ **PipeWire 通路** | 未发现 | **11 ms/帧（90 fps）** | gamescope 自带视频节点，**快 40 倍** |
| 输入注入 | 可行 | 可行 | 但"位置跟踪"方案不可靠，改用每步归零 |

**决定性发现**：gamescope 在 PipeWire 里暴露了一个名为 `gamescope` 的 `Video/Source` 节点，
`gst-launch-1.0 pipewiresrc path=93 ! videoconvert ! video/x-raw,format=RGB ! fdsink fd=1`
可以拿到 **90 fps 的原始 RGB 帧**（1280×800×3 字节）。

→ **原本要写 DLL 注入才能达到的速度，用现成的 PipeWire 通路就够了，零注入。**
（这也是你要求的"注入模式"的替代：不需要交叉编译器、不需要改游戏目录、不需要 DXVK 定制。）

| `ncvc/Bejeweled-3`（Python 2） | autopy + bmp 模板匹配；AI 用 `depth=2` 递归前瞻 | ❌ 前瞻慢（其 README 自承"看一步要 5 秒"）；模板匹配依赖固定窗口大小 |
| `DillonThyer/BejewledBot` | ⭐ **Steam 版 Bejeweled 3、专打闪电模式、以速度为纲** | ✅ **最有价值**：证实"外置视觉 + 连发排队"能打到 200–500 万分 |
| `TomWildenhain/blaster-bot`（36★） | C#，内存读取 | 参考（Windows 进程内存路线，Linux/Proton 下不可直接照搬） |

**从 DillonThyer 学到并采纳的一点**：他设 `SLEEP_TIME=0.02`、`MAX=10` 步**排队连发**，
不等动画结算。这是"爽感"的来源。本项目据此加了 `--turbo` 模式（见 §五）。
另外他的 README 里已经写明我们要踩的坑：

> *"Flashy animations limit accuracy of color recognition, could change/improve the color recognition method."*

本项目的识别方法（逐像素投票 + 饱和优先 + 像素级稳定性判据）正是针对这条的改进。

## 三、速度账：钱花在哪一目了然

| 环节 | 旧方案 | 现在 | 说明 |
|---|---|---|---|
| 抓帧 | 450 ms（gamescopectl） | **11 ms**（PipeWire） | 40× |
| 识别 | 99 ms（PIL） | **~10 ms**（numpy） | 10× |
| 求解 | 2 ms | 2 ms | 本来就快 |
| 鼠标动作 | 950 ms（每步归零 + 死等） | **~200 ms** | 参数优化 |
| 每步总耗时 | ~3–5 秒（0.2~0.3 步/秒） | **~1.2 秒（0.8 步/秒）** | **约 3 倍** |

**为什么不是 40 倍**：剩下的大头是**游戏本身的消除动画**（约 0.8–1.2 秒）。
外置方案必须等动画结束才能看清新棋盘 —— 这是方案 A 的**架构天花板**，
不是调参能突破的。要突破只有两条路：
- `--turbo` 连发（不等动画，实测可到 0.95 步/秒且基本正确，见 §五）
- 内存读取（需逆向，跨 Proton 复杂度高）

## 四、实测数据（全部现场测得，非推测）

### 4.1 抓帧通路

| 通路 | 帧率 | 备注 |
|---|---|---|
| `gamescopectl screenshot` | 2.2 fps | 只支持 PNG；换 BMP/JPG/RAW 全部不支持；连拍同速 |
| **PipeWire `pipewiresrc path=93`** | **90.7 fps** | 原始 RGB，3072000 字节/帧 |
| `/dev/shm` 落盘 vs `/home` | 同样 0.44 s | 说明瓶颈在编码不在磁盘 |

### 4.2 输入注入

`/dev/uinput` 对 `deck` 用户有 `rw` ACL（免 root），`python-evdev 1.9.0` 已装。

对照实验（**只用求解器算出的有效交换**，避免"无效交换被游戏拒绝"造成的假失败）：

| 方式 | 生效 | 说明 |
|---|---|---|
| 拖动（down 后立刻 move） | **4/4** | ✅ 采用 |
| 拖动（down 后等 0.2/0.35 s） | 2/4 | ❌ 等待反而变差 |
| 点击-点击 | 4/4 | 可行，但比拖动慢 |
| ~~位置跟踪（不每步归零）~~ | **不可靠** | ❌ 实测多次静默失效，已弃用 |

**结论**：用**每步撞角归零**的确定性定位（代价仅 0.02 s），不要跟踪光标位置。

### 4.3 标定（`board.json`）

```
x0=476.0  y0=79.0  pitch_x=89.17  pitch_y=88.17   棋盘覆盖率 0.912
列心 x: 476  565  654  744  833  922  1011 1100
行心 y:  79  167  255  343  431  519  608  696
```
已用"把网格画回实况帧"的方式目视核验：**每个格心都落在宝石正中**。

### 4.4 识别正确率

逐像素投票 + 饱和优先，在两张人工逐格核对过的棋盘上：

| 棋盘 | 结果 |
|---|---|
| 干净棋盘（`s_classic`） | **8×8 逐格零误差**，置信度 0.71–1.00 |
| 含道具棋盘（火焰宝石 + 超立方体） | `'?'` 格 = 0，**紫色火焰宝石正确读成 P** ✅ |

菜单/加载画面：`'?'` 格 45+，与棋盘（0–3）**完全分离**，据此做画面状态判定。

## 五、踩过的坑（都是实测撞出来的，重要）

### 坑 1：`gamescopectl` 不能写 `/tmp` ✅已解
gamescope 在独立 mount namespace 里，`/tmp` 是另一个。写 `/home/deck/` 可以。

### 坑 2：抓帧读到半截 PNG ✅已解
`gamescopectl` 异步写文件，直接 sleep 会读到损坏 PNG。**必须 `Image.verify()` 校验**。

### 坑 3：uinput 短读 ✅已解
`fdsink` 的 `read()` 会短读，必须累积满一帧再 reshape，否则 `ValueError`。

### 坑 4：⭐"画面两帧相同"不是棋盘静止的判据 ✅已解
Bejeweled 有**连消**和**道具自播动画**，识别结果可能碰巧相同，而 bot 抢在动画中出手
→ 交换被动画吃掉、棋盘回归原状 → 表现为**反复算同一招、分数不涨**。
实测数据：

| 状态 | 帧间平均像素差 中位 | p90 |
|---|---|---|
| 静止 | 0.15 | **0.44** |
| 动画中 | 2.52 | **10.73** |

→ **用像素级帧间差判"动没动"**（阈值 2.0、连续 4 帧），这是唯一可靠的判据。

### 坑 5：火焰宝石的火焰在**外圈** ✅已解
紫色火焰宝石的火焰白光裹在**边缘**、本体紫在**中心** —— 用"边缘环投票"或"整格投票"
都会被白光带偏读成白宝石，进而**凭空造出"四连白"**，bot 以为棋盘没结算而死等。
→ 改用**高饱和像素投票**：得到 P(0.80) ✅。

### 坑 6：金色超立方体会被读成白宝石 ⚠️已知，已用机制兜住
它是道具（金色方块），实测高饱和中位色 (229,212,118)、饱和度仅 0.48。
试过 4 种颜色判据（dark / glow / mid 占比 / 独立参考色）—— **全都会误伤真宝石**
（白骷髅有眼窝阴影又高光多，最容易误伤）。
**最终决定**：不为它改颜色规则（代价 > 收益），改用**机制兜底**：
如果同一交换连续 3 次都没改变棋盘，就把这两格拉黑，bot 自然会换别的走法。

### 坑 7：无效交换会被游戏拒绝 ✅已懂
Bejeweled 对"换完不能消"的交换会**弹回原位**。所以验证输入是否生效，
**必须只用求解器算出的有效交换**，否则会把"游戏正常拒绝"误判成"输入失效"。

### 坑 8：`pkill -f` 会自杀 ✅已解
SSH 命令行里含 `bot.py` 字样时，`pkill -f "bot.py"` 会把 SSH 自己杀掉（exit 255）。
→ 写成脚本文件执行，或用 `bo[t].py` 这类正则规避。

### 6.2 控制台用法

```bash
bash /home/deck/run2.sh on        # ⭐ 打开按需守护（游戏一起就起 bot，退出就停）
bash /home/deck/run2.sh status    # 看守护/bot/游戏状态
bash /home/deck/run2.sh logs 40   # 看日志
bash /home/deck/run2.sh play 50   # 手动跑 50 步
bash /home/deck/run2.sh turbo     # 连发模式（快，但准确率下降）
bash /home/deck/run2.sh off       # 全部停止
```

### 6.3 实测性能

| 模式 | 步频 | 准确率 | 建议 |
|---|---|---|---|
| 正常（等动画结算） | **0.8 步/秒** | 高（几乎全 ✓） | ⭐ 默认，稳 |
| `--turbo --gap 0.45` | 0.95 步/秒 | 中（大消除时会重复几手） | 想快一点用这个 |
| `--turbo --gap 0.22` | 1.77 步/秒 | ❌ 动作在两个之间交替，一半被丢弃 | **不建议**（假速度） |

`gap=0.22` 实测是"快过游戏受理速度"的典型症状：日志会在两个交换之间来回交替。
**真正的上限受游戏动画与受理速度约束，不是我们能单方面加快的。**

## 七、关于"倒计时模式（闪电）"

你问的这个是**真问题**，实测结论如下：

- 闪电模式给每步的时限约 2–3 秒（比经典模式紧得多）。
- 正常模式 **0.8 步/秒 ≈ 1.2 秒/步**，**在时限内，能跟上**，但余量不大。
- `--turbo --gap 0.45` 到 **0.95 步/秒 ≈ 1.05 秒/步**，余量更舒服。
- ❌ 但**如果卡在"等动画 + 消大链"的长局面上，会掉到 1.5–2 秒/步**，有超时风险。

**建议**：闪电模式用 `--turbo --gap 0.45`，并把 `--max-fail` 调低（卡住就快速退出重来）。
想彻底稳，只能走内存读取路线（§八）。

## 八、若要进一步提速（未做，供决定）

| 路线 | 预期 | 代价 |
|---|---|---|
| **内存读取棋盘** | 0.1 秒级决策，可达 5–10 步/秒 | 需逆向定位棋盘结构（Proton/Wine 下跨层读内存），无现成资料，风险高 |
| DLL 注入（DXVK 定制） | 60fps + 进程内识别 | 需装 `i686-w64-mingw32-gcc`，改 `d3d9.dll`（GE-Proton 自带 DXVK 的 i386 版有源码可对照）；但**风险：游戏更新或换 Proton 版本即失效**，且要改游戏目录 |
| 直接读 DRM framebuffer | 可能比 PipeWire 更快 | `/dev/dri/renderD128` 权限已通，但要从 compositor 的缓冲里挑出游戏层，复杂 |

**本次结论**：PipeWire 已经把外置方案的速度推到架构上限，进一步提速的投入产出比很低。
按你的实际体验决定是否值得。
