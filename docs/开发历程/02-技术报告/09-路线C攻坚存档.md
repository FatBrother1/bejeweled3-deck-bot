## 三、两次卡死事故的完整分析

### 3.1 第一次事故：只 hook 单个函数 + 8 倍激进倍数

- **做法**：只 hook `Sleep`，把参数除以 8
- **结果**：画面卡死；回滚 IAT **仍不恢复**；线程卡在 `hrtimer_nanosleep`
- **处理**：结束进程重启 → 恢复

### 3.2 第二次事故：BASE 基准错误（我的实现 bug）

```python
BASE = int(time.time()*1000) & 0xFFFF0000   # ❌ 用了 Linux 系统时间
# 得到 0xD2520000 (3,528,589,312)
# 而游戏 tick 只有 13,729,158 → real - BASE 回绕 257 倍！
```

- **后果**：时间值变成天文数字 → **状态机/加载超时逻辑崩溃**
- **现象**：主菜单正常（12 秒无异常），但**进入棋盘时卡死**
- **修正**：改用**游戏自己的 tick** 作 BASE（`0x00D1F000`，`real-BASE` 仅 2225ms）
- **修正后**：✅ **成功进入棋盘，状态机完全正常**（这是重要的正面证据）

### 3.3 ★ 第三次失败：A/B 实测零效果

**修正基准后游戏运行完全正常**，但测速结果：

| 条件 | 单步耗时（4 次取样） |
|---|---|
| 无加速 | 9.902 / 9.869 / 9.870 / 9.883 → 中位 **9.877s** |
| 2 倍加速 | 9.891 / 9.874 / 9.879 / 9.867 → 中位 **9.877s** |
| **变化** | **-0.0%（加速比 1.00x）** |

⚠️ **注意**：单步 **9.877 秒** —— 这比之前测的 1.98 秒**慢了 5 倍**！说明测量本身可能已被污染（游戏可能又处于异常状态，用户也报告"又卡死了"）。

## 四、路线 C 为什么失败（根因分析）

### 4.1 最可能的根本原因

**`timeGetTime` 不是动画时长的驱动者。** 从频率特征看：

- `timeGetTime` **1131 次/秒** —— 这是**主循环轮询节奏**，不是"动画进度计算"
- `Sleep` **99 次/秒** —— 主循环节流

**动画很可能是"帧计数驱动"或"固定时长常量 + Sleep 计数"，而非"实时时间差"驱动。**

⇒ 所以加速 `timeGetTime` 的返回值，对动画进度**没有影响**。

### 4.2 另一个关键疑点

单步耗时从 **1.98s → 9.877s**（慢 5 倍），且用户报告卡死。这暗示：
- 要么 `timeGetTime` 被加速后，**某些等待逻辑变长**了（超时时间被放大）
- 要么游戏在加速后进入了**异常但未完全死锁**的状态

**无论哪种，都说明时间加速对本游戏是"有害无益"。**

## 七、路线 C 的最终评估

**结论：路线 C 在此架构下不可行。**

| 维度 | 评估 |
|---|---|
| 时间 API 加速（SpeedHack） | ❌ **不可行（已证伪）** | A/B 实测零差异 + 两次卡死 |
| hook `Sleep` 缩短等待 | ❌ **不可行（已证伪）** | 直接卡死 |
| IAT hook 技术通路 | ✅ **完全可行**（已打通） | 可写只读页 + rwxp 代码洞 + IAT 重定向全部验证通过 |
| **动画变量 / 状态机逆向** | 🟡 **尚未证伪，待验证** | 本轮未触及此路径 |

**为什么"时间 API 加速"不可行**：
> `timeGetTime` 实测 **1131 次/秒**（主循环轮询），而动画时长是**固定的 1.25 秒**
> ⇒ 说明**动画进度不由实时 tick 驱动**，因此加速时间返回值天然无效。

**下一步方向**（见 `动画变量逆向可行性分析-20260924.md`）：
> **零修改动态追踪 → 找动画状态变化 → 再找时长/帧阈值**
> 不先找时间、不先找棋盘，而是直接扫描"只在动画期间变化"的变量，
> 再用反汇编找"变量与常量比较 → 分支到 READY"的模式定位完成条件。

## 八、本轮新增的方法论（有长期价值）

### ★ 零风险函数调用统计法

> **只加计数器（`inc dword[cnt]` + `jmp 原函数`），行为完全不变，即可精确测出每个 API 的调用频率。**

比"hook 改造"安全得多，且能直接判断"谁在驱动"。

### ★ 隔离验证法

> 用 gcc 写**等价的 C 代码**验证机器码的数学逻辑（我验证了"进度差放大 S 倍 = 数学等价"），在**不碰真游戏**的前提下排除数学错误。

### ★ hook 前必须查"调用频率"

> 如果我在 hook 之前就做了频率统计，会发现 `timeGetTime` 是 1131 次/秒的**主循环轮询**，而不是动画计算源——就能**避免这两次卡死**。

### 其他教训

1. **"重启游戏"命令可能只启动 Steam 库页** —— 必须 `pgrep Bejeweled3.exe` 验证
2. **回滚内存 ≠ 恢复运行** —— 被破坏的时序只能靠重启
3. **首次试验必须用最小倍数**（我用 8 倍太激进）
4. **hook 系统调用（`Sleep`）风险远高于 hook 纯查询函数**
