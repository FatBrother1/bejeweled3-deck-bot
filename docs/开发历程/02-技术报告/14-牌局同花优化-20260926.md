# 牌局模式「优先拿同花」优化 —— 技术报告

日期：2026-09-26
对象：Bejeweled 3 bot（Deck `deck@192.168.3.11`），牌局（Poker）模式
上游：`牌局模式说明.md`（2026-09-24 首次跑通）、`蝴蝶模式优先消蝴蝶-技术报告-20260926.md`
状态：**三个阻塞 bug 已修 + 求解器已改 + 牌局几何已标定**；干净环境下实测分/秒 57.8 → 696.4

## 〇、先说结论：原来的策略建立在一个错误假设上

`牌局模式说明.md` 的「已知限制」里写着：

> 不考虑手牌花色的分布。现在是"手牌里最多的那个花色"当目标；
> 如果手牌是 `R R Y Y ?`，其实追 R 或 Y 都只差一张，当前实现只选 R。

**这句话本身是错的**，因为它假设 `?` 是「暗牌」。同步抓帧实测证明 `?` 是
**还没拿到的空位**，手牌从左往右填：

```
G???? → GG??? → GR??? → GRR?? → GRG?? → GRGG? → GRGOR → GRGOO（结算）
????? → （新一手，重新从左边填）
```

已翻开的永远是一段**前缀**。于是：**同花要 5 张同色 ⇒ 已翻开里一出现第二种
颜色，这手同花就已经死了**。而旧代码 `GRGO?` 还在追 G —— 追一个数学上已经
不可能的目标。

## 一、三个阻塞 bug（都不是本轮引入的）

### Bug A —— 牌局模式一进去就崩

```
UnboundLocalError: cannot access local variable 'tgset'
```

`tgset` 只在**普通模式分支**里赋值（闪电修复 `de8149a` 引入），牌局分支从不赋值。
后果：牌局模式**第一步被拒就 traceback 退出**。实测 1 步即崩。

修法（最小）：在分支链之前给一个每轮默认值 `tgset = set()`，普通分支照旧覆盖。

### Bug B —— 每一步真有效的交换都被判「被拒」（本轮最大的一个）

```python
if nd > 0:                                   # 钻石矿
    effective = bool(changed and swapped)
else:                                        # ← 牌局走到这里
    effective = (real is not None and real != 0)
```

**牌局里消除宝石不给分** —— 分数只在凑成牌型时结算。用「分数变了没有」判有效性
⇒ 每一步有效交换都是 `实际=0` ⇒ 全判被拒 ⇒ 拉黑 ⇒ 掩码棋盘 ⇒ 每 12 步停手 20 秒。

这和钻石矿是**同一类问题**（`nd > 0` 那条分支就是为它加的），牌局从没享受同等待遇。

实测症状：0.36 步/秒、手牌 20 秒不涨、日志满屏 `✗拉黑`、44 次「无走法」。
而手牌其实在长（`G???? → GG??? → GR???` 就是这么来的）。

修法：`if nd > 0 or a.mode == "poker":` 走棋盘判据。

### Bug C —— 牌局模式用错了像素几何

牌局棋盘和钻石矿/蝴蝶同属「现代版式」（格距 **85.25**），但原点又不同。
bot 一直用经典几何（89.17/88.17、y0=79）。

用「内存真棋盘当基准反查画面」标定：

| 几何 | x0 | y0 | px | py | 采样命中 | 总色距 |
|---|---|---|---|---|---|---|
| 经典（旧，一直用的） | 476.0 | 79.0 | 89.17 | 88.17 | 44/64 | 5513 |
| 钻石矿 | 469.0 | 133.1 | 85.25 | 84.50 | 22/64 | 12444 |
| 蝴蝶 | 491.6 | 137.0 | 85.32 | 84.84 | 35/64 | 9988 |
| **牌局（新标定）** | **482.5** | **113.0** | **85.25** | **85.25** | **64/64** | **1725** |

31% 的格子采样错位 ⇒ 规划出的走法落到别的格子上 ⇒ 被游戏拒。
新几何色距比经典好 **3.2 倍**。落地：新增 `board_poker.json` + `bot_v6` 几何分支。

## 二、求解器优化（本次的「正题」）

### 1. `poker.flush_state(hand)` —— 同花还活着没有

```python
已翻开全同色  → (True, 该色, 还差几张)
已翻开混色    → (False, None, 0)      ← 这手同花已经死了
一张没翻开    → (True, None, 5)
```

### 2. 目标色决策重写（两遍扫描）

以前是「谁多追谁」，现在：

| 情形 | 目标色 |
|---|---|
| 同花还活着 | 锁定该色（还差 k 张） |
| 同花已死 | 改冲四条/葫芦 —— 选已翻开里最多的色 |
| 手牌全空 | **按「有多少步能把它做成严格多数色」选**，不再按盘面宝石数选 |

第三条是空手时的关键：盘面宝石多 ≠ 能凑出多数消除。

### 3. ★严格多数 vs 并列多数

实测出牌规则是「一次消除给一张牌，花色 = 多数色」，但**并列多数游戏给哪色未知**
（消 1G+1R）。旧代码把并列和严格同等对待（都是 `t_dom=1` → +2000）。
现在分开：严格多数 2600 分、并列多数 1800 分 ⇒ **必定拿到目标色的那步排前面**。

### 4. 日志带上同花状态

`手牌 OOOO?  目标色=O  牌型=四条  消目标色=0  [同花活·还差1]`
——以前只看得到目标色，看不出这手同花其实早就死了。

## 四、发现但**未修**的问题

### 牌局「手牌结算覆盖层」bot 不认识

手牌打出去以后，游戏在棋盘中央弹一层结果（5 张牌 + 「两对」+「+7,500」），
**挡住输入**，所有交换被拒。`screen_is_gameover` 用的是「橙色面板占比」，
这层覆盖层判不出来。

实测：bot 会在这层上趴窝 ~80 秒（21 步全被拒、30 次「无走法」），
最后靠乱点把它点掉才继续。**要彻底解决需要专门识别这层 + 主动点掉。**

### 环境坑（重要）

`bejewel-watch` 守护会**自动拉起 bot**（`--mode auto`）。本轮前半段的 A/B
全部被它污染（两个 bot 抢同一个鼠标）。**做任何单 bot 测量前必须先
`systemctl --user stop bejewel-watch`**。
