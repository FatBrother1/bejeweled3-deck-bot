## 二、报告漏掉的仓库

报告自己在 §12.3 里写明："未做 GitHub Code Search（需 GITHUB_TOKEN，未配置）"。

我这边有 token，补做了。第一条查询就命中了：

```
查询 Bejeweled3 ReadProcessMemory
命中 Ykzl/Bejeweled-3-Helper :: winMemUtils.py   全 GitHub 仅此一条
```

`Ykzl/Bejeweled-3-Helper` 是个 Python 写的 Bejeweled 3 辅助工具，
README 里写着"仅在 Steam 版本的 Bejeweled 3 上经过测试"。

它直接给出了 Steam 版的完整布局：

| 项 | Steam 版 | Plus 版（报告用的） |
|---|---|---|
| gApp 槽 | `0x008E1730` | `0x8A67AC` |
| Board | `[0x8E1730 + 0xBE8]` | `[gApp + 0xBE0]` |
| Piece 数组 | `[Board + 0xF8 + 4*x + 32*y]` | 调函数取 |
| Piece 颜色 | `[piece + 0x220]` | `[piece + 0x220]` 相同 |
| Piece 状态 | `[piece + 0x228]` | `[piece + 0x228]` 相同 |
| Piece 原色 | `[piece + 0x21C]` | 未提 |
| 分数 | `[Board + 0xD24]` | `[Board + 0xD28]` |
| 关卡 | `[Board + 0xE04]` | `[Board + 0xE0C]` |
| 棋盘宝石数 | `[0x8E170C + 0xB80 + 0xD0 + i*4]` | `[Board + 0x250]` |

这条推翻了报告的核心结论。

报告说 Steam 版偏移不可套用（§8），实际情况是 Piece 的颜色和状态偏移完全一致，
Board 层只差 4 个字节，颜色枚举 `-1..6`（红=0）也完全一致。

源码里的用法长这样：

```python
def readGem(x, y):
    gem = {
        "address": read4Bytes(0x008E1730, [0xBE8, 0xF8 + 4*x + 32*y]),
        "color":   read4Bytes(0x008E1730, [0xBE8, 0xF8 + 4*x + 32*y, 0x220]),
        "special": read4Bytes(0x008E1730, [0xBE8, 0xF8 + 4*x + 32*y, 0x228]),
    }
```

看 `0xF8 + 4*x + 32*y`，这是个指针数组，索引是 `4x+32y`，
也就是每行 32 字节等于 8 个 4 字节指针。

棋盘不是 64 个连续值，但是 64 个连续指针。这个形状报告其实扫到过
（§7.4 实验 7："64 连续指针窗口 12,034,220 个"），只是当时没有正确的颜色
偏移去做验证。

## 三、报告 §8 有个算术对不上

报告写：

> 读 `0x008A67AC`，= 0（该地址落在只读段 `02610000-09dd9000 r-xs`）

这句本身对不上：

```
0x008A67AC = 9,070,508
0x02610000 = 39,911,424
```

`0x8A67AC` 比 `0x02610000` 低 3084 万字节，不可能在那个段里。

报告列出的可用段只有三个：

```
0x00400000-0x00401000   头
0x008BD000-0x008D6000   数据
0x02610000-0x09DD9000   只读大段
```

`0x008A67AC` 落在 `0x401000-0x8BD000` 这 4.8 MB 里，报告漏列了代码段。

这也解释了为什么它读到 0，那个位置本来就不是 gApp。

## 四、真正的问题：扫错了范围

报告 §8 的做法是遍历 exe 数据段 `0x8BD000-0x8D6000`（102,400 字节）的
每个 4 字节指针，检查 `*(v+0xBE0)`、`*(board+0xD28)` 是否合法，
得到 1754 个候选全部失败。

真实的 gApp 槽在 `0x008E1730`，比它扫的上界高 46,896 字节。

```
报告扫描   0x008BD000 - 0x008D6000
真实答案   0x008E1730   ← 在窗口之外
```

那 1754 个候选失败是必然的，答案根本不在那个窗口里。

用 exe 文件大小独立验算：

```
文件大小 5,484,400 = 0x53AF70
映像基址 0x400000
VA 上限 = 0x400000 + 0x53AF70 = 0x93AF70
0x8E1730 < 0x93AF70，余量 366,656 字节
```

所以 `0x8E1730` 完全落在映像范围内。报告说的"数据段只到 0x8D6000"
大概只是描述了某一次进程里某一个段，不代表整个映像。

## 五、对 bot 的价值

### 能做的优化

**用内存读棋盘替掉视觉识别。** 现在识别要 77 毫秒一步，走内存是 64 次
`process_vm_readv`，按实测 1463 MB/s 的带宽算，毫秒级的事。

更要紧的是准确率。视觉路线现在有一堆麻烦：火焰宝石读成白色、
超立方体误判、标定依赖关卡背景（白天 0.912，夜间森林只有 0.568）。
内存路线没这些问题。

**用棋盘宝石数做静止判据的交叉验证。** 那个值在动画期间会变，静止时不变。
可以和我们现在的像素差判据互相印证。现在 250 毫秒的静止窗是纯靠试出来的，
有了内存判据也许能压得更短。

**精确读分数。** 现在评估 bot 表现要读游戏分数的绝对地址，游戏一重启就变。
用 `[0x8E1730+0xBE8+0xD24]` 这条固定链，重启也不变。

**读关卡和进度。** `[Board+0xE00]` 是进度，`[Board+0xE04]` 是关卡。
现在判断"是否进入新关卡"只能靠画面变化猜。

### 边界

只读，不写。那份源码里也有 `write4Bytes`，但那是作弊，不碰。

这是第三方给的布局，作者说只在 Steam 版测过，但那是 Windows 版
（用的 `wintypes` + `ReadProcessMemory`）。我这边是 Proton 下的 exe。
Proton 跑标准 PE，映像布局通常和 Windows 一致，但得实测。

汉化补丁应该没影响，核实过 `Bejeweled3.exe` 没被改动
（5,484,400 字节，2019-07-14），补丁只动了 `main.pak`。

### 验证步骤

Deck 现在离线（No route to host），等它回来：

```
第一步  读 0x008E1730，看是否非零且像个指针
        （期望值落在 0x00400000 以上的地址空间）

第二步  顺着链读 Board，看 [Board+0xD24] 是否等于画面上的分数
        这是最强判据，分数对得上就说明整条链是对的

第三步  读 64 个 Piece 的颜色，看是否覆盖 -1..6 且与画面棋盘一致
        这一步能同时验证指针数组偏移和颜色偏移

第四步  走一步，看颜色数组是否跟着变
```

第二步通过，后面就都是顺水推舟。
