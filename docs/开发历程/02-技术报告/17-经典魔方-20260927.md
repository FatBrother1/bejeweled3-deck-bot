# 经典模式「万变魔方」策略 —— 能造则造、造了就攒、真没招了才用

日期：2026-09-27　机器：Steam Deck deck@192.168.3.11　游戏：Bejeweled 3（Steam AppId 78000）

用户原话：「现在优化经典模式的消除逻辑，只要有万变魔方，游戏即使没有可消除的宝石也不会结束，消除魔方后会产生新的可消除三连宝石，现在你要优化脚本产生更多的万变魔方且不使用，要是没有可消除的三连宝石再使用万变魔方，争取打到高关卡，说明:万变魔方可以带入到下一关」

## 一、先说结论

| 用户要的 | 怎么做的 | 实测 |
|---|---|---|
| 产生更多的万变魔方 | 求解器加 `w_make_hyper`：这一步能凑成 5 连就加分，压过普通招 | 离线 1500 个随机盘：老解算器只有 **8.8%** 的步会去造魔方，现在是 **17.3%**（=「有 5 连招的盘」的全部） |
| 造出来不使用 | 求解器加 `save_hyper`：要动魔方的招扣 10 亿分，**但留在候选表里** | 上机：魔方在盘上活了 **68 秒**（改前实测 **2 秒**），还出现过**同时攒 2 个** |
| 没有可消的三连再用 | 扣分只是"排到最后"，一条普通招都没有时 `rk[0]` 就是魔方招 | 日志原话：`★ 盘上没有可消的三连了 → 动用万变魔方 (5,1)<->(6,1)`，预测 500 实际 3600 |
| 争取打到高关卡 | 上面三条合起来 | 一次新局（11:46:20 开）在 **13 分钟**内打到**第 11 关**、523,685 分 |

三处改动，只落在经典模式上：`solver_pro.py`（加两个默认关闭的参数）、`modes/classic.py`（声明策略 + 日志）、`modes/base.py`（加第 ①b 层兜底）。其它七个模式一个字节没变，离线逐项验过。

## 二、万变魔方在代码里长什么样

- 内存：`Piece+0x228` 的状态位 **== 2**，颜色 `Piece+0x220` 是 **-1**。`reader_mem._read_grid` 早就认它了（把这种宝石读成字形 `'S'`）。
- 求解器：`solver_pro.same()` 里 `'S'` **不参与普通连线** —— 它既不能当三连的一部分，也不能被别人连走。它唯一的用法是"跟邻居换一下"，然后引爆（`simulate` 里那段 `if "S" in (a0, b0)`：消掉目标颜色的**全部**宝石 + 自己）。
- 所以用户那句话在代码里是成立的：**只要盘上有一个 `'S'`，`rank_moves` 的候选表就永远非空**（魔方四邻都能换），bot 不会落进"0 候选 → 死局"。

这也是为什么"攒魔方"值得做：魔方既是保命牌，又**能带进下一关**（本轮实测抓到了这个现象，见 §5.4）。

## 三、改了哪三处

### 1. `solver_pro.rank_moves` 加两个参数（默认 = 老行为）

```python
def rank_moves(g, ..., w_make_hyper=0.0, save_hyper=False):
```

- `w_make_hyper`：这一步的首层连线里有几条长度 ≥ 5 的，每条加这么多分。
  5 连 = 一个万变魔方（`simulate` 返回的 `runs` 就是首层连线的长度表）。
  **拿魔方去引爆的招不算** —— 那种招 `simulate` 返回的 `runs` 是"被引爆的格数"，不是连线长度，所以代码里用 `uses_hyper` 排掉。
- `save_hyper`：这一步要动魔方（交换的两格里有一个是 `'S'`）就扣 `HYPER_USE_PENALTY = 1e9`。
  普通招的分数在几十~几千这个量级，扣 10 亿 = 钉死在候选表最后一名，**但它还在表里**，一条普通招都没有时它就是第一名。

两个参数的默认值分别是 `0.0` 和 `False`，也就是**不传就等于没改**。离线用 200 个随机盘逐项比对过（`test_hyper.py` A 组）：显式传默认值和不传，候选表的分数/分数预测/格子/级联/特殊数完全一致。这是可回滚、可 A/B 的前提，和之前蝴蝶/钻石矿那几轮的写法一致。

### 2. `modes/classic.py` 声明策略

```python
W_MAKE_HYPER = 3000.0   # 造一个魔方加多少分
SAVE_HYPER = True       # 有别的招就不动魔方
```

3000 这个数是这么定的：普通招的分数在几十~几千，3000 足以让"这一步能造魔方"压过绝大多数别的考虑，又不至于把明显更好的大级联也压掉（真要有个 5000 分的大级联，还是会选它）。

同时加了两条日志，好核对：
- 盘上魔方出现/消失/挪位时打一行（变化沿触发，不刷屏）：`◆ 盘上万变魔方 1 个: (4,2)  ← 攒着，没招了才用`
- 真的动用时打一行：`★ 盘上没有可消的三连了 → 动用万变魔方 (5,1)<->(6,1)`

### 3. `modes/base.py` 加第 ①b 层兜底（这条是必须的）

原来的选步链有两条兜底，都要求"候选表为空"才触发。**加了 `save_hyper` 之后，候选表永远不会空**（魔方招兜底）—— 于是掩码把普通招全掩光时，第①层永远不触发，bot 会把攒着的魔方当普通招用掉。

这不是理论风险：日志里 `掩码格 17`、`掩码格 18` 是常态（拉黑 3 次就掩一格，18 格足以把真棋盘掩成"只剩魔方招"）。

所以加了第 ①b 层：候选表**清一色是魔方招**且有掩码格时，拿真实棋盘重算一遍；真算出普通招就换成普通招，并清掉掩码。只对声明了 `SAVE_HYPER` 的模式生效，别的模式一行不变。

上机它救了好几次，原话：

```
11:55:06   ★ 掩码把普通招掩光了（只剩魔方招，掩码格 18）→ 用真实棋盘重算，先不动魔方（候选 6）
11:55:07   #309 (1, 4)<->(1, 5) 预测=50 实际=400 ✓      ← 走的是普通招，魔方留住了
11:55:07   ★ 盘上没有可消的三连了 → 动用万变魔方 (5, 1)<->(6, 1)
11:55:09   #310 (5, 1)<->(6, 1) 预测=500 实际=3600 ✓
```

11:51:31 和 11:59:17 也各触发过一次（掩码格 8 / 9）。

`test_hyper.py`（新增），在本机和 Deck 上各跑一遍，30/30：

```

C. 一盘同时有魔方招和普通招：默认解算器选魔方招（改动前的行为）、

F. 掩码把普通招掩光 → ①b 层用真实棋盘重算，仍然走普通招
G. 有 5 连招、但默认第一名不是它 → 加权重后第一名变成 5 连招

```

`test_modes.py` 40/40（D 组的参照系改成"带模式权重的求解器"，因为经典模式现在有意与老行为不同；其余 39 项一字未动）。

另外做了一次量化（本机，1500 个随机盘）：

```
存在能造魔方的招（5 连）      : 259 盘 (17.3%)
默认解算器真的会去造（=改动前）: 132 盘 ( 8.8%)

```

也就是说：**以前一半以上的造魔方机会被白白放过**（那些招的原始分不如别的招），现在一个不漏。

## 六、顺手发现、但**没动**的三件事

按"改必须点名"的规矩，这三条都只记录，不进代码：

1. **结算判据会在"过关过场动画"上命中。** 上一轮定的判据是区域 `f[150:450, 200:1080]` 里 `(R-B)>60` 的占比 > 0.75。本轮用一个逐帧探针（`gomon.py`）在真实对局里跑了 68,790 帧，正常对局最高只有 **0.458**，但过关那一下的**橙色旋涡过场**能到 **0.943~0.954**（帧存 `gomon_frames/go_36713_0.943.png`）。于是 bot 会把它当成局终，点一下 (640,738)、清掉拉黑。实测**无害**（游戏照常进下一关、分数不重置、关卡继续涨），只是日志里会多一条"已点「再来一次」"。要不要收紧判据请你说一声。
2. **`reader_mem.OFF_LEVEL = 0xE0C` 不是关卡。** 实测第 7 关时它读 1，重开新局从第 11 关掉到第 1 关时它一直读 7，跟画面完全对不上。`Board+0xEE4` 那阵子恰好等于 7，但新局后仍是 7，所以也不是它。这个字段目前只用在 `reader_mem` 自己的 `__main__` 打印里，不影响 bot 行为。真关卡号本轮是**看截图**读的。
3. **万变魔方被火焰/闪电炸到时，求解器当普通宝石处理。** `solver_pro.expand_specials` 的注释里写着"超立方(2) 被炸到时游戏里怎么算我没实测过 —— 保守当普通宝石，不展开"。新代码下抓到的 5 次魔方消失**全都**对应一次"动用万变魔方"日志，没抓到被炸掉的样本，所以没有依据去改，留着。
