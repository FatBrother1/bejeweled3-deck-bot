## 一、为什么做这个

报告 §7 记下了一条机制：**Bejeweled 3 丢了窗口焦点会静默暂停** —— 画面照旧渲染
（甚至还在动），但棋盘冻住、所有拖动被拒，恢复办法是点一下游戏窗口抢回焦点。

但这条机制**没有被写进代码**。`bot_v6.py` 里确实有一段「时钟冻结」检测，可它是
**专为钻石矿结算写的**：

```python
if cs_frozen >= 8 and nd > 0 and cs > 0 and marker_live():   # ← nd>0 = 必须有泥土
```

蝴蝶 / 经典 / 禅意模式 `nd == 0` ⇒ **这条分支永不触发**。于是暂停时无人处理，
bot 落进「棋盘冻住 → 求解器无解 → 死局循环 → 永远等不到洗牌」。

实测证据就是报告 §9.5 那条日志的现场：

```
08:55:04   死局(480)等洗牌/新局...
...
08:58:54   死局(660)等洗牌/新局...     ← 一路等到被外部杀掉
```

### 判据：为什么是「时钟冻结 ≥ 25 秒」

- **只能用游戏时钟 `Board+0x38`**。画面帧间差**不能**当判据 —— 暂停时仍有环境动画
  （本轮为此白跑十几轮、差点把假几何结论写进代码，见上游报告 §7）。
- **25 秒**：新局发牌 +「开始!」转场的冻结实测最多约 15 秒（续局那段代码自己就在等
  `18 × 0.8s`），留足余量，不会把正常转场误判成暂停。
- 另加 `cs > 0`（本局确实开始过）与 30 秒节流（失败后不连点）。
- 环境变量 `BJ_PAUSE_SECS` 可临时改阈值，仅供测试；部署默认 25。

### 恢复：两级降级

| 级别 | 动作 | 针对的暂停形态 |
|---|---|---|
| 1 | 点 `NEUTRAL_BTN (1200, 450)` | **失焦暂停**（无 UI，任意点击即可抢回焦点） |
| 2 | 点 `RESUME_BTN (882, 597)` | **局内「菜单」弹出的选项覆盖层**（模态，必须点「返回」） |

每级之后都**实测时钟是否恢复走动**（取两次采样、间隔 1.2 s 比较），成功才收工。
两级都失败 → 记日志、30 秒后再试。

`NEUTRAL_BTN` 的选点依据：棋盘横向约占 x 449~1131（蝴蝶几何 x0=491.6 / pitch_x=85.32，
8 列），1200 落在棋盘右侧装饰背景上；y=450 取中段，避开左下「菜单/撤回」与顶部蛛网装饰，
在结算/弹窗画面上也是无按钮的空白区。

## 三、离线验证：31 / 31 全绿

**方法（关键）**：不复制代码，而是用 AST 从 `bot_v6.py` 里**抠出真实的
`if cs is not None:` 整块**（102 行），塞进 `for _once in range(1):` 里执行
（`continue`/`break` 都能正常终止），配虚拟时钟 + 假鼠标 + 脚本化 `cs_now()`。
**测的就是将来真正上机跑的那段源码，不是重写的一份副本。**

```
1  冻结 3 秒（未到阈值）        → 不动手，cs_frozen 正常累加          ✓
2  冻结 30 秒 + 中性点击生效     → ⏸ → 点击 → ✓，状态全部复位         ✓
3  中性无效 → 「返回」生效       → 两次点击，降级成功                 ✓
4  两级都无效                   → 记失败 + 节流 30 秒               ✓
5  cs=None（读不到棋盘）        → 整块跳过，不崩                     ✓
6  节流期内                     → 不再动手                         ✓
7  回归：钻石矿冻结≥8 + 有泥     → 仍走结算续局，未走抢焦点           ✓
8  回归：钻石矿冻结 30 秒        → 仍只走结算分支，不误判成暂停        ✓
```

> 测试脚本第一版有 5 项失败，**全部是测试自己的 `cs_now()` 序列写错了**（多写了几个
> 500），代码无误 —— 记下来：这类失败先怀疑脚本，别急着改被测代码。

## 五、顺带破案：报告 §9.5「无声退出」

### 5.1 报的那次（08:58:54）—— 不是崩溃

| 证据 | 结论 |
|---|---|
| `earlyoom` 显示 mem avail 8.4 G，`dmesg` 无 OOM | **不是内存问题** |
| `journalctl --user -u bejewel-watch`：`08:59:29 Stopping ... Killing process 92450 (python3) with signal SIGKILL` | 是**被显式停止**的 |
| `run2.sh off` 的实现 = `systemctl --user stop bejewel-watch` + `pkill -f "python3 /home/deck/bo[t]_"` | 与现象完全吻合 |
| 日志停在 `08:58:54 死局(660)`，而该循环**每 30 轮（约 38 秒）才打一行** | 下一次本该 08:59:32 打，08:59:29 就被杀了 —— 只差 3 秒，所以看起来「话说到一半就没了」 |

**SIGKILL 不写 `=== 结束 ===`、不留 traceback**，加上最后一行恰好落在两次 tick 之间，
就伪装成了「无声退出」。**代码没问题。**

### 5.2 但我又复现了一次 —— 发现一个**启动陷阱**（新）

用裸 `setsid nohup` 从 SSH 启动 bot，结果它**在 SSH 会话一断开就死**：

```
13:57:37  启动（SSH 会话 1 同时断开）→ 正常出招
13:58:06  最后一行日志
13:58:07  SSH 会话 2 断开
（之后 ps 里已无该进程；journal 无 OOM、无 kill 记录）
```

对照实验：

| 启动方式 | SSH 断开后 |
|---|---|
| `setsid nohup python3 bot_v6.py`（裸启动） | **死**（复现 2 次） |
| `systemd-run --user --unit=... `（run2.sh 的方式） | **活**（跨 3 次以上断连，连续出招 1 分钟以上） |

**原因**：`setsid` 改的是 POSIX 会话，**改不了 systemd 的 cgroup**。SSH 会话作用域
被回收时，里面的进程全被 SIGKILL —— 所以既无 traceback 也无结束行。
`bot_v6.py` / `capture_pw.py` / `vmouse2.py` 里**没有任何** `os._exit` / `sys.exit` /
signal 调用（已 grep 确认），进程内不存在静默退出路径。

> **纪律：永远用 `run2.sh on`（或 `systemd-run --user`）启动 bot，不要裸 `nohup/setsid`。**
