## 1. 旧策略和「阶梯」哪里对不上

用户要的是**严格字典序**：同花 > 四条 > 葫芦 > 三条 > 两对 > 散牌 > 一对。
旧代码用的是一个加权和：

```
分 = 2600 × 严格多数色数 + 1800 × 并列多数色数 + w_score × 直接得分 + w_pot × 潜在分
```

加权和天生表达不了「严格优先」——一项足够大就能压过另一项。实测复现出三处偏差：

1. **该追新颜色的时候不敢追。**
   手牌 `GRBY?`（手里四色各一张、只剩一个空位）时，能凑到的最高牌型是
   **散牌 5000**，但它要求拿到一个「手里没有的颜色」。旧代码的目标色永远在手牌里，
   于是最好也只能凑成**一对 2500**。400 个随机盘面：旧代码 **400/400 都走一对**。

2. **拿不到目标色时，专挑消目标色最多的那一步。**
   这一步拿不到目标色的牌（这手同花注定死了），旧代码仍然按「消掉几颗目标色」排序，
   等于把棋盘上该颜色的库存清空。400 盘里有 159 盘（40%）第一步消的目标色是所有候选里最多的。

3. **排序主键是「模拟总分」。**
   300 个盘面里有 53 个，第一名是按模拟出来的总分选的，而不是按牌型。

## 2. 改成了什么

### 2.1 `poker.py`：把阶梯写成数据

```python
RANK_LADDER = (("同花", 50000), ("四条", 30000), ("葫芦", 15000),
               ("三条", 10000), ("两对", 7500), ("散牌", 5000), ("一对", 2500))
```

新增 `best_plan(hand) -> (名称, 分值, 还差几张, 目标色列表)`：从阶梯顶往下走，
第一个「还做得到」的牌型就是这手的目标；返回的「目标色列表」就是**要拿到哪几种颜色的牌**。

可做性按剩余空位算（`空位 = 5 − 已翻开张数`）：

- 同花：手牌里颜色种类 ≤ 1 → 还差 `空位` 张该色
- 四条：某色已有 n 张、`4 − n ≤ 空位`（多色都行则都进目标集合）
- 葫芦：三张 + 一对，`(3 − x) + (2 − y) ≤ 空位`
- 三条 / 两对 / 一对同理
- 散牌：**目标色 = 手里没有的颜色**（`颜色种类 + 空位 ≥ 5` 时可达）

对拍样例（全部通过）：`?????`→同花；`G????`→同花(锁 G)；`GGGR?`→四条(差 1)；
`GGRR?`→葫芦；`GGRB?`→三条；`GRB??`→三条(差 2)；`GRBY?`→**散牌，追手里没有的颜色**；
`GGRRB`→两对；`GRBYW`→散牌。

### 2.2 `solver_poker.py`：排序键改成字典序

```python
key = (-牌型值, 还差几张, -消目标色, -保住的供给, 不确定性,
       -特殊宝石权重, 是不是魔方招, i, j, i2, j2)
```

- 第一项 `-牌型值`：这一步发出的牌，能让这手**最高做到什么牌型**（用 `best_plan` 算）。
  这一项就实现了「优先同花、没有就四条、再没有就葫芦…」。
- `还差几张`：同样牌型下，离得越近越好。
- `-消目标色`：同牌型下，优先能发出目标色的那一步（`t[10]` 严格多数优先）。
- `-保住的供给`：还是平手时，优先把目标色留在棋盘上（旧代码在这里是反的）。
- **没有任何「消得多/总分」的项**——这就是「不求快」。

并列多数（游戏给哪色未知）不再单独加分，改成**对可能的牌色取期望**，
再加一点点不确定性罚分，避免「赌一把」。

返回值结构（11 元组）和下标**一个都没变**，`bot_v6.py` 不用改。

### 2.3 `modes/poker.py`：空手那条分支（行为改变）

旧代码：

```python
if not known:                      # 手牌一张没翻开
    rk = solver_pro.rank_moves(g, banned=banned)   # ← 普通评分：谁消得多谁第一
    cells = (t[6], t[7])
else:
    rk = solver_poker.rank_moves_poker(g, hand=hand, topk=10)
    cells = (t[5], t[6])
```

**每一手牌的第一张，就是这手牌能不能追同花的分水岭**（已翻开一出现第二种颜色，同花就死了）。
旧代码把这一张交给一个和牌型无关的贪心（普通评分），理由写在注释里是
「没有花色信息、乱打会攒骷髅」。这个理由不成立——游戏强制每手都要打出去，
这条分支实际效果只是「第一张不按牌型选」。

现在空手也走 `rank_moves_poker`：没有花色信息时它不会瞎选，而是按
「有多少步能把这个颜色做成严格多数」挑一个能持续产出的色当目标（第 17 轮定的规则，
当时被这条分支挡在外面、从没在实战里跑过）。

**回滚方式**：把 `choose()` 里那一段换回 `if not known:` 分支即可，其余改动不依赖它。

## 3. 离线证据

### 3.1 牌型阶梯（最直观的一组）

同一批 400 个随机盘面、同一手牌 `GRBY?`，两个版本各取自己的第一名，
看「走完这一步之后，这手牌还能做到的最高牌型」：

| | 一对 2500 | 散牌 5000 |
|---|---|---|
| 旧代码 | **400 次** | 0 次 |
| 新代码 | 0 次 | **400 次** |

### 3.2 新旧同盘面对照（400 盘 × 5 种手牌）

用第 17 轮的旧求解器（`牌局同花优化/solver_poker.py`，md5 `d73748e4`）
和新求解器跑同一批盘面：

| 指标 | 旧 | 新 |
|---|---|---|
| 同花还活时，第一名能发出锁定色 | 222 / 800（27.8%） | **222 / 800（27.8%）** |
| 同花还活时，第一名平均消掉几颗锁定色 | 2.21 | **1.04** |
| 同花已死时，第一名是计划目标色的严格多数 | 328 / 1200（27.3%） | 325 / 1200（27.1%） |

读法：

- 第一行一样，说明**「能发同花色牌的那一步」两个版本都找得到**——同花这条主路径没有被改坏。
- 第二行减半：拿不到目标色的时候（这手同花已经救不回来），新代码不再顺手清空该颜色库存，
  留给后面「四条/葫芦」用。这是「不求快」的直接体现。
- 第三行基本持平：换牌型的代价没有牺牲「能不能拿到目标色」。

### 3.3 三处旧偏差的复现与修复

| 偏差 | 旧代码 | 新代码 |
|---|---|---|
| `GRBY?` 目标色在手里 | 400/400 走一对 | 400/400 走散牌 |
| 拿不到目标色时消最多目标色 | 159/400 盘（40%） | 有真实取舍的 226 盘里，挑最少的 203 盘、挑最多的 9 盘 |
| 按模拟总分排序 | 53/300 盘 | 0（排序键里没有总分） |

## 5. 顺带核实的一条基础规则

第 17 轮把「一张牌的花色 = 这次消除的多数色」当成实测规则写进代码。这轮顺手用实机日志对了一次账。

**第一次统计得到 50%~66%，差点写成「规则错了」。** 原因是日志里「手牌」行只在读到至少一张牌时才打印，
相邻两条手牌行可能隔了好几步，把不相邻的两行凑成一对，得到的就是噪声。
改成只取**相邻两步、且手牌恰好多一张**的样本：

```
严格样本 699 条：新牌 == 目标色 640 条 / 不是 59 条 → 91.6%
```

**规则是对的**（8% 的例外可能是抓帧落在动画中间）。这条写下来是为了避免以后再踩一次同样的统计坑。

另外两件顺手看到的事（都**没改**）：

- **手牌读取有空洞、位置也不完全可信**：日志里出现过 `RWO?W`、`BBB?Y`，以及刚结算完
  第一张读成 `????Y`（牌在第 5 格）。但策略只用手牌的**颜色多重集**，不用位置，
  所以这些空洞不影响选步，只影响「还差几张」的估计（会自己纠正）。
  「已翻开永远是前缀」这条第 17 轮的说法至少不完整。
- 结算覆盖层的橙色占比实测 0.150 / 0.148（经典模式那套 0.5 阈值判不出来），与第 17 轮记录一致。

## 6. 待你确认的改动 / 未修问题

**工具修复声明（改到了既有资产）**：`poker.py` 里 `import numpy as np` 原来在模块顶层，
而 `numpy` 只用在 `_card_color()` 里。本机（手机）没有 numpy，导致整个牌局决策栈
在手机上无法离线测试。已把这条 import 挪进函数内部（惰性导入），行为不变、Deck 上无影响。
这是本轮唯一一处「为了能测试而动的既有代码」。

按优先级：

- **P1 牌局结算覆盖层**：打完一手牌中央弹的面板挡住输入，bot 只能乱点等它消失（约 80 秒/手），
  并引发 §4.4 的无走法风暴与频繁重启。这是目前牌局吞吐的最大单点。
- **P1 牌局频繁重启**：每 1~3 分钟一次，重启后要重新标定几何、重新进局。与上一条疑似同源。
- **P1 抓帧断了 bot 就永久瞎掉**（§4.4 第 3 条）：`capture_pw.py` 写死 `path=93`，
  PipeWire 视频节点一消失（实测 `pw-dump` 里一个 Video 节点都没有）就只会一直 `抓帧失败`，
  而 `gamescopectl` 兜底明明还能抓到帧。修法很小（取帧失败 N 次后降级到 `cap2.get()` 的兜底路径，
  或在启动时探测可用节点），但这是新改动，不在本轮点名范围，**当场没做**。
  当前 Deck 上 bot 仍在跑、但一直抓不到帧，需要你把游戏/Game Mode 弄回来让视频节点重新出现。
- **P2 `bot/install.sh` 仍不部署** `board_poker.json`、`board_butterfly.json`、`reader_mem.py`、
  `which_mode.py`（第 17、20 轮各记过一次）。全新安装会退回经典几何、牌局与蝴蝶直接坏掉。
- **P2 命名**：日志里 5000 分那档内部叫「散牌」，游戏面板上写「顺子」。为保持同一行日志
  只有一个名字，本轮沿用「散牌」。
- **P3 没有做深一层预判**：目前只看「这一步发出的牌」带来的牌型，没有模拟两步。
  做深一层会明显拉长每步耗时（当前 0.5~0.9 步/秒），没有证据表明划算，先记下。
