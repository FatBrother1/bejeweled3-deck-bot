## 二、确凿事实（下一步的出发点）

1. **整秒镜像 `0x109CBEC`（i4）**：暂停态与画面 5/5 吻合（56/53/38/36/17）。但钉住它 30 秒（写 200 次）画面照走 ⇒ 它是**每帧被覆写的镜像**。
2. **写入者是 `rep movsl` 块拷贝**（gdb 硬件观察点抓到，4 次）：
   - 现场 A：`0x65701a`（调用者 `0x604631`，后接 `jmp *0x657134(,%edx,4)` 分发）
   - 现场 B：`0x5fe5d1`，**下一条指令 = `incl 0xc84(%ebx)` = 递增 Board+0xC84 时钟**
   - 写入内容按帧在 **300.0 ↔ 202.0 ↔ 23.0（浮点）** 间交替 ⇒ 0x109CBEC 是**被复用的暂存槽**，多个 UI 属性结构体轮流 memcpy 经过
   - ★ **float 23.0 写入的瞬间正是倒计时=23 的时刻** ⇒ **倒计时以浮点形式存在于 UI/动画属性结构体中**，随块拷贝搬运
3. 结构体邻域（本轮 dump 过的窗口 `0x109cb40..0x109e590`）内是典型渲染属性值（0.5/1.0/0.207/545.0/676.0/300.0）。
4. **游戏时钟**：`Board+0x38`（厘秒，上升）、`Board+0xC84`（整秒，上升）、`Board+0xE38/E3C`、`Board+0x30A8`。钉住 B+0x38 共 25 秒（写入保持）画面照走 ⇒ **时钟不是显示源**（"剩余=结束时刻−时钟"假设被否）。
5. 倒计时框正确坐标 = **右上角 (1010,10)-(1155,90)**；`x=500..620` 是错误坐标（顶部中间的动画部件，噪声底 6.0 无秒级尖峰），**修改器会话记录的 (1025,18)-(1140,78) 才是对的**。

## 四、事故记录（两起，均已恢复）

1. **earlyoom 杀进程**：v1 扫描 's' 类窗口误含 0 → 1.33 亿命中 → 内存爆 → earlyoom 杀了 scan3.py，游戏也随之退出。**教训：扫描窗口永不包含 0；扫描进程内存超 1GB 即分块求交**。

## 五、接手点（下次第一件事）

1. 用户暂停并报数 N → 跑 `dump_window.py N`（窗口 `0x1098000..0x10A8000`，64KB）→ 找出所有 `f4 ∈ [N, N+1)` 的地址（母本+各副本一次现形）。
2. 对其中**非 0x109CBEC** 的地址逐个 `jump_pin.py <addr> f4 50 25`（跳 +5 秒并钉住）→ 用户肉眼看倒计时是否"跳+5 并冻住"。
3. 若母本也被块拷贝覆写：把观察点源地址（ESI）处的**结构体老家**找出来——扩展 `watch2.gdb`（已会打印 ESI/EDI），在命中时 dump `x/64xw $esi-0x40` 并多抓几次取交集；或以 0.02s 间隔同时钉住全部副本。
4. 找到后回填 `tscan2.py hold`（已支持 `hold <秒> <地址> <类型>`），交付《锁时间》使用说明。
