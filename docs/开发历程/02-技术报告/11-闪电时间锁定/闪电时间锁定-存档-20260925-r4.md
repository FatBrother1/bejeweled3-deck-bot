### ★ 本轮三项关键机制发现

1. **游戏内「菜单」键 = 暂停**（左下角 (215,730)）。弹出【选项】覆盖层，
   游戏逻辑完全冻结 —— 实测 `Board+0x38` 连续三次读数恒为 482/6761，而进程
   仍在运行、可自由读写内存。**这就是上一轮"用户暂停报数"的真实机制**。
2. **SIGSTOP 也能冻结，但会同时冻结游戏时钟** ⇒ 不能用物理时间当 Δt，
   必须用游戏内时钟做 Δt。这是 `fdump` 求出空集的根因。
3. **暂停态下点「返回」(882,597) 能恢复运行**，点「菜单」能再次暂停 ——
   已验证 `cs` 递增 / 冻结可反复切换（见 `run.py` 状态机）。

### ★ 状态判据修正（重要）

`Board` 指针在**结算页仍然是残值**（非空），所以「Board 非空」**不能**作为
"在对局中"的判据。可靠判据 = **`cs` 在两次采样间确实增长（≥20 厘秒）**。
`run.py enter` 已实现这条判据 + 自动重进局。

## 三、确凿事实（下一步出发点）

1. **整秒镜像 `0x109CBEC`（i4）：决定性证伪。**
   - 三次暂停快照交叉验证唯一命中：`A=15 → B=8 → C=1`
     （对应 ΔAB=675cs=6.75s、ΔBC=776cs=7.76s，两段独立吻合）
   - 四刻度（1/10/100/1000）× int/float 全内存复扫：**仍只有它一个**。
   - **但暂停态写入 300，0.3 秒内被改回 1** ⇒ 它是每帧被覆写的镜像，**不是母本**。
2. **写入者确认是 `rep movsl` 块拷贝**（gdb 硬件观察点，`watch3.gdb`）：
   - 现场 A：`PC=0x65701a`，ESI=`0x109e538`，EDI=`0x109cbf0`，**ECX=22**（每次搬 22 dword）
   - 现场 B：`PC=0x5fe5d1`，ESI=`0x109cb40`，EDI=`0x109cbf0`，ECX=6
   - **源结构体内容是渲染属性浮点**：`0x44024000`=520.5、`0x43ed4000`=474.5、
     `0x438b8000`=278.0、`0x3f000000`=0.5、`0x3f800000`=1.0
   - ⇒ 倒计时值**只是被搬运经过的字节**，源结构体里没有它以"字段"形式存在
3. **倒计时 ≠ 常数 − 游戏时钟。** 运行态实测 26 秒采样：
   `cs` 2430→4930（走），`show` 恒为 0，`show+cs/100` 从 24.30 单调涨到 49.30，
   **极差 25.00** ⇒ 两者不同源，倒计时另有独立存储。
   （三份快照里 `show+cs/100 ≈ 63` 的"巧合"是暂停态两边都冻结造成的假象。）
4. **`Board±0x8000` 内不存在 15/8/1 的任何表示**（int/float 都查过）⇒ 母本不在 Board 对象内。
5. **闪电局固定 60 秒**（结算页「总时间 1:00」），起始显示 1:00。
6. **`0x109CBEC` 所在区** = `00fa2000-011a0000 rwxp`（2MB 匿名段）；
   `gApp`(0x8E1730) 也在此区。**`Board`(动态 0xF4xxxxx) 不在同一区**——
   Board 在 `0xE1C2000-0xFA90000` 24.8MB 堆区，会随局变化。
7. `0x3936BD78`（v1 选出的 -1/s 候选）在 `372a0000-3aba0000` 57MB 匿名区。
   **至今未做画面同步验证** —— 是本轮遗留的可疑对象之一。

## 四、事故记录（两起，均为我方工具导致，已定位根因并修复）

1. **15:48:03 earlyoom 杀 `pclock.py`（PID 59018）**
   - 根因：把两次全量快照各存 int64+float64 共 4 份数组 ≈ **8.6GB**
   - earlyoom 阈值 `-M 409600,307200`（400MB/300MB，`/usr/bin/earlyoom -P ...`）
   - 后果：python3 被杀，**游戏 Bejeweled3.exe 与 Steam 会话随之退出**
   - 修复：`pdiff.py` 只存 int32（1.06GB）+ 边读边比 + RSS 硬闸
2. **16:07:53 earlyoom 杀 `pdiff3.py`（PID 60332）**
   - 根因：三份快照的「返回」点击未生效 ⇒ 游戏时钟三次全为 `cs=6761` ⇒ **Δ=0**
     ⇒ 「差值≈0」判据**退化为匹配全部未变化槽（~3 亿条）** ⇒ 候选列表爆内存
   - 后果：python3 被杀，**游戏再次退出**（Steam 客户端存活）
   - 修复：①`Δcs<=0` 直接报错退出，绝不比较 ②候选上限 30 万条 ③
     `ensure_paused`/`ensure_running` 自愈状态机（点完按钮**读时钟验证**是否真生效）

> 两次事故都记在 `证据_r4/incidents.log`。
> 根本纪律：**扫描/比较的内存占用必须与命中数成正比，绝不与内存总量成正比**。

## 五、接手点（下次第一件事）

按优先级：

1. **优先验证 `0x3936BD78`**（v1 遗留、从未做画面同步验证）。
   它满足「稳定 -1/s 且 25→1 单调下降」，是**目前唯一未被证伪**的整数候选。
   做法（工具已就绪）：`run.py enter` 进入运行态 → `decisive.py` 同款实验
   （暂停态写 +300 → 恢复 → 抓帧看画面是否显示 5:00 并冻住）。
2. **回到 gdb 抓"写入源"的源头**（接手点 #3 的升级版）。
   已知 `rep movsl` 源 `ESI=0x109e538 / 0x109cb40`。下一步应：
   - 用 `watch` 观察**镜像之外的槽**（例如把观察点设在这些源结构体内部某个
     随倒计时变化的字节上），反查**谁在给源结构体赋值** —— 那才是母本。
   - 或对 `0x109CBEC` 单步：`watch` 命中后打印 `$pc` 的调用栈
     （`bt`、`x/8i $pc-32`），沿调用者 `0x604631` / 上层函数找赋值点。
   - ⚠️ 注意：`0x65701a` 的**下一条是 `jmp *0x657134(,%edx,4)` 分发**；
     `0x5fe5d1` 的**下一条是 `incl 0xc84(%ebx)`（递增 Board+0xC84 时钟）**。
3. **换判据重扫**：既然倒计时既不等于镜像、也非时钟推导，那就用
   **"运行态连续采样，找每 1.000 秒精确 -1 且暂停时冻结的槽"**。
   `tb.py` 的快照机制已可用；注意暂停态下"冻结"是必要非充分条件，
   必须**同时**满足运行态每帧递减（可用两次运行态快照，Δt 用 `Board+0x38`）。
4. **兜底方案**：若母本始终找不到，可直接做**"冻结时钟"工具** ——
   实时把 `Board+0x38` 钉在低位（`live.py lock`）。虽然本轮已证伪
   "显示秒=常数−时钟"，但**先做 `live.py lock` 实测画面反应**是廉价的一步，
   值得一试（因为读取路径可能经过多级换算）。

## 九、两条必须留意的准确性提醒（存档后补充）

1. **地址稳定性分两类，别一视同仁。**
   - **EXE 映像内的地址是稳定的**（wine 默认无 ASLR，游戏加载在固定基址）：
     证据 = `reader_mem.py` 里 `GAPP_ADDR = 0x8E1730` 是**硬编码常量**且一直可用；
     `0x109CBEC` 在**第 3 轮**和**第 4 轮（重启后的新进程）**里都出现在同一地址。
   - **堆区地址不保证跨进程稳定**：`0x3936BD78` 位于 `372a0000-3aba0000`（57MB
     匿名 rwxp，属堆/动态区），而 `Board` 也从 0xF417600 变到 0xF404DC8
     ⇒ **`0x3936BD78` 在重启后可能失效**。下次验证它之前，建议先用
     `dfscan.py`（或 `track.py`）在**当前进程**里重新筛一遍 -1/s 候选，
     不要直接拿旧地址去写。
2. **`0x109CBEC` 的运行态行为补记（强化"暂存槽"结论）**：
   运行态 26 秒采样期间它**恒为 0**（而 `cs` 一路从 2430 涨到 4930）；
   只有**暂停瞬间**才短暂持有倒计时值（15/8/1）。
   ⇒ 它平时是 0，只在 UI 绘制时被写入倒计时值，随后又被覆盖 ——
   这比第 3 轮的"每帧被覆写"更精确：**它是一个绝大多数时间为 0 的复用暂存槽**。
   这也解释了为什么"按画面值搜它"在暂停态能命中、在运行态却命中不了。
