# 28 · 牌局「无走法风暴」根因与牌色修正（2026-09-27）

一句话：牌局每 1~2 分钟退出重启，根因不是「盘上没招」，而是**三件事叠在一起** ——
手牌结算覆盖层挡住输入、牌局求解器不认走法级拉黑导致同一招被连拒 3 次、
拉黑掩码把本来就只有几招的牌局盘整块掩死。三处都改了。

顺带查出一个**牌色读反**的老 bug：求解器在交换前的棋盘上读首层消除格，
而被交换的两格恰好总在首层里。实测 400 随机盘、31,757 个合法交换里
**5.16% 的招花色估错**，错的全是同一方向（把并列多数读成严格多数）。
它让 bot 白白放掉 43% 本来能拿到的目标色机会 —— 这正是「不抓同花」的主因。

---

## 一、风暴现场：先确认棋盘本身没坏

用户报「感觉在乱消宝石，根本不抓同花」，第一件事是排除「读盘读错了」。
在风暴发生的那一帧上做逐格核对（把内存读出来的字母画回截图，肉眼比对），
结论是**读盘是对的**：

- 风暴中的画面是一块**正常、完全可玩**的牌局盘，顶部提示「需要两对分或更高」，
  左侧分值表里顺子/一对两行有骷髅、还有「no entry」图标。
- 内存读出的 64 格与画面对得上（含一颗正在燃烧的蓝宝石，读成 `B`）。
- **内存盘上有 3 招**（暴力枚举与求解器一致，`bad=0`）；
- 游戏时钟在走（38409 → 38608，2 秒涨 199 厘秒）⇒ 不是失焦暂停；
- `gApp` 槽 `0x01924B08` 全程不变 ⇒ 不是读到了旧进程的盘。

所以「找不到走法」是**假**的。真凶是掩码：把拉黑计数 ≥3 的格子改写成 `"?"` 之后，
`"?"` 不但自己不能连线，还会切断别人的连线，而牌局盘本来招就少 ——
随机稳定盘的统计是**中位 11 招、≤3 招的比例 0.0%**，也就是说风暴里这种
「只有 3 招」的盘本身就是极端情况，几个掩码格足以把它掩成 0 招。

## 二、完整链条

1. 手牌打满 5 张 → 游戏在棋盘中央弹一层**结算覆盖层**（5 张白卡 + 牌型名 +
   「+分数」，金色星星飞散，约 2 秒）。这段窗口**游戏不接受交换**。
2. 覆盖层的判据是白卡带，`R-B ≈ 0`；而引擎里两个通用画面判据
   （结算面板靠暖色 `(R-B)>60` 占比、徽章面板靠顶部洋红条）**都命中不了它**。
   所以 bot 照常出手 → 交换被拒。
3. 牌局求解器 `rank_moves_poker` **没有 `banned` 参数**（普通求解器
   `solver_pro.rank_moves` 一直有），引擎算好的走法级拉黑传进 ctx 却被丢掉
   ⇒ **同一招每一步都被重选**。实测同一招 `(2,6)<->(3,6)` 在
   20:50:12 / 20:50:13 / 20:50:15 连拒三次，每次都打 `✗拉黑`。
4. 每次拒绝给那两格各 +1，三次就到阈值 3 ⇒ 掩码生效 ⇒ 盘上仅剩的 3 招全被掩掉。
5. `牌局无走法(1..30)` 连打 30 次、约 37 秒后 `DEAD_EXIT_AT` 主动 `break` 退出
   （不是崩溃，无 traceback），守护 2 秒后重拉、拉黑清空 ⇒ 再打一阵、再攒满 ⇒
   **这就是那个 1~2 分钟的周期**。

日志侧的旁证：`bot.out` 里 `检测到游戏结束` 199 次、`已点「再来一次」，新局已开始`
185 次 —— 说明通用判据对牌局的**「游戏结束」画面是有效的**，唯独漏了结算覆盖层。

## 三、四处改动

**（1）模式基类加「挡路画面」钩子**（`bot/modes/base.py`）
新增 `overlay_action(ctx)`，默认返回 `None`。动机与第 18 轮的模式脚本化一致：
这类画面是模式专属的，不该再往引擎里塞一条 `if`。

**（2）牌局认结算覆盖层**（`bot/modes/poker.py`）
区域 `(570, 330)-(1010, 470)`（中央白卡带），判据 = 白像素
（`min(R,G,B) > 200`）占比 > `0.15`。实测三张真实帧：
**结算覆盖层 0.475 / 正常对局 0.004 / 游戏结束画面 0.000**，阈值两侧余量都在 3 倍以上。
认出后**清空拉黑**（这段窗口里的拒绝是画面造成的、不是招不好）并轮询等它放完
（最多 8 秒），这一步不出手、也不计死局。
选择「等」而不是「点掉」：实测它是自己会消失的动画，点它反而可能点到棋盘格。

**（3）引擎每步开头调用钩子**（`bot/bot_v6.py`，+39 行）
放在两个通用画面判据之后、读盘之前。

**（4）牌局认走法级拉黑、并弃用掩码盘**（`bot/modes/poker.py`）
- 过滤 `banned ∪ banned_sticky`；候选**全被**拉黑时解禁重算并打一行日志
  （不解禁就会在原地打转、最后按「无走法」退出）。
- 直接用 `g_raw`（真实棋盘）。掩码对牌局**有害无益**：它的作用
  （别重选刚被拒的招）已经由 `banned` 承担，而牌局盘招少，几个掩码就足以造出假死局。

**（5）牌色改在交换后的棋盘上读**（`bot/solver_poker.py`）
`_colors_in_move` 加 `swap` 参数；调用处传被交换的两格。
这一步的影响见下节。

## 四、牌色读反：量化影响

旧读法直接在传入的 `g`（= 交换前的棋盘）上读 `first_cells` 的颜色。
被交换的两格**总在首层消除里**，所以它们的颜色读到的是换过去之前那一颗 ⇒ 多数色判错。

- 400 随机盘、31,757 个合法交换：**5.16% 估错**，修后 **0.00%**。
- 错法**全是同一个方向**：把「并列多数」读成「严格多数」。
  样本：`(4,3)<->(4,4)` 真实是 `5 颗 G + 5 颗 B 并列`，旧读法读成 B 严格多数。
- 后果：那一步被当成「拿不到目标色、还烧掉 5 颗 G」，被排序键里的
  「保住供给」压到后面；而它其实**有一半机会拿到 G 牌**，按期望值
  （同花 50000 与三条 10000 各半 = 30000）本该排第一。
- 同一批盘、同一手牌做 A/B（目标色取牌型阶梯定的那个色）：

  | 手牌 | 新拿到 / 旧没拿到 | 旧拿到 / 新没拿到 |
  |---|---|---|
  | `G????` | 94 / 400（24%） | 0 |
  | `GG???` | 94 / 400（24%） | 0 |
  | `GGG??` | 94 / 400（24%） | 0 |
  | `GGGG?` | 89 / 400（22%） | 0 |

  也就是说：目标色本来可拿的盘里，旧代码**放掉了 43% 的机会**，修后一招不落。

## 六、顺带查实（只记不改）

- **手牌读得对**：抓一帧、把 `CARD_BOXES` 画到图上肉眼核对 ——
  框住橙、红、3 张背面，读出 `O R ? ? ?`，与画面一致。
- **每步「拿到目标色」的比例 52.9%**（712 / 1346 个相邻两步）。
  按还差张数分：还差 4 → 83%、还差 3 → 41%、还差 2 → 46%、还差 1 → 57%。
  第一张最稳（目标色是按「有多少步能做严格多数」现挑的），后面靠盘面自己再摇。
- **测试辅助函数 `move_cards` 和被测代码犯的是同一个错**（都在交换前的盘上读），
  所以第 21 轮 40/40 全绿也没抓到这个 bug。已一并改掉。
- **引擎日志里的 `步/秒` 会出现 10~103 的离谱值**：`t0` 在续局分支被重置、
  `done` 没跟着重置，纯日志口径问题，不影响实际节奏（实测 0.53~1.32 步/秒）。
