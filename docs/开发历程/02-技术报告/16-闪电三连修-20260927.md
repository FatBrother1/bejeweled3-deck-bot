日期：2026-09-27（凌晨）　机器：Steam Deck deck@192.168.3.11　游戏：Bejeweled 3（Steam AppId 78000）

三个现象，三个根因，**互相独立但都修了**。

## 二、空转和重复交换：几何用错了

### 怎么发现的

给闪电棋盘重新标定（和之前蝴蝶/牌局/钻石矿同一套方法：抓一帧 + 用 `reader_mem` 读真实棋盘，网格搜 `(x0,y0,px,py)` 最大化「采样色==内存棋盘色」的格数），标定过程中撞到一个坑值得记下来：

**分类器必须带白宝石兜底，否则最优点会被拉到错的位置。**
第一版分类器只用「高饱和像素投票」（学 `vision_np` 的第一层），结果白宝石（低饱和）整块被排除，剩下的边缘像素被就近读成红色 → 最优解收敛到一个**偏左上**的错误几何，还打出 55/64 这种看起来不错的分数。
把 `vision_np` 的第三层「高饱和票数不足就用整格投票」搬过来之后，才在正确位置拿到 **64/64**。

### 实测数字

| 几何 | x0 | y0 | px | py | 命中 |
|---|---|---|---|---|---|
| 经典（原来一直在用的） | 476.0 | 79.0 | 89.17 | 88.17 | 44/64 |
| 闪电（本轮标定） | **498.0** | **126.0** | **85.286** | **85.90** | **64/64** |

行中心的偏差（经典几何给出的 → 闪电实际在哪）：

```
 79 → 126      差 47px
167 → 212      差 45px
255 → 298      差 43px
343 → 384      差 41px
432 → 469      差 37px
520 → 555      差 35px
608 → 641      差 33px
696 → 727      差 31px
```

半格是 43px，**每一行都差了将近半格以上**。拖动落点跑到隔壁行 ⇒ 游戏认为这不是合法交换、原样弹回 ⇒ 棋盘纹丝不动，而 bot 还在按自己的棋盘反复算同一招、反复点，同时把这些招一条条拉黑，拉黑满了就「解禁重算」再出同样的招 —— 这就是肉眼看到的空转和重复交换。

顺带一提：列中心的偏差只有 5~22px（不到 1/4 格），所以**左右基本能点中、上下全偏**，这也是为什么之前 54% 的步还能被判有效——不是全错，是错得刚好够难受。

闪电属于「现代版式」（格距 85.29，与蝴蝶 85.32 / 牌局 85.25 / 钻石矿 85.25 同族），但**原点又和它们都不一样**，所以必须单独一份标定文件，不能套用。

### 改动

- 新增 `board_lightning.json`（x0=498.0 y0=126.0 px=85.286 py=85.9，64/64）
- `modes/lightning.py`：`GEO = "classic"` → `GEO = "lightning"`，`GEO_WHY` 写明原因
- `install.sh`：板文件清单补进 `board_lightning.json`

### 验证

修完上线第一局：**开局 10 步 10 中**，全程 251 中 / 40 拒 = **86%**（修前 54%），1.01 步/秒，单局 391 步。

## 三、再来一局开关不起效果：两个原因叠在一起

### 原因 ① 旧结算判据差 0.04 分

旧判据（区域 150:650, 150:1130、橙色占比阈值 0.5）在闪电结算面板上实测 **0.461**，差一点点判不出。
闪电的结算面板比蝴蝶/钻石矿的**浅**，而且下半块是深褐色的柱状图区（火焰x7 / 闪电x3 / 时间+0:45 那一排），把整块区域的平均橙色占比拉了下来。

**重订判据**（对着 24 张真实抓帧量出来的）：

- 区域收窄到**上半张卡片 `f[150:450, 200:1080]`**——避开下面那块深褐柱状图，也避开左右装饰边框；
- 特征换成 **`(R-B)>60` 的像素占比**——结算卡片是暖色（R 远大于 B），对局区是彩色宝石 + 深蓝灰底（R-B 很小），分离度比原来那套四条件与运算大得多；
- 阈值 **0.75**。

实测两侧余量：

```
结算面板（7 张不同模式的样本）   0.876 ~ 0.912    全部 > 0.75   余量 +0.14
徽章面板                        0.647 / 0.626    全部 < 0.75   余量 -0.10
其余 20 张（对局/菜单/模式树等） 0.000 ~ 0.444    全部 < 0.75   余量 -0.31
```

> 阈值为什么不是 0.65：第一版我定在 0.65，上机实测撞到徽章面板 0.647，**只差 0.003**。
> 换成 0.75 之后两边余量都拉开到 0.1 以上。这个 0.003 的擦边是这轮最险的一处，
> 差点就当成「修好了」。

### 原因 ② 游戏局终会自己弹「徽章面板」盖住结算面板

这个是靠逐帧录像抓到的，**不是 bot 点出来的**：

把 2.5fps 的录像和 bot 日志对齐，局终那一刻的画面序列是——

```
t=316.0  v=0.077   对局画面（棋盘还在，时钟已冻结）
t=317.7  v=0.340   一枚徽章图标从左侧飞入、面板开始放大
t=318.1  v=0.585   面板放大中
t=318.5  v=0.626   徽章面板完全展开，盖在结算面板上面
```

期间 bot 没有任何一次点击落在徽章按钮上（那一局的走法里根本没有第 7 行的棋子）。
所以结论是：**闪电模式局终时，游戏会自动弹出徽章面板**（应该是这局达成了某个徽章进度——实测两局分别是「超级新星」「顶级机密 2/4」）。

这个面板**没有「再玩一次」，只有底部一个洋红色的「关闭」按钮 (640,716)**，而且它盖在结算面板上面，于是 `screen_is_gameover` 读到的是徽章面板的 0.626，永远判不出结算 ⇒ 永远点不到「再玩一次」，棋盘冻结、每步交换都被拒 ⇒ 日志满屏 `✗拉黑` + `时钟已冻结`，抢焦点两级自愈也无效（因为根本不是暂停）。实测卡过 5 分钟。

**识别徽章面板**用的是它顶部那条洋红色标题条（写着「徽章」）：

```
区域 y=48..78, x=330..950，洋红像素占比（R>140 & B>80 & G<100）
    徽章面板        0.451
    其余 20 张最高   0.039
```

差 11 倍，阈值 0.20。
（⚠️ 特意**没**拿底部「关闭」按钮的位置当判据——结算面板的「再玩一次」就在 y=722 附近，两个区域一重叠就分不开了，实测 0.362 vs 0.276。）

**处理**：认出它 → 点 (640,716)「关闭」→ 下面的结算面板露出来 → 下一轮照常续局。
这一步**不跟 --auto-restart 开关联动**：它是「把挡路的面板关掉」，不是「继续玩」；
开关关掉时关完它也只是回到结算面板待命，和原来开关=关的行为一致。

### 验证

- `test_settle.py`（本轮新增，70 项）：结算 7 张全过、非结算 21 张全过、徽章面板识别 + 误判 0
- `test_modes.py`（模式脚本化回归，40 项）：全过
- 上机连打：**连续 3 次自动续局**全部成功，每次局终 1~2 秒内「检测到游戏结束 → 已点再来一次」；3 局累计 713 中 / 145 拒 = **83%**，零冻结告警
- 结算面板从时钟冻结到画完只要 **0.2 秒**（逐帧量过：+0.09s 判据 0.208 → +0.18s 0.701 → +0.27s 0.890），所以只要面板没被徽章面板盖住，检测一定来得及

**徽章面板自愈的端到端验证**（受控，做了一次）：

停掉 bot → 等局终结算出现 → 手动点「徽章」把面板弹出来 → 启动 bot：

```
08:00:45  ★ 检测到徽章面板（局终游戏自动弹出，盖住了结算面板）→ 点「关闭」
08:00:47  ★ 检测到游戏结束（结算画面）
08:00:48  已点「再来一次」，新局已开始
08:00:49  像素几何: lightning  x0=498 y0=126 px=85.29 py=85.90
08:00:50  #1 ... ✓
```

一次跑通。之所以要特意做这一步：徽章面板是概率性弹出的（达成徽章进度才有），
连打 3 局都没碰上，不能靠等 —— 手动把它摆出来验证了完整链条。

### 顺带修的一个隐患：出手前再复查一眼画面

第一版验证时抓到一个细节：结算检测在每轮**开头**做一次，而真正出手（`m.drag`）隔着「读盘 + 求解」的 0.3~0.5 秒。结算面板的按钮行（徽章 / 再玩一次 / 主菜单，都在 y=738）**正好压在棋盘第 7 行的格心上（y=727，只差 11px）**，如果面板恰好在这 0.5 秒里弹出来，这一拖就等于替玩家点了「徽章」或「主菜单」。
所以在 `m.drag` 之前加了一次复查：再抓一帧、判一次结算，命中就本轮不出手，让下一轮的结算逻辑接手。只多读一次抓帧缓冲，不额外点击、不改时序。

## 四、时间宝石：修好前两条之后它自己就好了

上一局（几何错的时候）统计过：109 次读到时间宝石，选中的步只有 9 次碰到宝石（5 中 4 拒）。当时怀疑是「一次被拒就永久拉黑」。

修完几何之后不需要改任何权重，`solver_pro` 里那条 `+100000×踩到宝石数` 本来就在：

```
01:05:43   ⏱ 时间宝石 1 个: (2,2)+5
01:05:43   ★ 这一步直接拿时间宝石
01:05:44   #4   (2, 2)<->(2, 3) 预测=150   实际=0      ✗拉黑
01:05:44   ⏱ 时间宝石 1 个: (3,2)+5
01:05:44   ★ 这一步直接拿时间宝石
01:05:45   #5   (3, 2)<->(4, 2) 预测=100   实际=1050   ✓
```

那一局 291 步里 23 步是「直接拿时间宝石」，棋盘上反复出现 +5/+10 宝石，**一局从 1 分钟拉到 6 分多钟**（时间宝石每颗 +5 秒，等于这一局多吃了几十颗）。

结论：之前「不优先吃宝石」主要是**几何错导致步法全被拒**造成的表象 —— 宝石在盘上，求解器也选中了，但交换被游戏弹回，宝石吃不到；再加上结算判不出导致一局卡死，看起来就是「完全不理时间宝石」。

> 一个可复核的观察（没有改，只是记下）：`base.choose()` 把 `tgset` 传给引擎做**粘性拉黑**，
> 拉黑条件是「交换的两格里有一个是宝石位」。而宝石被**消除**（比如作为三连的第三个）
> 时不一定是交换的那两格，所以严格说 `tgset` 判的是「这次交换动了宝石位」，
> 不是「这次消除吃掉了宝石」。上一局那个 9/109 的统计用的也是同一个口径。
> 本轮没动它 —— 修完几何之后行为已经正常，再动就是没有证据的优化了。

## 五、待你确认的改动

除了你点名的三件事，本轮碰了这些，都在上面写明了原因：

**P1（建议采纳）**
- `install.sh` 的板文件清单补进 `board_lightning.json` —— 不补的话，全新安装的机器上闪电模式会退回经典几何，等于坏掉。这和之前 `board_butterfly.json` / `board_poker.json` 漏在安装脚本外是同一类问题。

**P2（外观/日志）**
- `screen_is_gameover` 的判据和阈值变了，`--death-shot` 连拍的画面仍然是同一套，无需重标定按钮。

**P3（优化，没做，只是记下）**
- 结算面板从时钟冻结到画完只要 0.2 秒，所以「出手前复查」理论上还有约 10ms 的窗口。要不要干脆用「时钟冻结就停手」这道闸兜底，我没有加 —— 它会在读盘抖动时误停手，风险大于收益。
- 徽章面板识别只验证了一张样本（加上 neg/ 里那张共两张）。如果游戏还有别的弹出面板（比如成就解锁横幅），现在的判据认不出，会退回「卡住等自愈」。等真实遇到再补样本。
