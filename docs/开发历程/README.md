# BJBot 开发历程：从零到 v2.0.0

2026-09-24 到 2026-09-27，四天，23 轮迭代。起点是一个「能不能让 bot 自己玩宝石迷阵 3」的想法，
终点是发出去的正式版 v2.0.0——一个从游戏进程内存里只读棋盘、用模拟鼠标打牌的 Python 程序，
外加一个在 Steam Deck 游戏模式里开关它的 Decky 侧边栏插件。

这份记录回答的是「发生过什么」：每一轮在解决什么、哪条路走通了、哪条路走死了、哪些结论后来被自己推翻。
它不回答「怎么接手」——安装、参数、排障、待办那些内容不在这里。

材料里的每个数字、文件名、提交号、md5 都是从当时的报告和日志里抄的；查不到的写「未记录」，不做推测。

---

## 一句话说清这是什么

BJBot 分两半，互相独立：

- **bot 本体**：一套 Python 脚本。棋盘直接从游戏进程内存里读出来（只读，从不写入），
  每步算一个最优交换，用模拟鼠标拖过去。不注入游戏进程，不改游戏文件，不联网。
- **Decky 插件**：Steam Deck 侧边栏里的一个面板，用来在游戏模式下开关 bot，
  看当前模式 / 启动脚本 / 抓帧后端 / 步数 / 时长。

插件不打包 bot，它只调用 Deck 上 `/home/deck/` 里的脚本。打牌全在 bot 里。

代码全部由 AI 编写，主模型 deepseek-v4.1-flash，闪电修复那几轮用了 glm-5.3-flash，人一行没写。

## 起点

09-24 开工时面对的是三个具体问题：

1. **抓帧只有 2fps。** Steam 自带的 `gamescopectl screenshot` 实测 0.45 秒一帧（2.2 fps），
   而且只支持 PNG（bmp/jpg/raw 全不支持），换 `/dev/shm` 落盘也一样——瓶颈在 PNG 编码。
   当时的判断是「想拿到可用速度，大概得写 DLL 注入」。
2. **状态判据不明。** 怎么知道棋盘静止了、可以出手？最初的做法是「两帧识别结果一样就算静止」。
3. **不知道游戏状态在内存的哪里。** 走子前后差分有 787~1059 页变化、噪声过大，相等关系模式反查零命中，
   棋盘不是「64 个连续类型 ID 数组」，很可能是对象数组。

当时定的目标：不改游戏文件、不做注入，让 bot 在 Steam Deck 上自动玩，并且把单步耗时压到
「500 毫秒级」。后面这条目标的前提在第四轮就被推翻了（见阶段一）。

### 阶段一：外置视觉闭环跑通，两条路走死（09-24）

要解决的问题是「能不能不动游戏就玩起来」。抓帧换成 PipeWire 之后速度问题直接消失：
gamescope 在 PipeWire 里暴露一个 `Video/Source` 节点，走
`gst-launch-1.0 pipewiresrc path=93 ! videoconvert ! video/x-raw,format=RGB ! fdsink fd=1`，
实测 90.7 fps、11 毫秒一帧，比 gamescopectl 快 40 倍。原以为要写 DLL 注入才能拿到的速度，
用现成的东西就够了，零注入。

关键转折是「静止判据」被证伪。连消和道具自播动画会造成假静止，bot 抢在动画中出手，交换被游戏吃掉。
实测静止时帧间差 p90=0.44、动画中 p90=10.73 ⇒ 改成像素级帧间差 <2.0 连续 4 帧。
输入方式也做了对照实验：按下后立刻移动 4/4 成功，中间加等待反而 2/4，位置跟踪静默失效
⇒ 采用每步撞角归零（代价 0.02 秒）。结果：实盘 90 步跨 4 关、0→34,110 分、0.8 步/秒。

同一天还试了三条没走通的路。用户原本想要的是修好 KelSat 修改器，结论是修不好——
它按进程名找 `popcapgame1.exe`，而实际跑的是 Steam 版 `Bejeweled3.exe`，代际不兼容；
转而自造了分数定位。内存只读这条路本身跑通了（免 root、同 uid 直读 1463 MB/s，
全量 1.1 GB 约 0.76 秒），但「棋盘就是 64 个连续类型 ID 数组」的假设失败，
走子前后差分有 787~1059 页变化、噪声过大。
攻动画瓶颈的路线 C 被决定性证伪：无加速单步 9.877 秒 vs SpeedHack 2 倍 9.877 秒，
加速比 1.00x，途中两次把游戏搞到卡死。动画变量逆向方法有效、变量没找到——
22,301 个候选里只有 16 个被代码绝对引用（0.07%），且 6 个波形命中做 3 次独立复现后全部排除。

### 阶段二：单步耗时优化与三消逻辑（09-24）

这一轮本来是要压单步耗时，结果把目标本身推翻了。逐阶段计时发现「等静止」那 2353 毫秒里，
识别占了 2147 毫秒——原代码在每一帧都调 `read_grid_np`，一次等待要处理 40 多帧。
也就是说，「动画占 96.7%」是测量假象，那两秒是自己的识别开销。

干净测出来的游戏动画真实时长是 535 毫秒，加拖动 182 毫秒，单步下限 717 毫秒、上限 1.39 步/秒
⇒「500 毫秒级」物理上不可达。改法是解耦静止判定与识别：等待时每帧只做降采样像素差（约 1 毫秒），
确认静止后才识别一次。每步 2000 ms → 834 ms，每步识别次数约 40 → 2.0。

随后是 pending 优化（复用上一步已确认的静止结果）与静止窗裁定。这里发现「步/秒会骗人」：
跑得最快的那一版 1.39 步/秒，分/秒只有 69.4，比基线还低，因为它不等动画演完就出手。
指标从此改成「分/秒」。40 步一组测下来 `--still-ms 250` 最优（168.3 分每秒），加大反而劣化。

求解器方面做了 `solver_pro`：A/B 实测旧 `fast` 320 分/步、181 分/秒，新 `pro` 695 分/步、325 分/秒。
同时得到一个否定性发现：得分本质是随机补给依赖，无法预测（相关系数 0.083，蒙特卡洛版 0.106）。

### 阶段三：内存后端、牌局模式与插件正规化（09-24 深夜）

抓帧和识别之外，棋盘能不能直接从内存拿。棋盘对象的地址来源是补做的 GitHub Code Search：
第一条查询就命中 `Ykzl/Bejeweled-3-Helper`，它的 README 明写只在 Steam 版上测过，
给出了完整布局（`gApp 0x008E1730`、`Board [gApp+0xBE8]`、`Piece [Board+0xF8+4x+32y]`、
颜色 `+0x220`、状态 `+0x228`、分数 `+0xD24`）。实机逐格比对 64/64 全中，
读一次完整棋盘 1.18 毫秒（视觉 54~77 毫秒），分数用 `+0xD24` 验证（画面 850 时读数 850）。

关键转折是一条反直觉的结论：静止判定仍然必须用像素差。过场动画期间内存里的棋盘数据完全冻结，
只看内存会以为可以出手，交换必被拒。混合方案（像素差判静止 + 内存读棋盘）在三种方案里指标最高。

同一段时间攻下牌局模式：一次消除给一张牌、花色等于这次消除的「多数色」（官方 wiki 未写明，10 轮实证），
手牌满 5 张自动结算。多数色规则把分数从 18000 打到 103900，分/秒 757.3。接着做了自动续局——
这里踩了一个坑：不能用 Board 指针判游戏结束，停在结算画面时它依然非零、只是数据冻结。

另外还做了游戏模式开关的 Decky 插件，第一步就走错了：手写 `dist/index.js` 没编译、
凭目测猜全局变量 `window.DFL`，实际 `DFL` 是 rollup 把 `@decky/ui` 打进来之后的局部绑定名，
于是整个 Decky 侧边栏渲染失败（`Error Reference: Shared SteamUI_1097`），连插件商城也打不开。
按源码加 `@decky/rollup` 正规重建（v0.2.0），再修掉 PyInstaller 的 `LD_LIBRARY_PATH` 污染
（v0.2.1），游戏模式开关才算打通。

### 阶段四：一个模式一个坑（09-25 到 09-26）

用户解锁钻石矿之后，问题开始成批出现，而且根因高度重复：**同一个游戏，每个模式的棋盘像素位置都不一样。**
`board.json`（经典/禅意）是 `x0=476.0 y0=79.0 px=89.17 py=88.17`，钻石矿实测
`x0=469.0 y0=133.1 px=85.25 py=84.50`（低约 54px）。决定性 A/B：用经典几何拖 (833,255)→(833,344)
变化 0 格，用实测几何拖 (809,304)→(809,388) 变化 12 格。差半格以上，拖动就落到棋盘外被拒。

钻石矿一共走了三轮修复：空转（几何错 + 指纹取自被改写的棋盘）、挖深后假死局（拉黑掩码把真棋盘掩成 0 候选）、
挖金与挖深策略。中间用户纠正了一次方向：目标是往下挖、越深越好，金子只是顺带的加分数，
按金子增量判断 bot 表现是错的。

另一条被反复验证的机制：**游戏会因失去焦点而静默暂停**——画面照旧渲染、甚至帧间还有差，
但棋盘冻住、所有拖动全被拒。唯一可靠判据是游戏时钟 `Board+0x38`（厘秒），画面帧间差不能当判据。
蝴蝶那一轮为此浪费了十几轮，还差点把「几何偏移」的假结论写进代码。第 16 轮把这条机制写进代码，
做成通用的失焦暂停自愈（两级降级：中性点击抢焦点 → 点覆盖层「返回」）。

模式识别本身也修了一轮：`which_mode.py` 的映射表六条里错了 2 条、漏了 1 条，
而且插件实际跑的是 Deck 上那份旧文件。修法是映射表只留对着画面核过的值、
「读不到棋盘对象」如实报菜单（`src="noboard"`）而不是拿去喂图像指纹。

### 阶段五：从 if 链到模式脚本（09-26 深夜到 09-27）

四个模式的修复全塞在 `bot_v6.py` 一条 if 链里、靠棋盘特征倒推模式，代价在牌局那一轮付清了：
修钻石矿时加的 `if nd > 0: 棋盘判据 else: 分数判据` 把牌局留在错分支里，
而牌局消除宝石不给分 ⇒ 每一步真有效的交换都被判「被拒」⇒ 拉黑 ⇒ 掩码棋盘 ⇒ 每 12 步停手 20 秒。
「判据写在一起，就一定会有人漏在分支外。」

于是做模式脚本化：引擎 `bot_v6.py` 只留与模式无关的东西（循环/抓帧/读盘/鼠标/暂停自愈/结算检测），
每步调 `mode.choose(ctx)`；`modes/<key>.py` 一个模式一个文件，声明
`KEY/NAME/GEO/EFFECTIVE/DEAD_EXIT_AT` 加 `detect/choose/on_board_info/on_picked/on_no_move/settles_on_clock_freeze`，
其余继承 `modes/base.py`；八个薄壳 `bot_<key>.py` 把模式钉死；守护 `watch2.py`
按 `which_mode.py` 认出的模式拉起对应入口，运行中模式变了也换脚本（两拍防抖）。

几何问题在这一阶段收尾：闪电、牌局各自拿到一份 `board*.json`。闪电用经典几何时行中心差 31~47px
（半格是 43px）、列只差 5~22px，所以不是全错、是错得刚好难受，有效率只有 54%；重标定后 64/64。
牌局同样从 44/64 修到 64/64、色距 5513→1725。经典模式还加了一条策略：
攒着万变魔方不用，盘上没有可消的三连了才动它（改后魔方存活从 2 秒变成 67 秒）。

### 阶段六：兜底、发行资产与正式版（09-27）

最后一轮从一次真实故障开始：PipeWire 的视频节点整条消失（`pw-dump` 里 0 个 `Video` 节点），
`capture_pw.py` 里 `path=93` 写死、`PwCapture.get()` 超时返回最后一帧而不是 None，
于是 bot 永久瞎掉、还不会自己恢复。改成启动时自动发现节点 + 运行中断流检测 + 退 gamescopectl 兜底 +
每 60 秒回试 PipeWire，回来自动切回 90fps。

这一轮同时定了一条纪律：**恢复性/运维性动作直接做，不要列进待确认清单**——
用户的原话是「我不确认 bot 不就永远瞎了」。

然后是正式版。GitHub 上已经有早期乱发的 v1.0.0/v1.1.0/v1.2.0，版本号问过用户、用户选 v2.0.0，

因为发行资产是快照、修复落在发布之后就必须回头改。

## 最后长什么样

**八个模式，一个模式一个文件。** `modes/` 下是 classic zen lightning icescape butterfly diamond poker quest，
每个声明自己的几何、有效判据、死局退出阈值。默认 `--mode auto`，按「特征越独特越靠前」的顺序问：
牌局（画面左侧绿色分值表）→ 钻石矿（有泥土）→ 蝴蝶 → 闪电 → 冰风暴 → 禅意 → 任务 → 经典兜底。
冰风暴与任务是空实现（能跑，没有针对性打法），禅意目前与经典同策略。

**五份棋盘几何。** 同一块屏幕上各模式的格距与原点都不同，差半格以上拖动就会被拒：

| 模式 | x0 | y0 | pitch_x | pitch_y |
|---|---|---|---|---|
| 经典/禅意（`board.json`） | 476.0 | 79.0 | 89.17 | 88.17 |
| 钻石矿 | 469.0 | 133.1 | 85.25 | 84.50 |
| 蝴蝶 | 约 492 | 约 137 | — | 约 84.8 |
| 牌局 | 482.5 | 113.0 | 85.25 | 85.25 |
| 闪电 | 498.0 | 126.0 | 85.286 | 85.90 |

**抓帧自动发现加兜底。** 优先 PipeWire（启动时从 `pw-dump` 找 `media.class == "Video/Source"` 的节点，
点名 gamescope 的优先，找不到才退回 93），90fps；失败退 `gamescopectl screenshot`（约 2fps），
兜底期间每 60 秒回试 PipeWire，回来自动切回。

**牌型阶梯。** 牌局按 `RANK_LADDER`（同花 50000、四条 30000、葫芦 15000、三条 10000、
两对 7500、散牌 5000、一对 2500）选步，排序键是字典序而不是加权和，键里没有任何「消得多」的项
——先保同花，同花死了退四条，以此类推，不图消得快。

**Decky 插件。** 面板显示当前模式 / 启动脚本 / 抓帧后端 / 步数 / 运行时长，
一个续局开关（单一事实源是 `/home/deck/bjbot/autorestart` 标记文件），
「启动脚本」那栏从实际在跑的进程读（`pgrep -af`）。

**发行资产三个 zip。** 每个 Release 挂三份，用 `git archive` 打（自动排除 `.git` 与 `__pycache__`）：
整仓 `bejeweled3-deck-bot-<版本>.zip`、bot 本体 `bejeweled-bot-<版本>.zip`、
插件 `BJBot-<版本>.zip`。v0.2.16 及更早是 `.tar.gz`，从 v0.2.17 起改成 `.zip`。

## 这四天最值钱的十条经验

1. **「画面两帧识别相同」不能当棋盘静止判据。** 连消和道具自播动画会造成假静止，bot 抢在动画中出手、
   交换被游戏吃掉，表现成「反复算同一招、分数不涨」。实测静止帧间差 p90=0.44、动画中 p90=10.73。

2. **游戏失去焦点会静默暂停，而画面帧间差也判不出来。** 画面照旧渲染、甚至帧间还有差，
   但棋盘冻住、所有拖动全被拒。唯一可靠判据是游戏时钟 `Board+0x38`（厘秒）：正常 7.5 秒走 750，暂停时冻住。
   蝴蝶那一轮为此浪费了十几轮，差点把假几何结论写进代码。

3. **标定分数高不等于标定对了。** 第一版分类器只用「高饱和像素投票」，白宝石低饱和整块被排除、
   剩下的边缘像素被就近读成红色，最优解收敛到一个偏左上的错误几何，还打出 55/64 这种看起来不错的分数。
   必须把标记画到图上肉眼核一遍——那个错解就是这么抓出来的。

4. **同一块屏幕上每个模式的棋盘位置都不一样。** 差半格以上拖动就被拒，而 bot 看起来一直在正常工作、
   只是每一步都被拒。原来的假设是「一套几何通用」，实际是每个模式必须单独一份 `board*.json`。

5. **判据写在一起，就一定会有人漏在分支外。** `if nd > 0: 棋盘判据 else: 分数判据` 是为钻石矿加的，
   牌局被留在错分支里 ⇒ 每一步真有效的交换都被判「被拒」。最后靠模式脚本化从结构上解决。

6. **拉黑掩码会制造假死局。** `?` 掩码不只是「这格不能碰」，还会切断别人的连线；同一盘面 bot 用的
   候选 0、真实棋盘候选 2。而且越到后期越严重——钻石矿越挖越深、可用宝石区越小，几个掩码就足以把整盘掩成 0。

7. **内存扫描的内存占用必须与命中数成正比，绝不与内存总量成正比。** 两起事故都是自己的工具把游戏挤爆的：
   一份脚本两份快照各存 int64+float64 共约 8.6GB；另一份因为 Δ=0 判据退化成匹配全部未变化槽（约 3 亿）。
   Deck 上 earlyoom 阈值只有 400MB/300MB，杀的是 python3，游戏和 Steam 会话一起退出。

8. **测量前先问「有没有别的东西在动同一台机器」。** 守护 `bejewel-watch` 会自动拉起 bot（`--mode auto`），
   做 A/B 时它自己起一个 bot 抢鼠标，那轮前半段的分数涨到 81250 其实是它打的。
   可靠的证据是 traceback、拉黑率、几何命中数这类不受抢鼠标影响的东西，不是分数曲线。

9. **结论的强度不能超过样本量。** 新代码上机只有 128 条手牌行，按旧比例只该期望约 0.4 把同花
   ⇒ 不能声称同花率提升。更打脸的是旧代码在同一晚的 22 分钟里打出过 2 把同花——
   「旧代码打不出同花」这句话是错的。

10. **日志显示成功不等于功能可用；「无声退出」先查外部谁杀了它。** Decky 的 `found plugin` /
    `Loaded BJBot` 只证明后端 `main.py` 起来了，前端的错要等 Steam UI 真正渲染面板才暴露。
    同理，bot「话说到一半就没了」的真因是 `run2.sh off` 发的 SIGKILL——SIGKILL 不写结束行、不留 traceback。

## 这份记录怎么读

各子目录：

- `01-项目概况/` —— 是什么、23 个 Release 的时间线、实机运行快照、资产盘点。
- `02-技术报告/` —— 按轮次编号的 26 组报告（23 篇 Markdown 加 3 个带代码与证据的目录），
  看名字就知道每轮修了什么。编号顺序大致对应时间顺序。
- `03-踩坑与教训/` —— 11 篇，按类别归的坑：标定与几何、抓帧、测量与验证、发布与运维、Decky 插件。
- 代码不在这份记录里 —— 代码就是仓库本身（`bot/` 含 `modes/`、五份 `board*.json`、五个离线测试；
  `decky-plugin/BJBot/` 是插件）。正式版快照见 tag `v2.0.0`。
- `05-配置与运行/` —— 运行参数、Deck 路径清单、仓库信息、容器工作目录。
- `06-开发进度与存档记录/` —— 第 1~23 轮的完整叙述，这份 README 的主要来源。
- `07-回滚与应急/` —— 回滚脚本与操作说明、已知问题与待做。

这份记录在代码仓库里位于 `docs/开发历程/`；本地打包的 tar 版本内容相同，只多一份代码快照。

建议阅读顺序：**01 → 06 → 02 → 03 → 05 → 07**。
先用 `01-项目概况/项目一句话说明.md` 花半分钟建立整体印象，再进 `06-开发进度与存档记录/`
读完整过程（这是信息密度最高的一块），遇到想深挖的轮次按编号翻 `02-技术报告/`，
然后扫 `03-踩坑与教训/` 把教训过一遍，`05-配置与运行/` 补齐参数与路径，
最后用 `07-回滚与应急/已知问题与待做.md` 看还剩什么没解决。
