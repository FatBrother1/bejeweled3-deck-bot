# 发布与运维踩坑

## plugin_loader 是系统单元

查插件加载日志用 `journalctl -u plugin_loader`。`journalctl --user -u plugin_loader`
查不到任何东西 —— 第 17 轮先被这个骗了一次，以为插件没加载。
正确日志形如 `Loaded BJBot (v2.0.0)`，同时能数到插件总数。

## 插件目录属主是 root

`scp` 直接覆盖 `/home/deck/homebrew/plugins/BJBot/` 会被拒。先
`sudo chown -R deck:deck` 也没用 —— 重启 plugin_loader 会把属主改回 root:root，
Decky 自己管这个目录。固定做法（已验证两次）：`scp` 到 `/home/deck/` 家目录 →
`sudo -n cp` 进插件目录 → 删临时文件 → 重启 loader。`plugin.json` 是 root 所有、
`package.json` 是 deck 所有，两个文件要分别用 sudo 和普通 cp。

## 备份不能放在 homebrew/plugins/ 下

放在那里会被 Decky 当成插件加载。备份一律放 `/home/deck/bjbot/` 下，
比如 `/home/deck/bjbot/backup-hc-20260927/`。bot 代码在 `/home/deck/` 下，
`/home/deck/bjbot/` 只放日志和备份。

## 从 SSH 裸 nohup 启动的进程会被 SIGKILL

现象：`setsid nohup` 从 SSH 起的 bot，SSH 会话一断就死，复现 2 次。
用 `systemd-run --user`（也就是 `run2.sh on` 的方式）起的，跨 3 次以上断连照常出招。
根因：`setsid` 改的是 POSIX 会话，改不了 systemd 的 cgroup；SSH 会话作用域回收时
里面的进程全被 SIGKILL。纪律：永远用 `run2.sh on` 启动，不要裸 `nohup`/`setsid`。
已 grep 确认 bot 代码里没有任何 `os._exit`/`sys.exit`/signal 调用，
进程内不存在静默退出路径 —— 所以「无声退出」先查外部谁杀了它，
`journalctl --user -u bejewel-watch` 里会明写 `Killing process ... with signal SIGKILL`。

## Deck 会睡眠断网

长等待类验证要留余量。第 19 轮 SSH 到一半报 `No route to host`，全网段扫 22 端口
无一开放，等它自己醒来才恢复。

## git push 的 GnuTLS 抖动

推送到 GitHub 偶发 `GnuTLS recv error (-110)`（TLS 连接被掐）。这不是认证问题，
token 是有效的 —— 加一个 5 次重试循环即可，别急着换 token。
第 21 轮和第 23 轮都是首次抖动、重试成功。

## 插件开关日志

谁停了 bot、谁开了 bot，查 `/home/deck/homebrew/logs/BJBot/*.log`，里面会写
`stop rc=0` / `start rc=0`；`journalctl -u plugin_loader` 里也有同名行。
`main.py` 的 `_unload` 只打一行日志、不停止正在跑的 bot，前端 `useEffect` 只
refresh、不会自动开 bot ⇒ 出现 start/stop 一定是人在面板上按的。

## 版本与发布纪律

版本号唯一来源是 `decky-plugin/BJBot/plugin.json`。但 Decky 的版本显示读的是
`package.json`，所以两个文件必须都同步（实测 plugin.json 还是 0.2.9、
package.json 已是 0.2.10 时，日志报的是 `Loaded BJBot (v0.2.10)`）。
已发布 Release 的资产不覆盖、不 force-push。打包用 `git archive`
（`HEAD` / `HEAD:bot` / `HEAD:decky-plugin/BJBot`），自动排除 `.git` 与 `__pycache__`；
zip 里要保留一层插件目录。提交粒度：功能提交只动代码，release 提交只动版本号两文件。
正式版发布前先核 README 与代码是否一致 —— v2.0.0 前顺手改了 README 四处与代码
对不上的地方，那四处偏差已经错了十几轮没人发现。
