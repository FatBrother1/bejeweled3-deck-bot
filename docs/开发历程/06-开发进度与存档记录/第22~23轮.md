# 第 22~23 轮

## 第 22 轮（2026-09-27）：抓帧兜底修复

用户原话「修复啊！！！」。这一轮同时定了一条纪律，优先级很高：像「bot 已经瞎了、恢复动作」这种事，
不要再列进待确认清单。我当时把「加一层抓帧降级」写成了「不在点名范围、我没动」，用户回的是
「这种事还需要我确认吗？我不确认 bot 不就永远瞎了，修复啊！！！」
⇒ 恢复性/运维性动作（让 bot 重新能跑、把挂住的进程救回来）默认直接做，
只有「改变行为的产品决策」才需要确认。

现象：13:34:14 起日志每约 10 秒一条 `抓帧失败: None/eof`，守护一直拉起 bot、bot 一起来就死。
查证结果是游戏进程 Sep 25 起没重启过；`pw-dump` 里一个 `Video` 类节点都没有
（`pw-cli info 93` 报 no global）；但 `gamescopectl screenshot` 仍能抓帧 ⇒ 画面在，
只是 PipeWire 那条路断了。

三个洞（第一个是当天撞上的，后两个是翻代码翻出来的）：

1. `capture_pw.py` 里 `path=93` 写死，且只在启动判一次，拿不到首帧就 `return`（进程退出）。
2. `PwCapture.get()` 超时后返回「最后一帧」而不是 None ⇒ 运行中途断流时画面冻住、
   bot 以为游戏暂停，「拿不到帧就退兜底」永远不触发。
3. 退到兜底后永远回不来。

另外，`cap2.py` 里本来就有「PipeWire 优先、失败退 gamescopectl」，`poker.py`/`which_mode.py`
早在用它，只有引擎没用它。

改动（4 个文件加 1 个新测试）：`capture_pw.py` 加 `find_video_node()`（按
`media.class=="Video/Source"` 从 `pw-dump` 找节点、点名 gamescope 的优先，找不到才退回 93）
加 `PwCapture(path=None)` 自动发现加 `start(wait=)`；`cap2.py` 重写（运行中检测 err、线程退出、
连续 5 次无新帧就切兜底并丢掉那帧旧画面；兜底路径每 60 秒回试 PipeWire，回来自动切回 90fps；
新增 `start()/backend/err/log`）；`bot_v6.py` 改用 `cap2.Cap` 并打印抓帧后端；
`install.sh` 补 `cap2.py`/`reader_mem.py`/`which_mode.py` 三个漏掉的硬依赖；
`test_capture.py` 新增 40 项（numpy/PIL 用假件顶掉、本机可跑）。

验证：离线 `test_capture` 40/40；Deck 受控端到端（把 `PwCapture` 换成永远起不来的桩）走通
`后端 gamescopectl → start() True → 4 秒 11 帧真画面 → 放回 PipeWire → 回试后自动切回 PipeWire(90fps)`；
真实现场 14:39:25 游戏重启（PID 60620→4349）后节点回来，新代码打
`抓帧: PipeWire 节点 93 可用（90fps）` 加 `抓帧后端: PipeWire`，之后不再抓帧失败。
Deck 全套 `test_capture 40/40 + test_poker 40/40 + test_modes 40/40 + test_hyper 30/30 + test_settle 70/70`。

新事实：`pipewiresrc path=9999`（不存在的节点号）照样能连上默认节点出帧（4 秒 361 帧）
⇒ 节点号不是「能不能出帧」的唯一变量，真正必失败的是「一个视频源都没有」；
写死 93 的锅是「节点号会变」，13:34 那次的主因是节点整条消失。

发布：功能提交 `3c90ed8`（+467/−9，含 `cap2.py`/`test_capture.py` 新增进仓库）加 release 提交
`ced5e96`（0.2.19→0.2.20），推 `81b0649..ced5e96`，Release v0.2.20（id 397540352）三资产；
Deck 插件同步已于 14:58:44 完成（`Loaded BJBot (v0.2.20)`、16 插件）。

收尾时那 2 条「抓帧失败」是 grep 假阳性：`awk '$1>"14:39:00"'` 命中的是 Python traceback 打出的
源码行（`if not cap.start(): log("抓帧失败: %s" ...)`，首字段是 `if`，字符串比较 `"if">"14:39:00"` 成立）；
真日志最后一条是 14:32:28，之后干净 ⇒ 教训是按时间戳过滤日志必须排除没有时间戳前缀的 traceback 源码行。
Deck 回来后 bot 在跑、走 PipeWire，日志停在 `读不到棋盘(bad=99)`（游戏重启后停在菜单没进对局，
属正常等待）。报告在 `输出/2026-09-26/bejeweled/抓帧兜底/`。

## 第 23 轮（2026-09-27）：正式版 v2.0.0 发布

用户原话：「本插件开发告一段落，形成一个正式版的版本发到GitHub上」。

版本号是用户拍板的。GitHub 上已经有早期乱发的 `v1.0.0`/`v1.1.0`/`v1.2.0`，三种走法
（删掉旧三个后发 1.0.0 / 用 1.3.0 / 不动旧资产、直接发 2.0.0）都问过用户，用户选 v2.0.0，
不动任何已发布资产。

发布事实：docs 提交 `8ece7ed`（只动 `README.md`，+32/−7）加 release 提交 `0e0753a`
（只动版本号两个文件 0.2.20→2.0.0），推 `ced5e96..0e0753a`（首次 GnuTLS 抖动、重试成功）。
Release v2.0.0（id 397545869，GitHub 的 latest 已指向它）三资产：
`bejeweled3-deck-bot-2.0.0.zip` 1519382 / `bejeweled-bot-2.0.0.zip` 127294 / `BJBot-2.0.0.zip` 1320730
（⚠️ 这三个字节数是发布当刻的；2026-09-27 已覆盖成 1523829 / 131733 / 1320730），
均过 `testzip()`、无 `__pycache__`。Deck 插件已同步 v2.0.0（15:10:39，日志 `Loaded BJBot (v2.0.0)`，
属主不变，同步时 bot 仍在跑 PID 7107）。

顺手改了既有资产 `README.md`（已在报告开头前置声明），四处与代码对不上：
①「用法」补 `run2.sh modes` / `run <模式> [步数]`；②「支持的游戏模式」从「normal/poker 两个、
bot 死盯一个花色凑同花」改成八个模式加 auto 识别顺序、每模式一份 `board*.json`、牌局牌型阶梯
（实测数据原样保留）；③「装不上的话」删掉「换机器要改 `path=93`」（现已自动发现加兜底）；
④「版本号」补 2.0.0 与跳过 1.x 的原因。正文其它段落一字未动，docs 单独成一个提交。

给以后的经验：正式版发布前应当先核一遍 README 与代码是否一致——这次四处偏差里有两处
（`--mode normal` 只有两个模式、`path=93` 要手改）已经错了十几轮没人发现，
因为每轮只提交点名的代码，没人回头读 README。报告在 `输出/2026-09-26/bejeweled/正式版/`。
