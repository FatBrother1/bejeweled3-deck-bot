## 09-24

### 首轮：方案 A 跑通（外置视觉闭环）

- 要解决的问题：让 bot 在 Steam Deck 上自动玩 Bejeweled 3，不改游戏文件、不做注入。
- 做法：PipeWire 抓帧（gamescope 的 `Video/Source` 节点，`node.name=gamescope`，本次 `path=93`）
  + numpy 逐像素投票识别 + `solver_fast` 求解 + evdev UInput 模拟鼠标
  （VMouse2 相对移动、每步撞角归零）+ `watch2.py` 按需守护（`systemd-run --user` 临时单元，重启即失效）。
- 实测：抓帧 90.7 fps / 11 ms 一帧（`gamescopectl screenshot` 是 0.45 s/帧、2.2 fps，瓶颈在 PNG 编码）；
  实盘 90 步跨 4 关、0→34,110 分、0.8 步/秒。
- 结论一：原以为要写 DLL 注入（DXVK 定制）才能拿到的速度，用现成 PipeWire 就够，零注入。
- 结论二：「画面两帧识别相同」不能当棋盘静止判据（连消和道具自播动画会造成假静止，bot 抢在动画中出手、
  交换被吃掉），改成像素级帧间差 <2.0 连续 4 帧；实测静止 p90=0.44、动画中 p90=10.73。
- 输入对照实验：拖动（down 后立刻 move）4/4 采用；加等待反而 2/4；位置跟踪静默失效，弃用。
  补丁核实：`main.pak`/`Bejeweled3.exe`/`compat.cfg`/`使用说明.txt` 与 7z 内条目大小日期逐一吻合，
  确已应用，不需要重标定。产物在 `输出/2026-09-24/bejeweled/`。

### 内存读取路线（P2）

  ⇒ hook D3D9 与「排队连发」都没有收益空间。

### 修改器（Deck 原生版）与进度存档 2

- 用户原始诉求是「KelSat 修改器一点反应都没有，能修好吗」。结论：修不好，代际不兼容——
  它按进程名找 `popcapgame1.exe`（2010-12-11 v1.0.8.6128），实际跑的是 Steam 版 `Bejeweled3.exe`；
  用 `popcapgame1.exe` 启动游戏会随即退出；它自身带 ASPack 壳、快捷键是 NUMPAD0~9。
- 自造替代品：分数定位。用户给的方法（多走几步让分数变大再搜）实测搜 400 有 1603 个候选、
  搜 10940 剩 14 个、搜 12110 剩 4 个。
- 分数结构：权威源 + 相距 `0x40` 的同步副本；分数总落在 `0x0f400000` 起 64KB 窗口内
  （三次实测 `0x0f403bf0`/`0x0f405aec`/`0x0f405ee4`）⇒ Wine 确定性映射、跨重启位置稳定，
  扫描量缩小 17000 倍。自动定位三步：扫 64KB 找「相距 0x40 且值相同」的成对（104 个）→
  走一步找「跟着涨且副本同步」（收敛到 1 个）→ 写独特值看画面变。
- 进度 2/9：设置分数（写 2468013 → 画面 2,468,013 一分不差）、立即完成当前等级（连过 3 关，第 3→6 关）。
  无限时间没做完：闪电每局只有 1 分钟来不及定位；11 个「写后保持」候选写 600 秒画面纹丝不动；
  画面永远在动导致差异判据大量误报。
- 教训：进程名对不上是修改器失效的常见根因；CheatEngine 两步法的过滤必须筛「精确等于新读数」；
  写入验证必须看画面，只看内存会假阳性；分类判据优于差异判据。

### 路线 C（攻动画瓶颈）：已证伪

- 要解决的问题：游戏自身消除动画是方案 A 的架构天花板，能不能用时间加速把它压下去。
- 打通的技术能力：解析 PE 导入表 + 读内存 IAT；`/proc/pid/mem` 可以写只读代码段
  （`process_vm_writev` 不行）；游戏 `.data` 之后的 `0x008bd000-0x008d6000` 是 rwxp 代码洞；
  写机器码 + 改 IAT 重定向已验证；定位了 8 个时间函数的 IAT。
- 零风险频率统计（只加计数器、行为不变）：`timeGetTime` 1131 次/秒（主循环轮询）、
  `GetTickCount` 180.6、`GetSystemTimeAsFileTime` 100、`Sleep` 98.8（约每 10 ms 节流）、
  `QueryPerformanceCounter` 0、`GetLocalTime` 0 ⇒ 主循环 = `timeGetTime` 高频轮询 + `Sleep(10)` 节流，
  `timeGetTime` 不是动画进度驱动者。
- 决定性 A/B：无加速单步 9.877 秒 vs SpeedHack 2 倍 9.877 秒，加速比 1.00x ⇒ 时间加速对动画完全无效。
- 两次卡死事故：只 hook 单个 `Sleep` 且用 8 倍激进 → 画面卡死、回滚 IAT 仍不恢复；
  第二次 BASE 基准用错（拿 Linux 系统时间当基准）→ 进棋盘时卡死。教训是 hook 前必须先做频率统计、
  回滚内存不等于恢复运行、hook 系统调用风险远高于 hook 纯查询函数。
- 收尾状态：IAT 全部还原、代码洞清空、游戏进程已结束、未修改任何文件，回滚无需操作。

### 动画变量逆向 Phase 0~3：方法有效，变量未找到

- 对用户原方案的修正：「每 10~20ms 全量快照」不可行（全量 1155.6 MB 实测 1.032 秒，差 50~100 倍，
  会把「采样率不足」误读成「没有动画变量」）⇒ 改成两阶段：静止时全量快照 A → 交换后逐区读 B 即时差分，
  热点 1206 页 / 394 区间 / 4.71 MB，之后只轮询这 4.71 MB = 13.76 ms/轮，1.05 秒动画能抓 146 轮；
  并加了「采样率自检」（轮数 <20 判结论不可用）。
- Phase 2 的方法学改进：只用「动画期变化多」筛选会把背景动画选进来
  （`0x0f9b6570` 动画期 266 次变化、静止期也有 47 次，比例与持续时间一致）⇒ 必须加「静止期不变」反向条件，
  加完得 50,567 个。
- Phase 3 最有力的发现：22,301 个候选里只有 16 个被代码绝对引用（0.07%）⇒ 游戏变量主要走
  「基址寄存器+偏移」而不是绝对地址，这与「棋盘是指针对象图」是两条独立路径指向同一结论。
- 找「动画计数器」波形命中 6 个，每个做 3 次独立交换复现后全部排除——它们都是只增不减的累计计数器，
  不是每轮从相同值开始到相同值结束的动画进度。
- 结论：动画控制变量未找到，但这个否定结论可信、不是假阴性；全程只读、零事故。
  下一步建议是转闪电模式或补完修改器。产物在 `输出/2026-09-24/bejeweled/动画变量逆向-Phase1至3实测报告.md` 与 `phase1/`。

### 动画时长重测：推翻「1900ms / 96.7%」前提

- 单步耗时剖析（10 步）：vision 2146.9 ms（32.8%）、quiet_wait 2353.3 ms（35.9%）、
  post_wait 1718.3 ms（26.2%）、grab/drag/solve 335.1 ms，合计 6553.6 ms。
- 关键发现：quiet_wait 里 vision 占 2147 ms（91%）——原 `wait_quiet` 在每一帧都调 `read_grid_np`
  （50 ms/次），一帧等待要处理 40+ 帧 ⇒「动画占 96.7%」是测量假象，那 2100 ms 是自己的识别开销。
- 干净测量（`measure_anim2.py`）：拖动 182 ms、首次运动 472 ms、末次运动 535 ms（动画真实时长）
  ⇒ 单步理论下限 717 ms、上限 1.39 步/秒。
- 优化：`reader_fast.py` 把静止判定与识别解耦，静止判定只用降采样像素差（约 1 ms/帧），
  确认静止后只识别一次 ⇒ 每步约 2000 ms → 834 ms、0.50~0.62 → 1.18 步/秒（峰值 1.90），
  每步识别次数约 40 → 2.0。
- 过程踩坑：静止判定 40 ms 短于动画 535 ms（加 `min_still_ms=260`）；重写时漏了「拉黑」机制；
  每次新建 VMouse2 有 0.4 s sleep；用 xdotool 时误关了游戏全屏（用户重新打开）。
- 遗留：输入落点漂移没解决——后来证明是绝对定位设备 EV_ABS 不生效，不是鼠标加速。

### 单步 720ms 达成（主记忆标为 Round 3）

- 100 步长跑：1.10 步/秒（每步 910 ms），短跑峰值 1.39（720 ms），有效 97/100，
  分数 426950→438510（真实 +11,560），分/秒 119.9。对照物理下限 717 ms ⇒ 已到极限。

### 09-24 深夜：牌局模式（Poker）攻破

- 三条机制：①出牌规则（实测，官方 wiki 未写明）一次消除给一张牌、花色等于这次消除的「多数色」

### 第 13 轮：模式显示全错

- 用户报「打开钻石矿显示闪电、经典显示菜单、选模式显示蝴蝶」，三条全部复现定位。
- 根因一：`MEM_MAP` 错标 + 漏项。`[Board+0x0]` 是棋盘对象的 vtable 指针，点进某模式立刻变成该模式的值，
  菜单/加载中没有棋盘对象、读不到。全量重测（每条对画面核过）：`0x86511C` 经典（旧表标 menu）、
  `0x866B6C` 禅意、`0x8665C4` 闪电、`0x867D0C` 蝴蝶、`0x8685EC` 冰风暴（旧表标 diamond）、
  `0x8657D4` 钻石矿（旧表缺失）。
- 根因二：插件实际跑的 `which_mode.py` 是旧版——`main.py` 里 `HOME="/home/deck"` ⇒
  `MODE_SCRIPT=/home/deck/which_mode.py`，而那一份没有泥土兜底，于是钻石矿掉进图像指纹、撞上
  `refs/mode_lightning.png` 显示闪电；模式树（无棋盘对象）也掉进图像指纹、撞上蝴蝶。
- 修复：`MEM_MAP` 只留六个对着画面核过的值（没核过的 `0x869364` 删掉）；新增分支
  「读不到棋盘对象 = 菜单/加载中 → 直接报菜单（`src="noboard"`）」，不再交给图像猜；
  游戏没跑报「未知」(`nogame`)；泥土 ≥4 报钻石矿；图像降级为最后兜底；两份文件都同步。
- 验证四态实测：冰风暴→冰风暴、模式树→菜单(noboard)、经典→经典、钻石矿→钻石矿，全过。
- 方法论收获：改前先确认「哪份文件真的在跑」（读 `main.py` 的 `HOME` 常量，别按直觉）；
  「没有信号」要如实报「不知道」，别拿去喂下一个不可靠的判据；映射表只放对着画面核过的值

### 第 14 轮：蝴蝶模式优先消蝴蝶（挂起存档）

- 用户需求：蝴蝶从底下出现、飞到顶就结束，要优先消掉蝴蝶。本轮把「能认出蝴蝶」这个前提打通了，
  但功能还没实现（用户中途喊挂起）。
- 关键发现一：蝴蝶宝石 = 状态位 `128`（0x80），在 `Piece+0x228`。实测抓到 4 只 `(3,1)(4,6)(6,2)(7,6)`
  全在棋盘下半部，裁图放大目视核实四张全是带蝴蝶翅膀的宝石。
- 关键发现二：游戏窗口失去焦点会被暂停（这次「bot 卡死」的主因）——棋盘冻住、蝴蝶不飞、所有拖动全被拒；
  点一下游戏内「菜单」抢回焦点，游戏立刻继续。教训是排查「点了没反应」先确认游戏有没有焦点，
  别先怀疑几何/坐标（这次为此浪费了十几轮，还差点把「几何偏移」的假结论写进代码）。
- 关键发现三：上一轮的「全 ban 解禁」兜底有 bug——它用掩码后的 `g` 重算，而掩码 `?` 才是杀死候选的元凶。
  实测 08:44 起只剩 3 个合法走法，三个全涉及被掩码的 (1,1) ⇒ 0 候选 ⇒ bot 趴窝 15 分钟。
  修法是这一层也必须用 `g_raw`（并 `blacklist.clear()`）。
- 关键发现四：蝴蝶模式几何存疑未定论——一次控制变量 A/B（同一走法只改 y0）显示 `board.json`(y0=79) 被拒、
  y0≈104 被接受（变化 8 格），但后续扫描时游戏已暂停 ⇒ 那批「全被拒」数据作废、结论不算数，
  等游戏有焦点时重做。
- 待办按序：P1 蝴蝶优先逻辑（`reader_mem` 收 `extra["butterflies"]` → `rank_moves(butterflies=)`
  按「消掉几只 + 离顶行多近」加权）；P2 修 `g`→`g_raw` 的兜底 bug；P3 游戏有焦点时重测蝴蝶几何；
  P4 bot 在 08:58:54 无声死亡原因未明（日志停在「死局(660)」、无 traceback、守护没拉起）。
  挂起时 bot 已停，仓库干净、HEAD `132f0f5`（= v0.2.13），Deck 运行文件与仓库一致。
