## 2026-09-24 · 第一阶段：基础方案打底

### 已跑通的能力

- **PipeWire 抓帧**：90.7 fps（11.07 ms/帧）
  - 对比：`gamescopectl screenshot` 只有 **2.2 fps**（瓶颈在 PNG 编码）
- **内存访问**：`process_vm_readv` 达 1463 MB/s（同 uid，无需 root）
- **输入**：uinput 虚拟鼠标（`vmouse2.py`）

### 踩坑记录

| 坑 | 现象 | 原因 |
|---|---|---|
| 1 | `gamescopectl` 写 `/tmp` 静默失败 | gamescope 有独立 mount namespace |
| 2 | 抓到半截 PNG | 需 `Image.verify()` + 重试 |
| 3 | `fdsink` 短读 | 必须累积到完整帧 |
| 4 | `sudo` 后抓帧失败 | `sudo` 清掉 `XDG_RUNTIME_DIR` |
| 5 | `pkill -f` 自杀 | SSH 命令行匹配到自身，需 `[x]` 转义 |
| 6 | 火焰宝石读成白色 | 火焰在**外圈**、本体紫在中心 ⇒ 改高饱和像素投票 |
| 7 | `xdotool getmouselocation` 不可靠 | gamescope 下位置跟踪失效 |

### ★ 重要认知：不能用"两帧识别相同"判静止

连消和道具自播动画会造成**假静止** ⇒ bot 抢在动画中出手 ⇒ 交换被吃掉。

实测：静止帧间差 p90 = **0.44**，动画 p90 = **10.73**
⇒ 改用**像素级帧间差 < 2.0 连续 4 帧**。

### 输入方式的对照实验

| 方式 | 成功率 |
|---|---|
| 拖动（down 后**立刻** move） | **4/4** |
| 拖动（加等待） | 2/4 |
| 位置跟踪 | 静默失效 |

⇒ 采用**每步撞角归零**（代价仅 0.02 s）。

## 2026-09-24 · 第二阶段：三消逻辑优化

### solver_pro vs solver_fast

| 指标 | solver_fast | solver_pro |
|---|---|---|
| 均分/步 | 320 | **695（2.17×）** |
| 分/秒 | 181 | **325（1.75×）** |
| ≥1000 分的步 | 1 | **6** |

### ★ 重要发现：得分不可预测

- 预测/实际相关性仅 **0.083**（Monte-Carlo 也才 0.106）
- 292 个真实候选：90% 只消 3 格、80% 只连消 1 层
- 期望分区间 50–342（中位 67），但实际出现 500 / 880 / 3450

**调参尝试失败**：6 组权重 × 2 轮 ⇒ **同一组在两轮间波动 10 倍**
（spec_hi 16 vs 156）⇒ 权重被噪声淹没。`w_special=30` 明显有害（16 分/秒）。

### 超立方体误判事故

**现象**：紫色火焰宝石 `sat_med=0.47` vs 真超立方体 `sat_med=0.39` —— 太接近
⇒ 误判为超立方体 ⇒ solver 反复选非法交换 ⇒ **15 步 0 分**。

**尝试过的特征全失败**：金箔暗斑（被棋盘背景污染）、核心色暖度（超立方体 +50 vs 紫火焰 +56）。

**结论**：单阈值无法分离 ⇒ 回退原始 `vision_np`（64/64 准确）+ 保留拉黑兜底。

## 2026-09-24 · 第三阶段：动画瓶颈攻关（目标轮）

### 目标
"单步 1975 ms（动画占 96.7%）→ 降到 500 ms 级"

### ★★ 最大发现：目标前提本身就是错的

逐阶段剖析（`tools/profile_step.py`，10 步平均）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **vision（识别）** | **2146.9 ms** | **32.8%** |
| quiet_wait | 2353.3 ms | 35.9% |
| post_wait | 1718.3 ms | 26.2% |
| grab/drag/solve | 335.1 ms | 5.1% |
| **合计** | **6553.6 ms** | 100% |

**`quiet_wait`(2353 ms) 里 vision 占 2147 ms（91%）** ——
因为原 `wait_quiet` 在**每一帧**都调 `read_grid_np`（50 ms/次）。

> **那 2.1 秒与游戏动画毫无关系，纯粹是自己的代码开销。**

### 干净测量动画（`tools/measure_anim2.py`）

| 交换 | 拖动 | 首次运动 | 末次运动 |
|---|---|---|---|
| (4,2)↔(4,3) | 182 ms | 472 ms | **472 ms** |
| (4,0)↔(4,1) | 183 ms | 478 ms | **589 ms** |
| (4,2)↔(4,3) | 181 ms | 182 ms | **195 ms** |
| (4,2)↔(4,3) | 183 ms | 491 ms | **535 ms** |

**中位 535 ms** ⇒ 单步下限 **717 ms** ⇒ 上限 **1.39 步/秒**
⇒ **"500 ms 级"物理上不可达**。

### 优化：解耦静止判定与识别

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 每步耗时 | ~2000 ms | **834 ms** |
| 步/秒 | 0.50–0.62 | **1.18** |
| 每步识别次数 | ~40 | **2.0** |

### 踩坑

| 坑 | 现象 | 修法 |
|---|---|---|
| 静止判定太快（40 ms） | 抢在动画前出手 | 加 `min_still_ms=260` + 运动感知 |
| 漏"拉黑"机制 | 同一招重复 30+ 次 | 恢复拉黑 |
| 每次新建鼠标（+0.4 s） | 额外开销 | 设备常驻 |
| 输入落点漂移 | bot 反复走同一招、0 分 | 见下（是绝对定位设备的锅） |

### ★ 否证：绝对定位鼠标不生效

**做法**：用 `EV_ABS` 绝对坐标 uinput，试图绕过鼠标加速。

**结果**：**游戏收到点击并高亮格子，但交换不被接受**（棋盘 0 变化）。

**对照**：同场景 `VMouse2`（`EV_REL` 相对 + 撞角归零）**30/30 成功**。

⇒ **本 gamescope 环境必须用相对移动。**

（这解释了"落点漂移"的幻觉 —— 其实是我的绝对定位设备不work。）

## 2026-09-24 · 第四阶段：pending 优化与目标达成

### pending 复用

**问题**：每步都重新"等交换前静止"，但上一步已确认过静止。

| 组 | 步/秒 | 每步 | 等待 | 识别 | 有效 |
|---|---|---|---|---|---|
| A 无 pending | 0.48 | 2080 ms | **1523 ms** | 154 ms | 30/30 |
| B **有 pending** | **1.11** | 900 ms | **642 ms** | 62 ms | 30/30 |
| B2 | **1.39** | **720 ms** | **458 ms** | 70 ms | 30/30 |

### ★★ 发现"假速度"陷阱

B2 跑到 **1.39 步/秒**（720 ms/步）看着最漂亮，但 **分/秒只有 69.4，低于基线**。

**原因**：等待压到 458 ms，**部分步抢在动画结算前出手** ⇒ 步数虚高、得分虚低。

> **裁定速度优化必须用「分/秒」（净得分/秒）。**

### 静止窗裁定（40 步/组）

| 组 | 步/秒 | 等待 | 有效 | **分/秒** |
|---|---|---|---|---|
| 无 pending | 0.25 | 2583 ms | 98% | 26.2 |
| **s250 ★** | **0.86** | 888 ms | **98%** | **168.3** |
| s350 | 0.79 | 989 ms | 95% | 124.4 |
| s450 | 0.80 | 969 ms | 92% | 58.6 |

### 100 步长跑（两轮）

| 运行 | 步/秒 | 每步 | 有效 | 净得分 | 分/秒 |
|---|---|---|---|---|---|
| 上轮 | 1.10 | 910 ms | 97/100 | +11,560 | 119.9 |
| **本轮** | **0.87** | **1155 ms** | **98/100** | **+14,900** | **124.7** |

**单步 3940 ms → 1155 ms（3.4×）；分/秒 26.2 → 168.3（6.4×）。**

## 2026-09-24 · 第五阶段：游戏模式开关（Decky 插件）

### 起因

用户提问：**"Steam Deck 游戏模式怎么运行命令，你那个开关形同虚设"**
—— 完全正确：**游戏模式没有终端**，`./run2.sh on` 只能桌面模式/SSH 用。

### ★★ 重大事故：手写 bundle 把 Decky 前端搞崩

**我的错误做法**：手写 `dist/index.js`，**没有编译**，凭目测**猜**全局变量：
```js
const DFL = window.DFL || window.DFL_;   // ← 猜的，不存在
```

**真相**：`DFL` 不是全局变量，是 rollup 打包 `@decky/ui` 后的**局部绑定名**。
⇒ `DFL` 为 `undefined` ⇒ `DFL.definePlugin()` 抛异常
⇒ **整个 QAM 面板渲染失败，连插件商城也打不开**（用户拍照反馈）。

**★ 关键误导**：加载日志显示的是"成功"：
```
found plugin: BJBot
Loaded BJBot (v0.1.0)
```
**这只证明后端起来了**；前端 bundle 的错要到 Steam UI 真正渲染该面板时才暴露。

**处置**：立即移出插件 + 重启 loader + 按健康清单逐项核对（15 插件恢复、内存正常）。
**没有强杀 PluginLoader**（会导致插件风暴 → 内存吃爆 → 全机黑屏）。

### 正规重建

| 项 | v0.1.0（崩了） | v0.2.0+ |
|---|---|---|
| 前端 | **手写** dist | **`src/index.tsx` 源码** |
| 构建 | **无** | **`@decky/rollup`** |
| Decky API | 猜 `window.DFL` | `import { definePlugin } from "@decky/ui"` |
| 隔离验证 | **无** | **`verify.mjs` 6 项** |

**又踩两个坑**：
- **本容器是 arm64** ⇒ `@rollup/rollup-linux-x64-gnu` 装不上 ⇒ 换 `arm64-gnu`
- **`jsx` 必须设 `"react"`（classic）** ⇒ 设成 `react-jsx` 会引入 `SP_JSX`
  （Decky 不注入的全局，装载即崩）

### v0.2.0 上线后又发现 bash 崩溃

用户实测：**面板渲染完全正常**（前端过关了），但点「开启 bot」报错：
```
/bin/bash: symbol lookup error: undefined symbol: rl_trim_arg_from_keyseq
```

**根因**：Decky 用 PyInstaller 打包，把解包目录注入 `LD_LIBRARY_PATH`：
```
实测: LD_LIBRARY_PATH=/tmp/_MEIPmBEEx
$ LD_LIBRARY_PATH=/tmp/_MEIPmBEEx /bin/bash -c "echo ok"
  symbol lookup error: rl_trim_arg_from_keyseq      ← 复现
$ LD_LIBRARY_PATH="" /bin/bash -c "echo ok"
  ok                                                ← 清空即正常
```

**修法**：`main.py` 的 `_env()` 里 `env["LD_LIBRARY_PATH"] = ""`
（这个处理方式是从参考项目 `decky-wmsxwd` 的源码学到的。）

### ★ 我的一个错误判断（已更正）

我看到 bot 日志里大量 `实际=0`，就推断"**bot 盲点击误触进了牌局模式**"。
**用户澄清：是他自己进去的。**

**教训**：不要从"异常日志"倒推"必然是我的代码有问题"，先问清用户操作。
相关记录已从文档中更正，并保留在此作为教训。

## 方法论沉淀

1. **"每帧都识别"是最容易犯的性能错误**
2. **裁定速度必须看有效吞吐（分/秒），否则会优化出假速度**
3. **物理下限要单独测** —— 否则不知道"再快就是丢步"
4. **目标的前提也要验证** —— 本项目最大的发现就是前提错了
5. **否定性结论同样有价值**
6. **改系统级组件前先隔离验证**
7. **日志"成功"不等于功能可用**
8. **不要从异常日志倒推代码有问题，先问清用户操作**
