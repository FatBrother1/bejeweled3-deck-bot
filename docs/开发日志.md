# 开发日志

按时间顺序记的，包括做错的判断和搞出来的事故。
写这个是为了让人看到过程，而不是只有一个漂亮的结果。

## 第一步，把基础跑通

PipeWire 抓帧能到 90.7 帧每秒，一帧 11 毫秒。作为对比，Steam 自带的
`gamescopectl screenshot` 只有 2.2 帧，瓶颈在 PNG 编码上，一帧要 0.45 秒。

内存读取用 `process_vm_readv`，实测 1463 MB/s，同一个 uid 不需要 root。

输入用 uinput 虚拟鼠标。

踩了一堆坑：

`gamescopectl` 写不进 `/tmp`，因为 gamescope 有独立的 mount namespace，
写失败还不报错，静默返回成功。

抓到的 PNG 经常是半截的，得用 `Image.verify()` 检查再重试。

`fdsink` 会短读，必须攒够一整帧。

用了 sudo 之后抓帧就废了，因为 sudo 会清掉 `XDG_RUNTIME_DIR`。

`pkill -f "某个模式"` 在 SSH 里会把自己杀了，因为命令行自己也匹配这个模式，
得用 `[x]` 这种写法绕开。

火焰宝石老是读成白色。后来发现火焰在外圈，本体紫色在中心，所以边缘环和整格
投票都会判错。改成按高饱和像素投票就好了。

`xdotool getmouselocation` 在 gamescope 下面不靠谱，位置跟踪会静默失效。

### 一个重要的认知

不能拿"两帧识别结果一样"来判断棋盘静止了。连消和道具自播动画会造成假静止，
bot 就会抢在动画中间出手，交换被游戏吃掉。

实测静止时帧间差 p90 是 0.44，动画时是 10.73。所以改成像素级帧间差小于 2.0
连续四帧才算静止。

### 输入方式的对照实验

| 方式 | 成功率 |
|---|---|
| 拖动，按下之后立刻移动 | 4/4 |
| 拖动，中间加等待 | 2/4 |
| 位置跟踪 | 静默失效 |

所以用了每步撞角归零，代价只有 0.02 秒。

## 第二步，优化三消逻辑

`solver_pro` 比 `solver_fast` 强不少，均分 695 对 320，分/秒 325 对 181。

但有个发现：得分基本预测不了。预测和实际的相关性只有 0.083，
用蒙特卡洛也就 0.106。292 个真实候选里 90% 只消三格，80% 只连消一层。
期望分中位数 67，可实际跑出过 880 和 3450。

调参也试了，六组权重各跑两轮，同一组两次之间差十倍，说明权重完全被噪声淹没。
`w_special=30` 明显有害，只有 16 分/秒。

### 超立方体误判

紫色火焰宝石的 `sat_med` 是 0.47，真超立方体是 0.39，太接近了，经常认错。
认错的后果是求解器反复选一个非法交换，实测十五步零分。

试过几种特征都不行。金箔暗斑会被棋盘背景污染，核心色暖度也是超立方体 +50
对紫火焰 +56，分不开。

最后放弃单阈值判别，回到原来的识别，加上拉黑机制兜底：同一格连着三次没效果
就不用它了。

## 第三步，攻动画瓶颈

目标写的是"单步 1975 毫秒，动画占 96.7%，降到 500 毫秒级"。

### 结果发现目标的前提就是错的

逐阶段计时（十步平均）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 识别 | 2146.9 ms | 32.8% |
| 等静止 | 2353.3 ms | 35.9% |
| 交换后等待 | 1718.3 ms | 26.2% |
| 抓帧 / 拖动 / 求解 | 335.1 ms | 5.1% |
| 合计 | 6553.6 ms | 100% |

"等静止"这 2353 毫秒里，识别占了 2147 毫秒。因为原代码在每一帧都调用
`read_grid_np`，一次等待要处理四十多帧。

这两秒跟游戏动画没有任何关系，全是我自己的开销。

### 重新测动画到底多长

把识别摘出去之后测，六次结果里动画中位数是 535 毫秒。

加上拖动 182 毫秒，单步下限 717 毫秒，最快 1.39 步每秒。

所以"500 毫秒级"物理上做不到。

### 优化

先拆开静止判定和识别。等待的时候每帧只做像素差，确认静止了才认一次。

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 每步耗时 | 2000 ms | 834 ms |
| 步/秒 | 0.50 | 1.18 |
| 每步识别次数 | 约 40 | 2 |

然后是几个小修：

静止判定太快了（40 毫秒就成立，比动画启动还快），加了最小静止时长和运动感知。

重写的时候漏了拉黑机制，导致同一招重复三十多次，补回来了。

虚拟鼠标创建的时候有 0.4 秒 sleep，改成常驻。

### 绝对定位不生效

我想用 EV_ABS 绝对坐标绕开鼠标加速，结果游戏收到点击、格子也高亮了，
但交换就是不被接受。同一场景下相对移动是 30/30。

排查这个花了不少时间，因为现象看起来像"落点漂移"。

## 第四步，pending 优化

上一步结束的时候已经确认过静止了，这一步没必要再等一遍。

| 配置 | 步/秒 | 每步 | 等待 | 识别 | 有效 |
|---|---|---|---|---|---|
| 无 pending | 0.48 | 2080 ms | 1523 ms | 154 ms | 30/30 |
| 有 pending | 1.11 | 900 ms | 642 ms | 62 ms | 30/30 |
| 有 pending（第二轮） | 1.39 | 720 ms | 458 ms | 70 ms | 30/30 |

### 假速度

第三轮那个 1.39 步每秒看着最好，但分/秒只有 69.4，比基线还低。

等待压到 458 毫秒，动画没演完就出手了，交换被吃掉，步数虚高得分虚低。

之后就改用分/秒来判断，不看步/秒。

### 静止窗

四十步一组测下来，250 毫秒最好（分/秒 168.3）。350 是 124.4，450 掉到 58.6。
加大静止窗反而更差，多等没有换来更高命中率。

### 最终跑 100 步

两轮，都在 98% 左右的有效率，单步 1155 毫秒，分/秒 124.7。

## 第五步，做游戏模式开关

用户提了一句："Steam Deck 游戏模式怎么运行命令，你那个开关形同虚设"。
说得对，游戏模式没有终端，`./run2.sh on` 在那边根本用不了。

### 把 Decky 前端搞崩了

我想省事，手写了前端 bundle，没编译，凭感觉猜了个全局变量：

```js
const DFL = window.DFL || window.DFL_;   // 猜的，实际不存在
```

实际上 `DFL` 不是全局变量，是 rollup 打包 `@decky/ui` 之后的局部绑定名。
所以它是 undefined，`DFL.definePlugin()` 抛异常，整个 QAM 面板白屏，
插件商城也打不开。用户拍了照片发我。

最坑的是加载日志显示一切正常：

```
found plugin: BJBot
Loaded BJBot (v0.1.0)
```

这只说明后端起来了。前端的错要等 Steam UI 真正渲染面板才暴露。

处理方式是立刻把插件移出目录、重启 loader，然后按健康清单核对：
插件数恢复到 15，内存正常，swap 只有 4 MB。没有强杀 PluginLoader，
那个会导致插件风暴，报告里写着会全机黑屏。

### 重做

照着参考项目 `decky-wmsxwd` 的技术报告重新做：源码用 React 和 TypeScript 写，
用 `@decky/rollup` 构建，装之前先跑隔离验证。

又踩两个坑。构建环境是 arm64，x64 的 rollup 原生包装不上，报了 EBADPLATFORM。
另外 `tsconfig.json` 里 `jsx` 设成 `react-jsx` 会让产物引用 `SP_JSX`，
而 Decky 不注入这个全局，对比参考插件的产物只有 `SP_REACT` 才发现的。

### 修 bash 崩溃

v0.2.0 装上去之后面板渲染完全正常，前端算是过关了。但点"开启 bot"报错：

```
/bin/bash: symbol lookup error: undefined symbol: rl_trim_arg_from_keyseq
```

原因是 Decky 用 PyInstaller 打包，运行时把解包目录塞进 `LD_LIBRARY_PATH`，
里面有它自带的 libreadline，子进程调 bash 就加载到错的版本。

在 `_env()` 里清空 `LD_LIBRARY_PATH` 就好了。这个是参考项目源码里学到的。

### 我判断错了一次

我看到 bot 日志里一堆"实际=0"，就推断是 bot 误触进了牌局模式。
用户说不是，是他自己进去的。

教训是不要拿异常日志倒推自己的代码有问题，先问清楚用户做了什么。

### 交付

用户验收通过了。插件版本 0.2.1，插件数 16，游戏文件没动过。

## 被否掉的路线

| 路线 | 结论 | 依据 |
|---|---|---|
| SpeedHack 时间加速 | 证伪 | 两次搞崩游戏，修正后仍然零效果 |
| "动画占 96.7%" | 测量假象 | 那两秒是自己的识别开销，动画真实 535 毫秒 |
| 绝对定位鼠标 | 不生效 | 游戏收到点击但不接受交换 |
| 棋盘内存搜索 | 死路 | 五种方法零命中 |
| 自动标定 | 不可靠 | 覆盖率随背景变化，白天 0.912 夜间 0.568 |
| 动画变量逆向 | 未证伪但不需要 | 瓶颈不是动画 |
| 超立方体单阈值检测 | 不可行 | 紫火焰 0.47 对真超立方体 0.39，太近 |

## 攒下来的经验

每帧都识别是很容易犯的性能错误。

优化速度要看有效吞吐，只看步数会优化出假速度。

物理下限要单独测，不然不知道还差多少。

目标的前提也要验证，这个项目最大的发现就是前提本身错了。

否定的结论也有价值。

改系统级的东西前先在隔离环境跑。

日志显示成功不等于功能可用。

别拿异常日志倒推自己的代码有问题，先问用户。

## 2026-09-25 文档纠错：README 不再说"内存不碰"

1.1 版本起棋盘就是从内存读的（process_vm_readv，只读），但 README 和
bot/README 的开头还写着"内存也不碰"，读也是碰，这话有歧义。今天全部改成
"内存只读，从不写入"。

顺手改掉的还有三处过时说法：
- 流程图还画着"截屏→认棋盘"，现在棋盘来自内存，画面只用来判结算和识别模式；
- "像素差判静止 + 内存读棋盘"这句不对——那个混合版 wait_still_and_read 被
  同名的内存轮询版覆盖了，实际生效的是内存轮询（指纹+分数当运动信号）；
  过场动画冻结内存的坑靠结算画面判据兜底；
- 模型署名补上 glm-5.3-flash（闪电修复那几轮是它写的）。
