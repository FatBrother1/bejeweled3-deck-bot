# 性能优化：单步 3940 ms → 1155 ms

> 本文给出完整的**证据链**，每一步优化都有实测数据支撑。

---

## 摘要

| 指标 | 优化前 | 优化后 | 倍率 |
|---|---|---|---|
| **单步耗时** | 3940 ms | **1155 ms** | **3.4×** |
| **步/秒** | 0.25 | **0.87** | 3.5× |
| **分/秒（有效吞吐）** | 26.2 | **168.3** | **6.4×** |
| 每步识别次数 | ~40 | **2.0** | 20× |
| 有效率 | — | **98/100** | — |

**物理下限 717 ms（拖动 182 + 动画 535）⇒ 上限 1.39 步/秒。**

---

## 一、起点：一个错误的前提

原目标写着："单步 1975 ms，其中**动画占 1900 ms（96.7%）**"。

**这个前提是错的。** 逐阶段剖析结果：

```bash
python3 tools/profile_step.py     # 10 步平均
```

| 阶段 | 平均耗时 | 占比 |
|---|---|---|
| **vision（识别）** | **2146.9 ms** | **32.8%** |
| quiet_wait（等静止） | 2353.3 ms | 35.9% |
| post_wait（交换后等待） | 1718.3 ms | 26.2% |
| grab（抓帧） | 146.5 ms | 2.2% |
| drag（拖动） | 182.5 ms | 2.8% |
| solve（求解） | 6.1 ms | 0.1% |
| **合计** | **6553.6 ms** | 100% |

### ★ 关键观察

看 `quiet_wait`（2353 ms）里 **vision 占了 2147 ms（91%）**：

> **原 `wait_quiet` 在【每一帧】都调用 `read_grid_np`（50 ms/次）**，
> 一次等待要处理 40+ 帧 ⇒ **视觉开销累计 2147 ms/步**。

**这 2.1 秒与游戏动画毫无关系 —— 纯粹是自己的代码开销。**

---

## 二、真实动画时长（干净测量）

用 `tools/measure_anim2.py`（设备常驻 + 纯像素差轮询，**完全不调识别**）：

| 交换 | 拖动 | 首次运动 | 末次运动 | 结束 |
|---|---|---|---|---|
| (4,2)↔(4,3) | 182 ms | 472 ms | **472 ms** | 693 ms |
| (4,0)↔(4,1) | 183 ms | 478 ms | **589 ms** | 815 ms |
| (4,2)↔(4,3) | 181 ms | 182 ms | **195 ms** | 416 ms |
| (4,2)↔(4,3) | 183 ms | 491 ms | **535 ms** | 747 ms |
| (4,2)↔(4,3) | 181 ms | — | — | 4002 ms |
| (4,2)↔(4,3) | 182 ms | 150 ms | **622 ms** | 845 ms |

**中位**：拖动 **182 ms** / 首次运动 472 ms / 末次运动 **535 ms**

```
单步下限 = 拖动 182 + 动画 535 = 717 ms
⇒ 上限 = 1.39 步/秒
```

**⇒ "500 ms 级"物理上不可达**（除非不等结算，但那会丢步）。

## 三、五环优化

### 第 1 环：解耦静止判定与识别（最大收益）

**错误做法**：
```python
while not still:
    frame = grab()
    grid = read_grid_np(frame)     # ← 每帧都识别！50 ms/次
    if is_still(frame): break
```

**正确做法**：
```python
while not still:
    d = frame_diff_downsampled()   # ← 只要 1 ms，不调识别
    if d < thr: still_frames += 1
grid = read_grid_np(frame)         # ← 确认静止后只识别一次
```

| 指标 | 前 | 后 |
|---|---|---|
| 视觉开销/步 | 2147 ms | **62 ms** |
| 识别次数/步 | ~40 | **2.0** |

### 第 2 环：运动感知 + 静止窗

解耦后静止判定只要 40 ms，**远短于动画启动延迟** ⇒ bot 抢在动画前出手
⇒ 交换被吃掉 ⇒ 反复无效交换 ⇒ 盲点击落到菜单。

**规则**：先见运动（`d >= thr`）→ 再见静止，且**静止持续 ≥250 ms**。

### 第 3 环：拉黑机制

同一格连续 3 次无效交换 ⇒ 标记为 `?`，不再使用。

**背景**：曾出现同一招重复 30+ 次的死循环。

### 第 4 环：设备常驻

`VMouse2()` 构造里有 `time.sleep(0.4)`。
每步新建 = 每步多 400 ms ⇒ 改为**只创建一次**。

### 第 5 环：pending 复用（第二大收益）

**问题**：每步都重新"等交换前静止"，但**上一步结束时已确认过静止**。

| 组 | 步/秒 | 每步 | **等待** | 识别 | 有效 |
|---|---|---|---|---|---|
| A 无 pending | 0.48 | 2080 ms | **1523 ms** | 154 ms | 30/30 |
| B **有 pending** | **1.11** | 900 ms | **642 ms** | 62 ms | 30/30 |

**等待 1523 → 642 ms。**

## 四、★ 假速度陷阱（重要）

跑到 **1.39 步/秒**（720 ms/步）时，看起来最漂亮。但：

| 组 | 步/秒 | 每步 | 等待 | **分/秒** |
|---|---|---|---|---|
| P_off | 0.48 | 2080 ms | 1523 ms | 77.1 |
| P_on | 1.11 | 898 ms | 642 ms | 96.2 |
| **P_on2** | **1.39** | **720 ms** | **458 ms** | **69.4** ⚠️ |

**P_on2 步速最高，但分/秒反而最低** —— 因为等待压到 458 ms，
**部分步抢在动画结算前出手**，交换被吃掉 ⇒ 步数虚高、得分虚低。

> **裁定任何速度优化必须用「分/秒」（净得分/秒），不能只看步/秒。**

---

## 五、静止窗裁定

40 步/组，指标 = 分/秒：

| 组 | 步/秒 | 等待 | 有效 | **分/秒** |
|---|---|---|---|---|
| 无 pending | 0.25 | 2583 ms | 98% | 26.2 |
| **s250 ★最优** | **0.86** | 888 ms | **98%** | **168.3** |
| s350 | 0.79 | 989 ms | 95% | 124.4 |
| s450 | 0.80 | 969 ms | 92% | 58.6 |

**`--still-ms 250` 最优** —— 等待窗再加大反而劣化：
多等的时间**没有换来更高命中率**，只降低步速。

## 六、最终验证（100 步长跑）

| 运行 | 步/秒 | 每步 | 有效 | 净得分 | 分/秒 |
|---|---|---|---|---|---|
| 上轮 | 1.10 | 910 ms | 97/100 | +11,560 | 119.9 |
| **本轮** | **0.87** | **1155 ms** | **98/100** | **+14,900** | **124.7** |

**每步构成**：拖动 183 ms + 等待 872 ms + 识别 77 ms

对比物理下限 717 ms ⇒ **已达极限的 62%**（等待里含 250 ms 静默窗）。

## 七、复现方法

```bash
# 单步耗时剖析
python3 tools/profile_step.py

# 动画时长干净测量
python3 tools/measure_anim2.py

# 100 步长跑
cd bot && ./run2.sh play 100
```

测量脚本会输出：拖动 / 首次运动 / 末次运动 / 静止确认 各阶段耗时。

## 八、结论

1. **原目标的前提是错的** —— "动画占 96.7%" 实为识别开销
2. **单步 3940 → 1155 ms（3.4×）**，分/秒 **26.2 → 168.3（6.4×）**
3. **物理下限 717 ms**，已达极限
4. **再快就是假速度** —— 必须用分/秒裁定，不能只看步/秒
5. **不需要 SpeedHack** —— 瓶颈从来不是游戏动画
