# 单步从 3940 毫秒降到 1155 毫秒

每一步优化都有实测数据。所有脚本在 `tools/` 下面，可以自己复现。

## 结果

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 单步耗时 | 3940 ms | 1155 ms |
| 步/秒 | 0.25 | 0.87 |
| 分/秒 | 26.2 | 168.3 |
| 每步识别次数 | 约 40 | 2 |
| 有效率 | — | 98/100 |

单步快了 3.4 倍，分/秒快了 6.4 倍。

上限是每秒 1.39 步，也就是每步 717 毫秒，这个后面会说为什么。

## 一开始的假设是错的

原来的目标是"单步 1975 毫秒，动画占 1900 毫秒也就是 96.7%，降到 500 毫秒级"。

跑了一遍逐阶段计时（十步平均）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 识别 | 2146.9 ms | 32.8% |
| 等静止 | 2353.3 ms | 35.9% |
| 交换后等待 | 1718.3 ms | 26.2% |
| 抓帧 | 146.5 ms | 2.2% |
| 拖动 | 182.5 ms | 2.8% |
| 求解 | 6.1 ms | 0.1% |
| 合计 | 6553.6 ms | 100% |

第二行的"等静止"是 2353 毫秒，其中 2147 毫秒是识别。

原来的 `wait_quiet` 在每一帧都调用 `read_grid_np`，一次调用 50 毫秒，
一次等待要处理四十多帧，乘起来就是 2147 毫秒。

也就是说这两秒多跟游戏动画没有任何关系。

### 动画真实时长

把识别从等待循环里拿出来，用纯像素差重测（`tools/measure_anim2.py`）：

| 交换 | 拖动 | 首次运动 | 末次运动 |
|---|---|---|---|
| (4,2)↔(4,3) | 182 ms | 472 ms | 472 ms |
| (4,0)↔(4,1) | 183 ms | 478 ms | 589 ms |
| (4,2)↔(4,3) | 181 ms | 182 ms | 195 ms |
| (4,2)↔(4,3) | 183 ms | 491 ms | 535 ms |
| (4,2)↔(4,3) | 181 ms | 无运动 | 无运动 |
| (4,2)↔(4,3) | 182 ms | 150 ms | 622 ms |

中位数：拖动 182 毫秒，动画 535 毫秒。

```
单步下限 = 182 + 535 = 717 毫秒
速度上限 = 1.39 步/秒
```

所以"500 毫秒级"做不到，除非不等动画结算，但那样会丢步。

## 五次优化

### 一、把静止判定和识别拆开

原来的写法：

```python
while not still:
    frame = grab()
    grid = read_grid_np(frame)     # 每帧都认，一次 50 毫秒
    if is_still(frame): break
```

改成：

```python
while not still:
    d = frame_diff_downsampled()   # 只要一毫秒，不认棋盘
    if d < thr: still_frames += 1
grid = read_grid_np(frame)         # 确认静止了才认一次
```

识别开销从每步 2147 毫秒降到 62 毫秒，每步识别次数从四十多次降到两次。

### 二、加运动感知和静止窗

拆开之后静止判定 40 毫秒就成立了，比动画启动还快。结果是 bot 抢在动画前面
出手，交换被游戏吃掉，然后就是反复无效交换，盲点击还会点到菜单上。

改成必须先看见画面在动，再看见静止，而且静止要持续 250 毫秒以上。

### 三、补回拉黑机制

重写的时候漏了这个。同一格连着三次没效果就标记成未知不再用。

漏掉的后果是无效交换被无限重试，实测同一招重复了三十多次。

### 四、虚拟鼠标常驻

`VMouse2()` 构造的时候有 `time.sleep(0.4)`。每步都新建就等于每步白花
400 毫秒。改成只创建一次。

### 五、pending 复用

每一步开始都要等"交换前静止"，但上一步结束的时候已经确认过静止了。
把那个结果存下来给下一步用就行。

| 配置 | 步/秒 | 每步 | 等待 | 识别 |
|---|---|---|---|---|
| 无 pending | 0.48 | 2080 ms | 1523 ms | 154 ms |
| 有 pending | 1.11 | 900 ms | 642 ms | 62 ms |

等待时间从 1523 毫秒降到 642 毫秒。

## 假速度

有一版跑到 1.39 步每秒，每步 720 毫秒，是所有版本里最快的。但它的分/秒是 69.4，
比基线还低。

| 组 | 步/秒 | 每步 | 等待 | 分/秒 |
|---|---|---|---|---|
| P_off | 0.48 | 2080 ms | 1523 ms | 77.1 |
| P_on | 1.11 | 898 ms | 642 ms | 96.2 |
| P_on2 | 1.39 | 720 ms | 458 ms | 69.4 |

P_on2 步速最高，分/秒最低。因为等待压到 458 毫秒，动画还没结算完就出手，
交换被游戏吃掉。步数上去了，得分反而少了。

所以判断速度优化要看分/秒，看步/秒会被骗。

## 静止窗取多少

四十步一组：

| 静止窗 | 步/秒 | 等待 | 有效 | 分/秒 |
|---|---|---|---|---|
| 无 pending | 0.25 | 2583 ms | 98% | 26.2 |
| 250 ms | 0.86 | 888 ms | 98% | 168.3 |
| 350 ms | 0.79 | 989 ms | 95% | 124.4 |
| 450 ms | 0.80 | 969 ms | 92% | 58.6 |

250 毫秒最好。往上加反而更差，多等没换来更高的命中率，只是把步速拖下来了。

## 最后跑 100 步

| 轮次 | 步/秒 | 每步 | 有效 | 净得分 | 分/秒 |
|---|---|---|---|---|---|
| 第一轮 | 1.10 | 910 ms | 97/100 | +11560 | 119.9 |
| 第二轮 | 0.87 | 1155 ms | 98/100 | +14900 | 124.7 |

每步的构成是拖动 183 毫秒、等待 872 毫秒、识别 77 毫秒。

对比物理下限 717 毫秒，已经到极限的六成左右，剩下的主要是那 250 毫秒的静默窗。

## 怎么复现

```bash
python3 tools/profile_step.py      # 单步耗时剖析
python3 tools/measure_anim2.py     # 动画时长测量
cd bot && ./run2.sh play 100       # 跑 100 步
```

三个脚本都会打出拖动、首次运动、末次运动、静止确认各个时间点。

## 结论

原来的目标前提是错的，"动画占 96.7%" 实际上是识别开销。

单步 3940 降到 1155 毫秒，分/秒 26.2 涨到 168.3。

物理下限是 717 毫秒，已经贴着走了。

再快就是假速度，判断的时候要看分/秒。

不需要 SpeedHack，瓶颈从来不是游戏动画。
